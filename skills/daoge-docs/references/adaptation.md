# 项目适配方法

## 选择最小充分 Profile

| Profile | 适用项目 | 必备体系 |
| --- | --- | --- |
| `lean` | 小型、低风险、单团队应用 | 项目概览、当前版本、功能、架构、测试、发布、ADR |
| `standard` | 多模块产品或多人团队 | `lean` 加产品蓝图、PRD、稳定 ID、OpenAPI、数据模型、安全和边界 |
| `strict` | 资金、平台、安全、外部服务、受监管数据或高可用项目 | `standard` 加追踪矩阵、高风险设计、E2E、性能、恢复、机器证据和生产门禁 |

完整复用参考项目的 `docs` 治理能力时选择 `strict`。不要在没有明确需求时创建多套未来版本规格；保持一个活动版本，未来内容先进入隔离规划区。

## 初始化前调研

优先从仓库证据回答：

1. 当前版本解决什么业务问题，用什么指标判断成功？
2. 用户、运营者和外部调用方是谁？
3. 逻辑领域、服务职责和数据所有者是什么？
4. 已有哪些接口、数据库、外部系统和部署单元？
5. 哪些不变量涉及资金、授权、秘密、并发、删除、恢复或合规？
6. 已实现什么，现有测试和证据能证明到什么等级？
7. 发布环境、审批、回滚和恢复要求是什么？

把结果分为“代码或配置已证实”“需要确认的推断”“未知且阻塞”。不能从仓库得出的关键答案必须显式保留，不得生成方便但虚假的默认值。

## 稳定项目代码

选择 2 至 12 位大写英文字母或数字作为项目代码，并用于稳定 ID：

```text
CODE-FR-001
CODE-NFR-001
CODE-RG-001
E2E-001
ADR-0001
```

ID 发放后，产品改名、文件移动或需求废弃都不能改变或复用 ID。

## 状态词汇

机器字段保留以下英文状态，正文解释使用中文：

| 状态 | 中文语义 |
| --- | --- |
| `planning` | 只有方向，尚未形成规格 |
| `draft` | 正在编写，存在未决内容 |
| `ready` | 输入闭环，允许开始实现 |
| `implementing` | 正在实现 |
| `local_verified` | 当前提交已通过本地验证 |
| `staging_verified` | 当前构建已通过发布级预发验证 |
| `released` | 指定制品已发布并保留证据 |
| `blocked` | 已记录阻塞原因和责任人 |
| `deprecated` | 已废弃并指向替代项 |

状态只能依据证据向前推进；文档数量和作者主观判断不能推进状态。

## 采用顺序

1. 先建立文档权威和项目事实清单。
2. 冻结产品蓝图、活动版本范围和退出条件。
3. 建立稳定需求、领域和功能规格。
4. 冻结架构、API、数据、错误和界面契约。
5. 建立测试策略、E2E、性能、发布、回滚和恢复空间。
6. 建立冻结决策、ADR 和变更记录。
7. 生成索引与追踪矩阵，运行结构检查。
8. 按 discovery、version-ready、feature-ready、release 顺序通过门禁。
