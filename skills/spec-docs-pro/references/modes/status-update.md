# 模式：增量更新与实现状态回写

适用：需求变更后更新已有功能文档；测试通过或进展变化后回写实现状态。

## 原则

- **增量修改，不重写全文。** 只改受影响的章节，保留原有编号、验证记录和变更历史。
- **状态只写在实现状态表。** 功能主文档只追加验证记录，不写状态结论（硬规则 3、8）。
- **证据不升格。** 本地 mock 通过写“本地通过”，不写“生产通过”；静态审阅写“静态核验”，不写“已通过”。状态词见 [status-and-ids.md](../status-and-ids.md)。

## 需求变更

1. 读当前功能主文档，列出变更影响：功能边界、业务规则、接口、数据、AC、技术设计分支、依赖它的其他功能（用 `grep V1-FR-NNN` 查引用）。
2. 变更触及硬规则 4 的口径时，先走[冻结决策模式](decision.md)。
3. 修改受影响章节。新增 AC 用下一个未用编号，不重排已有 AC；废弃的 AC 标注“已废弃：{原因}”而不是删除。
4. 在功能文档“变更记录”和 `06-决策记录/V{n}-文档变更记录.md` 各追加一条。
5. 运行 `check-docs.mjs`。

## 状态回写

1. **核实证据。** 用户给了测试命令和结果时，记录原样；能运行时可以自己运行确认。没有证据的状态变更不写入。
2. **功能主文档：** 在“验证记录”追加一条：日期、环境、完整命令（密钥用 `***`）、N/M 通过、覆盖内容、遗留工作。同步更新“AC 逐项测试设计”表中对应 AC 的证据状态。
3. **实现状态表：** 更新该功能行的“状态”（只用标准词）、后端 / 前端 / 验证列和更新日期；在“进展记录”最上方追加一条“旧状态 → 新状态”。
4. **判定状态：** 全部 AC 本地或 CI 通过 → 本地验证；预发证据齐备 → 待验收；发布门禁证据齐备 → 已完成。部分通过仍是“开发中”。
5. **交付说明：** 新旧状态、依据的证据、尚缺的证据。
