## 1. 拆分判定

一个功能对应**一个可独立开发、测试和验收**的用户或系统目标。必须能回答：

1. 谁在什么条件下使用它？
2. 输入是什么？
3. 成功输出是什么？
4. 失败有哪些稳定结果？
5. 它读写哪些数据？
6. 如何独立证明完成？

判定信号：

- 应继续拆：多个不同角色、多个可独立上线目标、混合在线接口与后台任务/通知/导出/运维、数据跨域但没有共同事务目标。
- 不应拆：单个按钮、纯视觉组件、同一状态机的内部步骤、拆分后无法表达业务价值、无法独立验收。

好例子：用户注册、API Key 生命周期、支付回调、低余额通知、账号加权路由。
坏例子：“用户模块”（太大）、“注册页的提交按钮”（太小）。

## 2. 七段标准结构

主文档以 **YAML frontmatter + 单一一级标题** 开头，固定七段。文件名 `NN-中文功能名.md`，放在版本目录下的领域子目录中。

```yaml
---
title: "01 功能名"
version: V1
feature_id: V1-FR-001
domain: <领域名>
updated: YYYY-MM-DD
---
```

### 第 1 段 功能卡

表格列出：领域、上游依赖、版本、规格负责人、规格状态、规格版本、更新时间。实现状态只在版本实现状态文档维护。可选补充“目标”“功能边界”“来源与追踪”“完成定义”四个小节：

- 目标：一段话，可验收。
- 功能边界：包含 / 不包含两份清单。“不包含”是防止范围蔓延的关键。
- 来源与追踪：需求编号、上游 PRD 章节、关联 E2E、下游影响功能号。
- 完成定义：什么情况下这个功能可以说完成。

### 第 2 段 需求说明

用户故事、前置依赖、范围、业务规则、主流程、异常与边界、页面与交互、领域数据语义、本版本不做。

- 主流程用编号步骤或 Mermaid 流程图；异常与边界逐条列出触发条件与稳定失败。
- HTTP 字段的类型、必填与格式约束只在 OpenAPI 写；功能文档描述这些约束对应的业务含义，不复制 schema。
- 业务规则是“违反时必须拒绝/降级”的硬规则，不是实现建议。

### 第 3 段 接口契约

公共约定、接口清单（含 operationId）、业务契约要求、错误触发条件与 error_key 映射。HTTP 字段、类型、约束和请求/响应示例只在 OpenAPI 维护。

- 无接口时写“不适用 + 理由”。
- 公共规则（鉴权方式、响应包体、分页、错误结构）引用公共契约，不复制。
- 功能主文档引用 OpenAPI operationId，不复制字段 schema；具体数值错误码以统一错误码文档为准。

### 第 4 段 数据与事务

涉及数据、约束与事务、字段读写矩阵、状态与生命周期、物理约束与迁移、数据所有权、安全与保留。

- 无持久化时写“不适用 + 理由”。
- 状态与生命周期写清“初始状态 → 事件 → 新状态”。
- 资金、并发、幂等场景写清失败与补偿路径；事务边界要明确哪些步骤必须原子。

### 第 5 段 验收标准

详见第 6 节。三段式：功能验收（AC 逐条 Given/When/Then）+ 自动化测试映射 + AC 逐项测试设计 + 回归要求。

### 第 6 段 实现与验证

工程落点、任务清单（后端/前端/测试）、当前差距、已有实现证据、剩余工作、文档就绪检查、验证记录（日期/环境/代码版本/命令/结果/证据/遗留风险）。

- 只记录可被仓库或外部证据验证的事实。
- 静态核验必须标注“不构成测试通过证据”。

### 第 7 段 技术设计（标准风险内联）

单元契约、伪代码、分支到测试追踪。高风险功能把这一段拆成独立的 `NN-功能名-技术设计.md`，主文档只保留链接与来源行。

## 3. 两种状态：规格状态与实现状态

| 状态 | 含义 | 维护位置 |
| --- | --- | --- |
| 规格状态 | 文档是否具备开发输入（Draft / Ready） | 功能卡与执行空间表格 |
| 实现状态 | 代码与证据实际做到哪一步（规划中…已完成/阻塞） | 版本实现状态文档，是唯一维护位置 |

两者不能混用：规格 Ready 不等于实现完成；实现完成也不代表规格已冻结。功能主文档不复制实现状态；索引只提供链接，状态表中的功能 ID 必须与功能文档 ID 一致。

## 4. 风险分级

下列任一命中即为**高风险**，必须独立技术设计：

- 资金：余额、扣费、退款、结算、对账、价格快照。
- 权限与身份：认证、鉴权、角色、所有权、密钥/凭证。
- 秘密：密钥、Token、签名、加密、日志脱敏。
- 隐私与个人信息：PII 收集、查看、导出、跨境或删除，必须评估最小化、权限、审计、保留和脱敏。
- 路由与外部依赖：账号选择、限流、熔断、上游协议适配。
- 外部回调与异步：支付回调、Webhook、队列、定时任务、补偿。
- 跨系统状态：多个服务/存储共同维护一个业务状态。
- 动态制品与外部输入：可上传/下载的协议包、目录同步、外部 URL。
- 数据删除与不可逆操作：级联删除、归档、导出、审计。

标准风险功能命中“重新深度评审触发条件”后，必须先更新风险分级表和技术设计，再进入开发。分级的价值在于把“必须逐分支验证”的功能挑出来，避免所有功能都被当成高风险。

## 5. 技术设计

独立技术设计保持精简，固定三节 + 一段约束备注：

```text
# NN 功能名：技术设计
来源：链接到主文档（需求/接口/数据/验收细节以主文档为准）

## 单元契约
| 函数 | 前置条件 | 返回 | 副作用 |

## 伪代码
带分支 ID 注释的类 Python/C 伪代码

## 分支到测试追踪
| 分支 | 功能 AC | 跨功能验收 |

## 约束备注
数据库约束/锁是最终兜底；秘密不得出现在日志；分支未映射 AC 不满足 Ready
```

当功能是异步任务/长流程/外部回调型高风险能力时，可在三节之外追加这些小节（按需，不强制）：

- **切片与可独立实施边界**：把能力拆成可单独验收的切片（如 S0a 纯契约、S1 运行时），每片写清依赖与完成定义。
- **迁移与回滚**：数据结构变更、历史回填、兼容期与回滚方式。
- **素材与产物流转**：上传、存储、访问权限（签名/过期）、清理策略。
- **推进与恢复**：任务状态机、租约/重试、进程中断后的恢复路径与幂等。

伪代码规范：

- 类 Python/C 语法，有类型标注；`REQUIRE` 写前置条件，`ASSERT` 写关键不变量。
- 显式标注副作用（`// ASYNC:`）和错误路径（`ROLLBACK; RETURN Err(code, "error_key")`）。
- 每个关键判断、状态迁移、事务或外部副作用一行一个分支 ID 注释（`// B19-01`），编号格式 `B<功能号>-NN`，只增不改。
- 数据结构用表格（字段/类型/约束/说明）。
- 事务段用 `BEGIN TRANSACTION … COMMIT OR ROLLBACK` 标出边界；锁与幂等检查显式写出。

Review 口径：伪代码里的每个关键分支都应能在测试矩阵里找到覆盖；测试里的 E2E 用例应能回溯到需求和概要里的业务目标。问一句“这个测试证明了用户路径可用，还是只证明 mock 被调用过？”

## 6. 验收标准与映射

AC 来源是需求、接口、数据、状态机、异常流程，不允许凭空出现。写法：

```markdown
#### AC01 正常注册

Given 使用未注册邮箱和合法密码。

When 提交注册。

Then 创建 active 用户和零余额账户，响应不包含 password_hash。
```

AC 编号格式 `ACNN`，功能内唯一；跨功能引用写作 `<版本>-FR-NNN/ACNN`。

两张映射表：

1. **自动化测试映射**：按 AC 范围聚合，列 `AC 范围 | 自动化重点 | 建议测试文件 | 建议命令 | 当前状态`。
2. **AC 逐项测试设计**：逐条 AC，列 `AC | 验收重点 | 测试层级 | 目标资产 | 目标命令 | 初始资产状态`。

分层口径：Unit / Integration / E2E / 前端 / 手工。目标资产必须写具体文件路径；命令必须可执行；状态用词：未创建 / 规划中 / 已通过 / 失败。

最低覆盖矩阵（每个功能都要有）：正常主流程、必填/格式/上下界/枚举、未登录/错误角色/对象所有权、资源不存在/禁用/过期/依赖冲突、重复提交与幂等、关键写操作并发与回滚、日志与响应敏感信息、前端加载/空态/失败态/成功反馈。

资金类附加：Decimal 精度与舍入、并发扣费/补单/退款、任一步失败全事务回滚、订单-用量-消费-流水-审计关联完整。

## 7. 领域与索引维护

1. 新增功能先在版本索引、领域 README、功能查找表登记，再创建主文档。
2. 接口、表结构、错误码变化 → 同步主文档对应章节 + 公共基线 + openapi + 追踪矩阵。
3. 高风险功能在技术设计索引登记，写明风险焦点与分支范围。
4. 跨功能链路维护在端到端验收规范与执行空间，主文档不重复。
5. 不适用的模板项写“不适用 + 理由”；文档结构或路径变化后运行 `check-docs`。
6. 使用图片/文件的产品功能，明确上传组件、接口、类型与大小限制、状态、存储引用和清理策略；不要让用户填写外部 URL。
