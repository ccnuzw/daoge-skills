# 产品蓝图与版本 PRD 写作及评审

两份产品文档要让评审者在不逐一打开功能规格的情况下，理解用户要完成什么、系统如何回应、何时算成功。它们保留产品语义和跨功能场景；接口字段、数据约束和单功能 AC 仍以功能主文档、OpenAPI、数据模型为权威来源。引用稳定 ID 和链接，避免复制第二套契约。

## 先收集事实

在动笔前，按角色记录：目标与触发场景、现在如何完成、主要障碍、成功结果、常见失败、权限边界。再记录首版范围、后续版本、已冻结决策、外部证据和未决问题。资料不足时标注“待确认 + 责任人/验证方式”，不得把推测写成冻结结论；影响权限、资金、删除或外部副作用的未决问题阻止规格 Ready。

## 产品蓝图：长期产品判断

蓝图回答“为谁解决什么问题、为什么这样组织能力、长期如何衡量”。概念使用稳定 ID 并登记所有者、首次适用版本和权威定义；成功标准逐项关联指标口径、能力/功能、验证证据、责任人和状态。至少让读者找到：

- 角色与场景矩阵：每个重要角色的目标、触发、当前阻碍、期望结果，以及适用版本；未来角色不能被写成首版已可用。
- 能力地图与概念关系：主要能力域、关键对象及所有权、依赖与边界；具体字段和状态枚举链接到权威契约。
- 跨角色核心流程：触发、参与者、主要步骤、成功终态、失败/恢复路径、关联能力和版本；不能只列导航名称或画一条箭头。
- 信息架构：各角色能到达的入口、主要任务及权限差异，和版本路线图相符。
- 指标、非功能目标与风险：每项指标含口径、当前基线或“未测”、目标、观测方法和适用版本；未冻结数值说明何时由谁冻结。风险有影响、应对和待决事项的跟进位置。

蓝图不逐接口定义请求体，不复制全部功能 AC，不维护实现进度。版本变化后检查角色、场景、指标、导航与路线图是否仍一致。

## 版本 PRD：可评审的交付体验

版本 PRD 回答“这版谁能完成哪些任务、在什么条件下、失败时如何恢复、怎样验收”。至少包括：

- 本版目标、明确排除项和归属版本；未来能力可列在边界表，但不能混入本版交付场景或页面。
- 按角色列出关键场景。每个场景有触发、前提、主要步骤、成功结果、失败/恢复、关联功能 ID 与跨功能验收 ID；对关键路径补足足以执行的步骤，不能只有 `A -> B -> C`。
- 页面/入口视图：主要任务、可见条件、提交/取消反馈、空态、加载态、错误态和关联功能。UI 字段与路由的权威定义仍放在功能规格和界面/路由规范。
- 跨功能业务规则与非功能约束：只保留影响整个用户旅程的规则和可量化目标；细节链接到功能规格、接口、数据和错误码。
- 版本验收场景：真实入口、成功终态、关键失败断言、E2E/发布门禁编号及证据要求；演示脚本不能替代异常和权限验收。
- 交付顺序与依赖：先决条件、阶段产物、不能提前宣称完成的能力。
- 版本交付闭环：每个交付单元关联功能、AC、E2E、负责人、完成定义与证据；发布门禁写明阻塞级别、责任人和失败处置。
- 非功能需求：指标目标、当前基线、测量窗口/环境、负责人和验证证据；未知目标写出冻结条件，不留空。

对于每条关键场景，评审时追问“谁触发、输入来自哪里、状态如何变化、失败后用户能做什么、哪份功能规格和测试证明”。如果答案只能从几份互不相连的规格中猜测出来，PRD 还不是合格的版本入口。

### 一条场景应达到的具体程度

例如“成员申请访问受限资源”：说明成员从哪里发起申请，系统如何显示待审批状态，审批人从哪里收到并处理申请，批准后成员何时获得访问权。再说明资源已删除、审批人无权限、重复提交和通知失败时各自的可见结果与恢复动作。最后链接申请、授权两个功能 ID 和一条从申请到首次访问的 E2E。这里描述的是用户可观察的行为；请求字段、权限枚举和事务细节仍由对应规格与契约定义。

## 单一来源与深度取舍

产品文档可以写清业务效果，例如“重复提交不会生成第二次扣费”，并链接对应功能 ID、AC 和 E2E；不要复制数据库列、完整 API 请求/响应或错误码清单。小项目可合并场景和页面视图，但关键路径的成功、失败与验收追踪不能省略。文档长度由场景复杂度决定，不按样板行数、页面数量或模块数量设门槛。

## 评审清单

1. 重要角色、核心场景、能力地图、导航及版本范围相互一致；未来能力有清楚归属。
2. 核心场景覆盖首次使用、重复操作、权限不足、外部失败和恢复；不适用项有业务理由。
3. 每个本版场景能追踪到本版功能和验收；没有孤立的必做能力或无来源页面。
4. 指标有口径、样本/环境、目标和验证计划；“未测”不被写成已达标。
5. 发现产品规则与功能、OpenAPI、数据模型冲突时，先记录冻结决策，再同步权威来源。
6. 结构检查通过后仍进行产品/技术/测试评审；自动检查只能证明结构和引用关系，不能证明场景真实或业务选择正确。
