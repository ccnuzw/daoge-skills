# {{活跃版本}} E2E 运行手册

## 1. 执行入口

```sh
<统一的 E2E 命令>
```

该命令执行已落地的用例；分文件入口和证据状态以[用例矩阵](用例矩阵.md)为准。本地自动化不包含真实外部依赖或 production-gate，不能把本地通过误报为生产验收通过。

## 2. 批次前置

1. 记录 `run_id`、代码版本/构建标识、操作者、环境类型。
2. 启动依赖组件并执行[环境说明](环境说明.md)的 health/ready 检查。
3. 确认外部依赖模式，并确认日志脱敏开启。
4. 创建[测试夹具](测试夹具.md)中的批次测试数据。

前置失败时不执行用例，批次状态记为 `environment_failed`。

## 3. 推荐执行顺序

| 阶段 | 用例 | 原因 |
| --- | --- | --- |
| A 身份基础 | <用例> | 创建身份与会话 |
| B 资金/数据基础 | <用例> | 建立可重复验证的业务状态 |
| C 主链路成功 | <用例> | 验证核心闭环 |
| D 拒绝分支 | <用例> | 证明失败时无副作用 |
| E 边界与并发 | <用例> | 幂等、回滚、竞态 |

单独运行某用例时，测试框架必须自动建立其依赖夹具，不得依赖另一批次遗留数据。

## 4. 每个用例的统一步骤

1. Arrange：创建或查询本批次夹具，保存对象 ID，不输出秘密。
2. Act：通过公开入口触发行为；内部入口只用于服务间或后台任务专项验收。
3. Assert API：校验 HTTP、code/error_key、响应字段和 request_id。
4. Assert side effects：校验关键状态、流水、审计和外部调用次数。
5. Replay：对幂等用例重放相同事件或幂等键。
6. Archive：保存脱敏报告、失败日志片段和必要查询结果。

## 5. 失败处理

- 业务断言失败：保留批次数据，记录首个失败步骤和 request_id，不自动把对象修成成功状态。
- 环境故障：标记 `environment_failed`，不得把用例记为业务失败或通过。
- 依赖替身不可用：中止依赖它的已执行用例，保留受影响清单与健康检查结果。
- 涉及数据不一致、重复副作用或负余额时立即停止后续相关用例。

## 6. 批次完成

1. 汇总 passed/failed/skipped/environment_failed；“未自动化”和“未纳入本批次”不是 passed。
2. 更新[验证证据](验证证据.md)，填写代码版本、命令、报告位置和遗留风险。
3. 只在有可复现证据时更新实现状态或功能主文档的“实现与验证”章节。
4. 按环境保留策略清理批次数据。
