## 1. 它是什么

一套**以文档为唯一决策输入**的开发方法：范围、行为、约束、验收都在文档里冻结，代码和测试负责兑现并留下证据。

- 对 AI：读完有限几份文档就能得到与产品、接口、数据、错误码一致的实现，不需要猜。
- 对人：任何时候能回答“为什么这么做、做到哪了、还差什么、怎么证明”。
- 对团队：开发、测试、验收、交接共用同一套口径，冲突有仲裁机制而不是靠人记。

它**不是**“多写文档”，也不是“先写一堆再冻结”。文档是约束链：上游定义边界，下游逐层收敛到可执行逻辑和可验证证据。最容易断链的地方有三处——需求没人追踪到验收、验收没有真 E2E、接口/数据有两套口径。

## 2. 四条基本假设

1. **读者的上下文有限**：AI 和新人不会读完整套文档。体系必须提供按任务、按业务词、按编号三条入口，且单份文档要能独立回答自己边界内的问题。
2. **事实会变，且分三类**：冻结需求、当前实现、待修差距。混在一起就会出现“文档说做了、代码没做”或“代码这样做，就偷偷把需求改了”。
3. **没有仲裁必分叉**：任何共享事实（字段名、枚举值、错误码、状态机、金额单位）只要有第二个维护位置，就会产生分叉；分叉必须由决策机制收敛。
4. **证据会撒谎**：静态检查、mock、本地结果很容易被当成“通过”。所以证据必须分级、绑定环境与提交、可复现。

## 3. 十二条不变式

按重要性排序。规模裁剪可以简化承载形式，但不得违反任一不变式；前 6 条属于不可削弱的追踪与决策底线。

| # | 不变式 | 为什么 | 落地检查 |
| --- | --- | --- | --- |
| 1 | 单一权威来源 | 两处维护必然分叉 | 每份导航文档有一张“权威来源表”；同一事实只在一处定义，其余用链接 |
| 2 | 稳定 ID 永不变 | 追踪链的锚点，文件会移动 | 需求/AC/分支/决策 ID 有登记表；移动或改名不改 ID |
| 3 | 三类事实分离 | 防止用代码反改需求、用文档冒充实现 | 需求在功能文档；状态只在实现状态表；差距和证据在实现与验证章节 |
| 4 | 冲突先决策后编码 | 代码里兼容两套语义是最贵的债务 | 冻结决策表记录选择、影响、迁移；代码与其不一致时改代码或发起变更 |
| 5 | 一个功能一个可独立验收目标 | 拆得太小无法验收，太大无法并行 | 六个问题（谁/输入/成功/失败/数据/如何证明）全部可答 |
| 6 | AC 可执行且映射测试 | 没有映射的验收等于没有验收 | 每条 AC → 层级 / 目标资产 / 命令 / 证据状态 |
| 7 | 模板不是业务事实 | 防止“看起来很完整”的空文档 | 不适用条款写“不适用 + 理由”；禁止通用模板句 |
| 8 | 权威来源不一致时停止 | 调用方不能自行选口径 | 发现冲突 → 冻结决策 → 同步全套 |
| 9 | 状态只在实现状态维护 | 多处宣布完成度必然互相矛盾 | 功能文档与索引不复制状态值，只链接实现状态表 |
| 10 | 证据分级、不许升格 | “本地通过”被当成“可交付”是最大风险 | 验证记录含日期/环境/提交/命令/结果/证据位置；标注证据等级 |
| 11 | 归档不删除 | 历史是审计材料，也是防重复踩坑的资产 | 废弃材料进归档 + 迁移映射；被取代决策标注取代关系 |
| 12 | 版本定范围，功能定行为 | 混在一起会导致范围蔓延或行为缺失 | 版本文档只回答“做不做”，功能文档只回答“怎么做、怎么验收” |

## 4. 分层模型：四个问题层

| 问题层 | 回答 | 文档位置 | 变化频率 |
| --- | --- | --- | --- |
| 范围 | 这个版本做不做、依赖谁、成功标准 | `02-产品与版本` | 低 |
| 行为 | 单个可验收目标怎么做、输入输出、如何验收 | `03-功能规格` | 中 |
| 一致性 | 跨功能的架构、接口、数据、错误码、界面约束 | `04-技术架构` | 中 |
| 事实 | 代码、测试、migration、运行证据实际做到什么 | 代码库 + `05-测试与发布` + 实现状态 | 高 |

判断“这件事该写哪”：先问它属于哪一层，再问谁是权威来源。跨层信息用链接，不复制。

此外有两层辅助：`06-决策记录`（为什么这样定，含冻结决策与 ADR）和 `90/99`（非当前权威的参考与历史，必须与当前文档物理隔离）。

## 5. 追踪链

```text
稳定需求 ID (V1-FR-019)
  → 功能主文档（需求/接口/数据/验收）
    → 技术设计分支 ID (B19-01…)
      → AC (AC01…)
        → 测试层级 + 目标资产 + 命令
          → 证据（日期/环境/提交/结果）
            → 跨功能 E2E (V1-E2E-08) / 发布门禁 (V1-RG-012)
```

规则：

- 新增需求必须登记编号；新增接口必须有来源需求；没有孤立必做需求，也没有无来源接口。
- 编号表、追踪矩阵、功能索引、查找表是同一个事实组的四个视图，改一处要检查其余三处。
- 跨功能链路（如“注册 → 登录 → 调用 → 扣费 → 退款”）维护在端到端验收文档，功能文档只负责本功能边界。

## 6. 治理机制

七个机制，详细规则见 [governance.md](governance.md) 和 [evidence.md](evidence.md)：

1. **权威来源表**：每份导航文档列出“信息 → 维护位置”，冲突时按此仲裁。
2. **稳定编号**：`Vx-FR`（功能）/ `Vx-NFR`（非功能）/ `Vx-RG`（发布门禁）/ `Vx-E2E`（跨功能验收）/ `ACxx` / `B<功能号>-NN`（设计分支）/ `Dxxx` / `ADR-xxxx`。
3. **两种状态分开**：规格状态（Draft/Ready）表示“文档是否具备开发输入”；实现状态（规划中 → 开发中 → 基础实现 → 本地验证 → 待验收 → 已完成；异常态“阻塞”）表示“代码与证据做到哪一步”，只在实现状态文档维护。
4. **三道门禁**：版本进入开发门禁（未来版本解锁）、Definition of Ready（单功能可开工）、Definition of Done（单功能可交付）。发布另有发布检查清单。
5. **变更联动矩阵**：改接口/字段/错误码/页面/状态机/删除/权限/资金/进度，各自规定必须同步的文件与测试。
6. **证据分级**：静态核验 < 本地自动化 < 门禁环境 < 生产证据；不同等级不能互相冒充。
7. **两层自动检查**：`check-docs`（结构、链接、编号、索引，证明体系自洽）与 `docs-gate`（AC→测试资产→证据、审批摘要绑定权威文档哈希，判断能否交付）。结构检查通过不代表交付就绪。

## 7. 规模裁剪：S / M / L 三档

体系按体量裁剪，但**硬规则前 6 条永远保留**。升级时结构是超集，不丢工作。

| 维度 | S 轻量 | M 标准 | L 重度 |
| --- | --- | --- | --- |
| 适用 | 1 人、≤ 2 周、≤ 5 个功能 | 1–3 人、1–3 月、3–10 个模块 | 5+ 人、多子系统、3 月以上 |
| 文档形态 | 核心必需项精简；完整模板树作为可选参考并保留链接 | 本 skill 默认结构（8 个编号目录） | 默认结构 + 子系统目录 + 每功能独立技术设计 + 机器可读证据报告 |
| 功能文档 | 保留可追踪的七段结构，非适用章节写理由；可减少跨功能执行空间 | 七段固定结构 | 七段 + 高风险独立技术设计 + 分支 ID |
| 追踪 | 编号表 + AC 一段说明 | 编号表 + 追踪矩阵 + AC 映射表 | 完整追踪矩阵 + E2E 矩阵 + 性能预检矩阵 |
| 证据 | 验证记录（日期/环境/命令/结果） | 同上 + 端到端验收空间 | 同上 + 机器可读报告 + 审批摘要 |
| 自动检查 | policy 中 S 档必需项 | policy 中 M 档必需项 | policy 中 L 档必需项 + docs-gate |
| 前期文档时间 | 30 分钟 | 4–8 小时 | 1–3 天 |

**升级触发条件**（出现即升级，不要等“项目变大了”）：

- 团队从 1 人变 2–3 人 → S 升 M。
- 出现第二个子系统、需要独立 E2E、或功能涉及资金/权限/外部回调 → 升 L 的对应部分。
- 同一功能被两个团队改动、或功能数超过 10 → 必须 M 起步。

## 8. 新项目上手路径

```text
第 1 步  建骨架（S/M/L），确认 docs-policy
第 2 步  写范围层：产品蓝图 → 版本路线图 → 当前版本总览 + 产品需求
第 3 步  建编号与索引：需求编号表 → 功能查找表 → 追踪矩阵（可先空）
第 4 步  写公共基线：总体架构 → 服务边界 → 接口契约 + openapi → 数据模型 → 错误码 → 界面/路由
第 5 步  写验证层：测试策略 → 安全基线 → 端到端验收空间 → 发布空间 → 证据报告规范
第 6 步  逐功能写：登记编号 → 主文档七段 → 风险分级 →（高风险）技术设计 → AC 映射
第 7 步  建治理：冻结决策表 → ADR → 变更记录 → 归档与迁移映射 → check-docs 进 CI
```

顺序背后的逻辑：先冻结稳定的东西（范围、公共契约），再写易变的（功能细节、状态），最后接自动检查。反过来做会导致功能文档反复重写。

## 9. 反模式

- 只写产品总览，不写功能边界和字段、错误、状态。
- 用“见相关文档”“待补充”占位，却把功能标成已完成。
- 以代码现状回填需求，不做决策记录。
- 同一个字段/枚举/错误码在两个文档各写一份。
- 只改后端，不同步前端类型与契约；只靠前端做权限。
- 测试只 mock 内部函数却声称 E2E；把静态核验写成生产验证。
- 文档不归档、不改映射，旧结论与当前结论并存。
- 先写满模板再想业务，产出“结构完美但没有任何真实规则”的文档。

## 10. 与瀑布 SOP 的对应

传统六层文档（概要设计 / 系统设计 / 接口设计 / 详细设计 / 单元设计 / 测试设计）在本体系里的等价物：

| 瀑布 | 本体系 |
| --- | --- |
| 概要设计 | `04-技术架构/总体架构` + `02-产品与版本/版本总览` |
| 系统设计 | 服务边界、部署与运行拓扑、ADR |
| 接口设计 | 接口契约 + openapi/JSON Schema + 统一错误码 |
| 详细设计 | 功能主文档的需求/数据/状态机章节 |
| 单元设计 + 伪代码 | 高风险功能的技术设计（签名、前后置条件、副作用、分支 ID） |
| 测试设计 | 测试策略 + AC 映射表 + 端到端验收 + 证据 |

区别在于：这里的每一层都必须**向下游提供可验证的输入**，且能被自动检查；写完不是为了归档，而是为了让实现和验收有唯一依据。
