# 功能文档规范

本规范定义功能级文档的结构。完整开发流程见[功能开发流程](功能开发流程.md)。

## 1. 拆分原则

一个功能对应一个可独立开发、测试和验收的用户或系统目标。页面上的单个按钮、纯视觉组件或无法独立验收的内部步骤不单独建功能。

每个功能必须：

- 有稳定编号、清晰目标、输入、输出和完成条件。
- 标明上游依赖、下游影响和不做范围。
- 引用公共架构、接口、数据和错误码基线，不复制第二套公共规则。
- 同时描述冻结需求、当前实现证据和剩余差距。
- 具有可执行的 Given/When/Then 验收用例。
- 能从稳定需求 ID 追踪到验收用例和测试证据。

## 2. 标准文件结构

每个功能维护一份中文主文档，文件名为 `NN-中文功能名.md`。主文档只有一个一级标题，固定包含：

| 章节 | 必须包含 |
| --- | --- |
| 元信息与功能卡 | frontmatter（title/version/feature_id/domain/updated）与功能卡表格：领域、依赖、版本、规格负责人、规格状态和更新时间；实现状态只在版本实现状态文档维护 |
| 目标 | 一段话可验收目标 |
| 功能边界 | 包含范围和不做范围 |
| 来源与追踪 | 需求编号、上游章节、关联 E2E 和下游影响 |
| 需求说明 | 用户故事、前置依赖、范围、业务规则、主流程、异常、页面与交互、领域数据语义和本版本不做；HTTP 字段约束只维护在 OpenAPI |
| 接口契约 | 公共约定、接口清单（operationId）、业务语义与错误映射；HTTP 字段 schema 和请求/响应示例只在 OpenAPI 维护 |
| 数据与事务 | 涉及数据、约束与事务、字段读写矩阵、状态与生命周期、物理约束与迁移、数据所有权、安全与保留；无持久化时写明不适用原因 |
| 验收标准 | 正常、边界、权限、重复、并发、回滚和 UI 状态；AC 逐条 Given/When/Then，附自动化测试映射与 AC 逐项测试设计（层级/目标资产/命令/状态） |
| 实现与验证 | 工程落点、任务清单、当前差距、已有证据、剩余工作、文档就绪检查和日期化验证记录 |
| 技术设计 | 标准风险功能在主文档内维护单元契约、伪代码和分支到测试追踪 |

## 3. 高风险技术设计

资金、权限、秘密、PII、路由、外部回调、异步任务、动态制品和跨系统状态等高风险功能，额外维护 `NN-中文功能名-技术设计.md`，固定包含：

- 单元契约：函数签名、前置条件、返回/后置条件和副作用。
- 伪代码：带稳定分支 ID 注释，显式标注事务边界、错误路径与异步副作用。
- 分支到功能 AC、跨功能 E2E、NFR 或发布门禁的映射。
- 约束备注：数据库约束/锁作为最终兜底、秘密处理要求。

风险分级与独立设计要求见 [{{活跃版本}} 功能风险分级]({{活跃版本}}/功能风险分级.md)。标准风险功能的技术设计合并在主文档中，不建立第二个文件。

## 4. 公共基线

单功能文档不重复维护以下公共事实：

- 版本范围：[{{活跃版本}} 版本总览](../02-产品与版本/当前版本/{{活跃版本}}-版本总览.md)。
- 当前完成度：[{{活跃版本}} 实现状态](../02-产品与版本/当前版本/{{活跃版本}}-实现状态.md)。
- 稳定编号：[{{活跃版本}} 需求编号]({{活跃版本}}/00-{{活跃版本}}需求编号.md)。
- 需求映射：[{{活跃版本}} 需求追踪矩阵]({{活跃版本}}/00-{{活跃版本}}需求追踪矩阵.md)。
- 接口公共规则：[{{活跃版本}} 接口契约](../04-技术架构/当前版本/{{活跃版本}}-接口契约.md)与 [OpenAPI](../04-技术架构/当前版本/{{活跃版本}}-openapi.yaml)。
- 数据公共规则：[{{活跃版本}} 数据模型](../04-技术架构/当前版本/{{活跃版本}}-数据模型.md)与 migration。
- 跨功能验收：[{{活跃版本}} 端到端验收规范](../05-测试与发布/端到端验收/{{活跃版本}}-端到端验收规范.md)。
- 冻结决策：[{{活跃版本}} 冻结决策](../06-决策记录/{{活跃版本}}-冻结决策.md)。

发现冲突时先形成冻结决策，再同步主文档、公共基线、代码和测试。

## 5. 状态定义

功能卡中的“规格状态”只表示文档是否具备开发输入（Draft / Ready），与实现状态是两件事，不能混用。实现状态只维护在版本实现状态表，功能文档不记录第二份状态值。

| 状态 | 定义 |
| --- | --- |
| 规划中 | 已确定范围，尚未进入开发 |
| 开发中 | 已开始实现，但未满足全部验收条件 |
| 基础实现 | 主链路已有代码，仍存在专项测试或边界缺口 |
| 本地验证 | 实现和本地自动化已通过，仍缺生产或真实外部依赖证据 |
| 待验收 | 实现和自动化验证完成，等待业务验收 |
| 已完成 | 需求、实现、测试、文档和验收全部闭环 |
| 阻塞 | 存在明确外部依赖，当前无法继续 |

实现状态只在[{{活跃版本}} 实现状态](../02-产品与版本/当前版本/{{活跃版本}}-实现状态.md)维护，功能文档和导航索引不得复制状态值。

## 6. 维护规则

1. 新增功能先登记到功能索引与查找表，再创建主文档。
2. 接口、表结构或错误码变化时，同步更新主文档对应章节和公共基线。
3. “实现与验证”只记录可由仓库或外部证据验证的事实，不能用“存在代码”代替验收。
4. 功能 AC 编号在功能内唯一，格式为 `AC01`、`AC02`。
5. 跨功能链路在端到端验收规范中维护，主文档只负责本功能边界。
6. 每个 AC 必须映射测试层级、目标文件、目标命令、资产存在性和当前证据状态。
7. 规划命令不得伪装成已执行证据；静态核验必须声明“不构成测试通过证据”。
8. 不适用的模板项必须写明“不适用”及理由，不能留空。
9. 使用图片的产品功能必须落实共享上传组件、上传接口、类型/大小、状态、存储引用和清理策略；不得让用户填写图片 URL。
10. 文档结构或路径变化后运行 `node scripts/check-docs.mjs`。
