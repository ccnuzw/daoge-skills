# Spec-Docs-Pro 文档质量检查清单

本清单用于确保生成的规格文档符合所有质量标准。

---

## 📋 功能主文档质量检查

### ✅ 基础信息（必须）

- [ ] Frontmatter 完整（title, version, feature_id, domain, status, updated）
- [ ] 功能卡完整（领域、状态、上游依赖、版本、规格负责人、规格状态、规格版本、更新时间）
- [ ] 目标清晰（一句话说明核心目标）
- [ ] 功能边界明确（包含 + 不包含，每项都有说明）

### ✅ 来源与追踪（必须）

- [ ] 主 PRD 章节号
- [ ] V1 README 章节号
- [ ] E2E 编号
- [ ] 下游影响功能列表

### ✅ 需求说明（必须）

- [ ] 用户故事（作为...我希望...以便...）
- [ ] 前置依赖（系统依赖、功能依赖、外部依赖）
- [ ] 业务规则（至少 3 条关键规则）
- [ ] 主流程（步骤清晰）
- [ ] 异常与边界（列出主要异常场景）
- [ ] 字段规则表（字段、类型、必填、规则）

### ✅ 接口契约（必须）

- [ ] 接口清单表（接口、鉴权、用途）
- [ ] 请求字段表（字段、位置、类型、必填、规则）
- [ ] 响应字段表（接口、请求/查询、成功 data）
- [ ] 错误矩阵（code、error_key、HTTP、提示）
- [ ] 请求示例（JSON 格式）
- [ ] 成功响应示例（JSON 格式）

### ✅ 数据与事务（必须）

- [ ] 涉及数据表列表（schema.table + 说明）
- [ ] 约束与事务（数据库约束、事务要求）
- [ ] 字段读写矩阵（数据、操作、字段）
- [ ] 状态与生命周期（如有状态机）
- [ ] 物理约束与迁移（字段约束、触发器）

### ✅ 验收标准（AC）- 核心！

#### AC 清单

- [ ] 至少 5 个 AC（覆盖正常、异常、边界）
- [ ] 每个 AC 使用 Given-When-Then 格式
- [ ] Given 条件详细（不是"有效的输入"而是"邮箱 user@example.com，密码 Test1234"）
- [ ] When 操作具体（不是"提交"而是"POST /api/v1/register"）
- [ ] Then 结果完整（包含所有副作用，如数据库写入、状态变更）

#### AC 逐项测试设计表（必须！）

- [ ] 每个 AC 都有一行
- [ ] 每行包含：AC 编号、验收重点、测试层级、目标资产、目标命令、初始资产状态
- [ ] 测试层级明确（单元/集成/E2E/前后端）
- [ ] 目标资产是具体文件路径（可多行，前后端分开）
- [ ] 目标命令完整可执行（包含环境变量、包名、测试名）
- [ ] 初始资产状态标注日期和状态（规划中/已创建/已通过）

#### 自动化测试映射

- [ ] AC 范围表（AC01-AC05、AC06-AC10）
- [ ] 建议测试文件路径
- [ ] 建议命令
- [ ] 当前状态

### ✅ 实现与验证（必须）

#### 工程落点

- [ ] 后端代码路径
- [ ] 前端代码路径
- [ ] 数据 migration 文件名
- [ ] 测试文件路径

#### 验证记录（必须！）

- [ ] 至少一条验证记录
- [ ] 包含完整环境变量（DATABASE_URL, CARGO_HOME 等）
- [ ] 包含精确命令（cd xxx && cargo test -p xxx --test xxx）
- [ ] 包含通过数量统计（N/M 通过）
- [ ] 包含详细覆盖内容说明（列出所有测试场景）
- [ ] 包含明确的遗留工作（前端交互、E2E 仍待补）

#### 文档就绪检查

- [ ] 所有检查项已勾选
- [ ] 实现任务清单（后端、前端、测试）
- [ ] 当前差距说明
- [ ] 冻结后的剩余工作

### ✅ 技术设计（如有复杂逻辑）

#### 内嵌技术设计（标准风险）

- [ ] 单元契约表（函数、前置条件、后置条件、副作用）
- [ ] 伪代码包含分支 ID（// B{编号}-01, B{编号}-02...）
- [ ] 伪代码标注事务边界（BEGIN TRANSACTION / COMMIT / ROLLBACK）
- [ ] 分支到测试追踪表（分支 ID、AC 映射、E2E 映射）

#### 独立技术设计文档（高风险）

- [ ] 引用独立文档（{编号}-{功能名}-技术设计.md）
- [ ] 文档包含风险评估
- [ ] 文档包含并发控制说明
- [ ] 文档包含幂等保证机制

- [ ] 包含：分支 ID、分支描述、AC 映射、E2E 映射、NFR 映射
- [ ] 分支 ID 与伪代码注释精确对应（一一对应）

- [ ] E2E 映射明确（关键分支映射到 E2E 场景）

## 📋 使用方法

### 文档生成前

在生成文档前，按照本清单检查信息是否齐全：

```
我现在生成文档前，先做一个质量检查：

【AC 逐项测试设计表】
- [ ] 每个 AC 都有明确的测试层级
- [ ] 每个 AC 都有具体的目标资产
- [ ] 每个 AC 都有可执行的目标命令
- [ ] 每个 AC 都有初始资产状态

【技术设计要求】（如有高风险功能）
- [ ] 伪代码每个关键分支标注了分支 ID
- [ ] 分支到测试追踪表建立了完整映射
- [ ] 事务边界明确标注
- [ ] 并发控制说明完整

【验证记录格式】
- [ ] 完整的环境描述
- [ ] 精确的命令
- [ ] 通过数量统计
- [ ] 覆盖内容说明
- [ ] 遗留工作

所有检查通过！开始生成文档...
```

### 文档生成后

生成文档后，按照本清单逐项检查：

1. **打开文档**，找到"验收标准"章节
2. **查看 AC 逐项测试设计表**：是否完整？
3. **查看验证记录**：格式是否符合要求？
4. **如有技术设计**：查看分支追踪表是否完整
5. **补充缺失项**：如果有检查项未通过，立即补充

### 对话中检查

在对话过程中，主动提醒用户补充缺失信息：

```
我注意到还有一些关键信息需要确认：

【AC 测试映射】
❌ AC05 还没有对应的测试层级说明
   → 需要确认是单元测试、集成测试还是 E2E 测试

【技术设计】
❌ 并发场景（AC04）还没有讨论加锁策略
   → 需要确认是乐观锁、悲观锁还是分布式锁

需要我们补充这些吗？
```

## 📊 质量评分标准

### 优秀（90-100 分）

- ✅ 所有必须项都齐全
- ✅ AC 逐项测试设计表完整且详细
- ✅ 验证记录包含完整环境和覆盖说明
- ✅ 分支追踪表建立完整映射
- ✅ 技术设计包含分支 ID、事务边界、并发控制

### 良好（70-89 分）

- ✅ 大部分必须项齐全
- ⚠️ AC 逐项测试设计表基本完整，但部分细节缺失
- ⚠️ 验证记录基本符合格式，但覆盖说明不够详细
- ⚠️ 分支追踪表基本完整，但部分映射缺失

### 及格（60-69 分）

- ⚠️ 必须项大部分齐全，但关键项缺失
- ❌ AC 逐项测试设计表不完整（缺少测试层级或目标命令）
- ❌ 验证记录格式不规范（缺少环境变量或通过数量）
- ❌ 分支追踪表缺失或不完整

### 不及格（< 60 分）

- ❌ 关键必须项缺失
- ❌ 没有 AC 逐项测试设计表
- ❌ 没有验证记录或格式完全不符合要求
- ❌ 技术设计没有分支 ID 或分支追踪表

## 📝 常见问题

### Q1：为什么 AC 逐项测试设计表这么重要？

**A**：因为它是验收标准的核心，建立了从 AC 到测试资产到测试命令的完整映射。没有这个表，AC 就是空话。

### Q2：验证记录为什么必须包含环境变量？

**A**：因为测试结果必须可复现。没有环境变量，别人无法重现你的测试。

### Q3：分支 ID 必须连续吗？

**A**：是的。分支 ID 从 B{编号}-01 开始连续编号，不能跳号，这样才能准确追踪。

### Q4：E2E 的 Given 条件为什么要这么详细？

**A**：因为 E2E 测试必须可复现。不详细的 Given 条件会导致测试结果不稳定。

### Q5：技术设计什么时候需要独立文档？

**A**：涉及资金、权限、加密、外部回调、复杂并发等高风险场景时，必须创建独立技术设计文档。
