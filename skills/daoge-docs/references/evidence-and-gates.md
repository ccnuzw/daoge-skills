# 证据与门禁

## 证据等级

| 等级 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 静态检查 | 文件、链接、ID、映射和预期结构存在 | 运行时行为正确 |
| 单元测试 | 纯规则和局部分支通过 | 数据库或集成行为 |
| 集成测试 | 真实数据库或组件契约正确 | 完整用户路径和生产依赖 |
| 本地 E2E | 记录的本地依赖下跨功能路径可用 | 预发容量或真实外部服务 |
| 预发 | 类生产拓扑和配置可用 | 自动获得生产批准 |
| 生产门禁 | 真实依赖、恢复、安全、容量和批准满足 | 未来发布继续安全 |

结论不得高于证据等级。本地结果不能改名为预发证据，失败批次不能被成功批次覆盖。

## Discovery 门禁

要求项目问题、用户、成功指标、仓库现状、技术栈、外部依赖、现有能力、未知项和验证计划已经查明。关键方向未知时不得进入版本冻结。

## Version Ready 门禁

要求：产品蓝图和当前版本范围冻结；FR/NFR/RG 使用稳定 ID；功能主文档和高风险设计闭环；领域、API、数据、错误、安全和测试边界一致；每条需求进入追踪矩阵和 E2E；冻结决策无冲突；版本进入开发清单完成。

## Feature Ready 门禁

每个功能必须具有：问题、用户、结果、范围和非目标；冻结的输入、输出、权限、错误和状态转换；数据所有权、约束、事务、幂等、删除和保留语义；成功、边界、权限、重复、并发、失败和回滚验收项；每条 AC 的测试层、目标资产、命令和证据状态；高风险功能的独立技术设计。

## Done 与可解释性

实现完成至少要求：服务端业务校验和授权；数据库约束与事务；前端完整状态或明确不适用；稳定错误映射；与风险相称的单元、集成、前端和 E2E；敏感数据和可观测性复核；功能证据与实现状态同步。

重要结果必须能解释：采用的规则版本、输入事实、命中分支、状态转换、数据和外部副作用、失败处置、证据入口。只能通过日志猜测的行为不算可解释。

## Release 门禁

要求四类机器报告：

| 类型 | 必须证明 |
| --- | --- |
| `development` | 干净检出、依赖、构建、静态检查、单元和集成命令 |
| `e2e` | 发布级环境、逐用例结果、无跳过关键用例 |
| `performance` | 已批准负载、阈值、实测值和比较结果 |
| `release` | 精确制品、迁移、备份、恢复、安全、冒烟、观察、回滚和批准 |

四类报告必须绑定同一版本、提交和不可变构建。报告记录命令、退出码、检查项、环境和时间；检查器重新计算关键结论，不信任手填的“通过”。发布批准必须由有权人员在全部证据产生后确认。

## 四类 details 契约

| 类型 | 必填内容 | Release 门禁复算规则 |
| --- | --- | --- |
| `development` | `clean_checkout`、`dependency_mode`、`services`、`required_checks` | 必须是干净检出，且 `build/static/unit/integration` 均有通过检查项 |
| `e2e` | `dependency_mode`、`required_case_ids`、`cases` | 必需用例必须与当前 E2E 文档全集一致，逐项为 `passed` 且有证据 |
| `performance` | 负载 ID、SHA-256、批准人和时间、逐场景指标 | 重新执行 `lte/gte/lt/gt/eq`，手填结果必须与复算一致且达到阈值 |
| `release` | 制品 SHA-256、当前 E2E/性能报告、迁移到回滚的结构化检查项 | 每项必须 `passed` 并有证据，或 `not_applicable` 并有明确原因 |

发布审批必须包含 `proposal_id`、`confirmed_by`、`confirmed_at` 和 `authority_digest`。使用 `authority-digest` 计算当前权威集合摘要；摘要内任何文档变化后，旧审批失效。

## 证据边界

- 报告位于仓库内或稳定引用受控存储，不使用个人临时路径。
- 报告不得包含密钥、Token、签名 URL、完整敏感请求或未脱敏数据。
- 所有批次保留，当前证据清单只选择有效批次。
- 证据必须绑定当前源码和制品；权威文档或构建变化后旧批准失效。
- 不得为了通过门禁伪造命令、时间、提交、环境、结果、审批或剩余风险。
