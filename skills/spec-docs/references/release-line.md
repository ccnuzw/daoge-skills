# 版本能力线与发布状态

## 1. 为什么单独维护版本清单

`spec-docs` 同时包含 Skill 本体、项目内复制的脚本、模板和治理参考。只在 `SKILL.md` 或 `CHANGELOG.md` 中写版本，容易出现“文档声明已发布，但工作树还包含未发布能力”的漂移。

Skill 根目录的 `release-manifest.json` 是能力发布状态的机器可读清单；`SKILL.md` 的 frontmatter 是触发和当前声明版本的权威入口。两者必须保持一致。

## 2. 当前能力线

| 能力线 | 状态 | 说明 |
| --- | --- | --- |
| `1.7.0` | 当前声明版本，未发布 | 事实注册表、统一机器状态、任务上下文包 |
| `1.8.0` | 工作树已实现，未发布 | 显式关系、追踪报告、关系图影响传播 |
| `1.9.0` | 工作树已实现，未发布 | 证据新鲜度、失效传播、规格差异基线 |

“工作树已实现”不等于 GitHub 标签、安装地址或项目副本已经可用。发布前必须先更新清单、README、CHANGELOG、固定安装地址和评测记录。

## 3. 收口规则

1. 当前声明版本只能有一个，必须同时出现在 `SKILL.md`、README 和 `release-manifest.json`。
2. 未发布能力可以进入工作树，但必须标记为 `implemented_in_worktree`，不能写成已发布。
3. 固定版本安装命令只能指向已发布标签，不能指向本地能力线。
4. 项目内脚本副本属于项目自己的版本；升级项目脚本时必须记录来源 Skill 版本。
5. 能力发生破坏性行为变化时，先更新能力线和迁移说明，再修改模板或脚本。

## 4. 检查命令

```bash
node scripts/release-status.mjs
node scripts/release-status.mjs --json
```

该检查只验证 Skill 发布元数据之间是否一致，不验证 GitHub 标签是否已经存在，也不替代项目内的 `check-docs` 或 `docs-gate`。
