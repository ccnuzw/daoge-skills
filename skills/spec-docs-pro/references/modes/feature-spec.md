# 模式：写或评审功能规格

适用：新增功能规格；评审一份已有规格；为已实现但没有规格的功能补规格（见末尾“补齐已实现功能”）。

## 步骤

1. **定位。** 找到 `docs/`。读 `00-V{n}需求编号.md` 确定下一个可用编号（不复用废弃编号），读同领域已有的 1～2 份功能主文档对齐写法，读冻结决策中与本功能相关的条目。
2. **设计评审。** 按 [design-review.md](../design-review.md) 一轮集中提问，识别高风险信号，确定风险等级。发现需要裁决的冲突时，先走[冻结决策模式](decision.md)。
3. **写功能主文档。** 复制 `assets/templates/feature-main.md` 到 `03-功能规格/V{n}/{NN-领域}/{NN}-{功能名}.md`，逐节填写：
   - frontmatter 写 `feature_id`、`domain`、`spec_status`、`risk`，可选 `track`（主责能力主线，与功能演进矩阵中的标题一致）。不写 `status`。
   - 每条 AC 用 `#### ACNN 标题` + Given / When / Then。覆盖正常路径、每个错误码、每个高风险信号（回滚、并发、幂等、越权）。
   - “AC 逐项测试设计”表每个 AC 一行，目标命令要能直接执行；还没有测试时证据状态写“未创建”。
   - 不适用的章节保留标题，写“不适用：{理由}”。
4. **高风险功能写技术设计。** 复制 `assets/templates/technical-design.md` 到同目录 `{NN}-{功能名}-技术设计.md`。伪代码每个关键分支标 `// B{NN}-{序号}`（功能号两位），“分支到测试追踪”表覆盖全部分支 ID 并指向 AC。
5. **同步登记。** 在需求编号文档登记功能；在实现状态表新增一行（状态“规划中”）；需求追踪矩阵补一行；新增的冻结决策在功能文档“来源与追踪”中引用。
6. **校验并交付。** 运行 `check-docs.mjs`，修复本功能相关的错误和警告。交付时说明：生成了哪些文件、评审中发现的风险及处理方式、仍待用户确认的问题。

## 评审已有规格

按 design-review.md 的高风险信号逐项检查，再运行 `check-docs.mjs --docs docs` 看格式问题。输出“问题 → 位置 → 建议”的列表，按影响排序；先给结论，修改要用户确认后再动手。

## 补齐已实现功能

1. 先读代码、测试、旧文档，不臆测。分析结果写成三栏：已实现的行为、已有测试、缺失的测试。
2. 基于证据提问：“代码中对 email 有唯一约束，但没有并发注册测试，两个请求同时注册同一邮箱时期望返回什么？”
3. 代码里没有、用户确认“明确不做”的能力写进“不包含”；“以后再做”的写去向版本。
4. AC 覆盖现有行为和补充的边界。已有测试对应的 AC，证据状态按真实运行结果写；没运行过就写“已创建”，不写“本地通过”。
5. 发现代码与 PRD 或旧文档不一致时，不要自行选择，记为冻结决策草案请用户裁决。
6. 实现状态按证据回写到实现状态表（见[状态回写模式](status-update.md)）。
