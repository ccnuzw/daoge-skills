# Spec-Docs-Pro P1 升级计划：迭代式文档与多版本支持

## 📋 发现的新需求

通过用户反馈和深度分析样例，发现当前 Skill 在以下方面存在不足：

### 1. 缺少迭代式更新支持

**用户需求**：
- 边对话边完善文档
- 增量更新而非全量重写
- 对话历史驱动文档演进

**当前问题**：
- ❌ Skill 只支持"一次性生成完整文档"
- ❌ 没有"局部更新"模式
- ❌ 没有"基于对话逐步完善"的工作流

**样例证据**：
- `V1-文档变更记录.md` 显示了每次变更的详细记录
- `V1-实现状态.md` 按时间倒序记录进展
- 每次更新都有明确的日期、背景、变更内容

### 2. 缺少多版本规划支持

**用户需求**：
- 先规划 V1-V8 的整体蓝图
- 逐步细化当前版本，其他版本保持概要
- 版本间的演进关系和依赖追踪

**当前问题**：
- ❌ Skill 只支持单一版本（V1）
- ❌ 没有"版本路线图"、"功能演进矩阵"模板
- ❌ 没有"后续版本"规划机制

**样例证据**：
- `02-产品与版本/后续版本/` 包含 V2-V8 的规划文档
- `功能演进矩阵.md` 展示跨版本的能力演进
- `具体功能演进索引.md` 追踪单个功能的完整时间线

### 3. 缺少文档变更追踪

**用户需求**：
- 记录每次文档变更
- 追踪决策的演进过程
- 保持变更历史的完整性

**当前问题**：
- ❌ 没有"文档变更记录"模板
- ❌ 没有"变更历史"追踪机制
- ❌ 更新文档时没有记录变更理由

**样例证据**：
- `V1-文档变更记录.md` 详细记录每次变更
- 格式：日期 + 标题 + 背景 + 变更内容 + 影响范围 + 验证证据

### 4. 缺少实现状态追踪

**用户需求**：
- 按时间顺序记录开发进展
- 区分"规划"、"开发中"、"已验证"
- 每次更新包含验证证据

**当前问题**：
- ❌ 没有"实现状态"模板
- ❌ 功能主文档的"状态"字段缺少详细说明
- ❌ 没有"时间倒序"的进展追踪机制

**样例证据**：
- `V1-实现状态.md` 按时间倒序记录每个功能的进展
- 每条记录包含：日期、功能、当前状态、验证证据、剩余工作

## 🎯 P1 升级目标

### 目标 1：支持迭代式文档更新

**新增模式 7：增量更新文档**

```
基于对话更新功能 05 的验收标准：
- 添加 AC07：管理员批量导入
- 更新 AC03 的验证记录：已通过 8/8 测试
- 记录此次变更到文档变更记录
```

**关键能力**：
- 读取现有文档
- 识别需要更新的章节
- 只更新指定部分，保留其他内容
- 自动记录变更历史

### 目标 2：支持多版本规划

**新增模式 8：创建版本路线图**

```
创建 V1-V8 版本路线图：
- V1：最小商业闭环（当前开发）
- V2：稳定网关
- V3-V8：概要规划
```

**新增模式 9：规划后续版本**

```
规划 V2-稳定网关：
- 主要目标：网关稳定性和可靠性
- 核心功能：失败重试、熔断降级、限流增强
- 依赖：V1 基础功能完成
- 不包含：新协议支持
```

**关键能力**：
- 创建版本路线图
- 创建功能演进矩阵
- 创建后续版本规划文档
- 追踪跨版本依赖

### 目标 3：支持文档变更追踪

**新增模板**：`version-change-log.md`

**自动记录变更**：
- 每次更新文档时，自动添加变更记录
- 格式：日期 + 标题 + 背景 + 变更内容 + 影响 + 验证

### 目标 4：支持实现状态追踪

**新增模板**：`version-implementation-status.md`

**时间倒序记录**：
- 最新进展在最上方
- 每条记录包含：日期、功能、状态、证据、剩余工作

## 📊 样例文档分析

### 文档变更记录的模式

```markdown
## 2026-09-20 标准视频协议与任务型 Driver 设计

- 按用户要求先补设计：新增 V1-FR-040、独立技术设计、公共协议设计。
- 明确 model 必填、同模型 Binding 别名、完整能力组合。
- 同步新视频 OpenAPI、错误码、目标数据、功能追踪与测试计划。
- 文档生成脚本从固定 39 功能改为按实际登记发现。
```

**关键要素**：
- 日期（明确的时间点）
- 简洁的标题（What）
- 背景说明（Why）
- 变更内容（What changed）
- 影响范围（Which docs updated）
- 验证证据（Proof）

### 实现状态的模式

```markdown
## 2026-09-20 — 标准视频协议设计（V1-FR-040）

状态：整体规划中，S0a 纯契约本地已验证。

已将调用方必传模型、同模型跨渠道映射、统一视频契约、task-v1 Driver、
持久任务恢复、素材和媒体计量纳入设计文档。

当前尚未实现视频入口、task-v1 执行器、模型映射、持久任务、对象存储、
账务分支和管理交互。

S0a 验证：视频 26 项单元/契约测试通过...
```

**关键要素**：
- 日期 + 功能编号
- 当前状态（清晰定义）
- 已完成内容
- 剩余工作
- 验证证据（详细）

### 多版本规划的模式

**版本路线图**：
- V1: 最小商业闭环
- V2: 稳定网关
- V3: (历史，已迁移)
- V4-V8: 规划阶段

**功能演进矩阵**：
- 按"能力主线"组织
- 每个能力展示跨版本演进
- 明确依赖关系
- 清晰的状态标识

## 🔧 具体升级内容

### 1. 新增模板

#### `templates/version-change-log.md`
```markdown
# V{版本} 文档变更记录

## {YYYY-MM-DD} {变更标题}

- {变更原因/背景}
- {具体变更内容}
- {影响范围：功能、接口、数据}
- {验证证据}
- {相关决策：D{编号}}
```

#### `templates/version-implementation-status.md`
```markdown
# V{版本} 功能实现状态

更新时间：{日期}。状态依据当前仓库代码、页面和已记录验证。

## {YYYY-MM-DD} — {功能名称}（V{版本}-FR-{编号}）

状态：{规划中/开发中/本地验证/生产验证/已完成}

{当前进展描述}

验证：{验证证据}

剩余工作：{待完成任务}
```

#### `templates/version-roadmap.md`
```markdown
# 版本路线图

## 版本概览

| 版本 | 主题 | 核心目标 | 状态 | 预计时间 |
| --- | --- | --- | --- | --- |
| V1 | 最小商业闭环 | 完整的用户注册到付费调用 | 开发中 | 2026 Q4 |
| V2 | 稳定网关 | 高可用、容错、限流 | 规划中 | 2027 Q1 |
```

#### `templates/feature-evolution-matrix.md`
```markdown
# 功能演进矩阵

## 能力主线跨版本演进

| 能力主线 | V1 | V2 | V3 | V4 | V5 |
| --- | --- | --- | --- | --- | --- |
| 身份与权限 | 个人账户、API Key | Key级限流 | - | 项目、预算 | - |
```

### 2. 更新 instructions.md

**新增模式 7：增量更新文档**

当用户说"更新功能 X"或"添加 AC"时：

1. 读取现有文档
2. 识别需要更新的章节
3. 生成更新内容
4. 保留其他章节
5. 自动添加变更记录

**新增模式 8：创建版本路线图**

当用户说"规划版本路线"时：

1. 询问版本数量和主题
2. 生成版本路线图文档
3. 生成功能演进矩阵
4. 为每个后续版本创建概要规划文档

**新增模式 9：规划后续版本**

当用户说"规划 V2"时：

1. 创建后续版本目录
2. 生成版本概要文档（不细化到功能规格）
3. 说明与 V1 的关系和依赖
4. 标记为"规划"状态

**新增模式 10：记录开发进展**

当用户说"功能 X 已完成测试"时：

1. 更新功能主文档的状态和验证记录
2. 添加到实现状态文档（时间倒序）
3. 添加到文档变更记录

### 3. 增强对话式工作流

**支持的对话模式**：

```
用户：功能 01 用户注册已经完成后端测试
AI：
- 读取功能 01 文档
- 更新验证记录章节
- 更新状态为"本地验证"
- 添加到实现状态文档
- 添加到变更记录
- 询问：需要更新哪些验证证据？

用户：6/6 通过，覆盖正常注册、重复邮箱、弱密码
AI：
- 补充详细的验证记录
- 完成更新
```

### 4. 支持版本演进追踪

**跨版本功能追踪**：

```
功能：用户 API Key 管理

V1：基础 CRUD、生命周期
V2：Key 级限流、缓存
V4：项目标签、预算控制
V8：组织 Key、成员权限
```

**自动维护**：
- 具体功能演进索引
- 功能演进矩阵
- 版本间依赖关系

## 💡 Skill 自身的完善

### 发现样例的不足

通过分析，样例文档也有以下可改进之处：

1. **文档变更记录缺少结构化**
   - 建议：添加"影响范围"固定字段
   - 建议：添加"破坏性变更"标记

2. **实现状态缺少可视化**
   - 建议：生成进度图表
   - 建议：添加完成度百分比

3. **多版本规划缺少依赖图**
   - 建议：生成 Mermaid 依赖图
   - 建议：明确阻塞关系

### Skill 的自我完善机制

**元能力**：Skill 能够识别自身不足并提出改进

```
模式 11：分析文档质量

当用户说"分析文档质量"时：
- 检查缺失的关键元素
- 对比样例文档
- 提出改进建议
- 询问是否应用改进
```
