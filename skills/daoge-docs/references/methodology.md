# 文档驱动开发方法论

## 目标属性

| 属性 | 必须表现出的行为 |
| --- | --- |
| 确定性 | 相同输入、状态和规则版本产生相同结果；受控随机行为保留种子或选择证据 |
| 指向性 | 每项变更都指向版本、稳定需求、AC 和可衡量结果 |
| 稳定性 | 重复、并发、依赖失败、迁移、降级和回滚不破坏业务不变量 |
| 可解释性 | 重要结果能追溯规则、分支、输入事实、状态转换、副作用和证据 |

## 权威模型

不同事实不能使用一张笼统的优先级表。按事实类型指定权威：

| 事实 | 权威来源 |
| --- | --- |
| 长期产品方向 | 产品蓝图和跨版本约束 |
| 当前版本范围 | 当前版本总览和 PRD |
| 功能行为与验收 | 功能主文档 |
| 长期选择和理由 | ADR 或冻结决策 |
| HTTP 字段 | OpenAPI；Markdown 只描述公共语义 |
| 物理数据库结构 | 可执行迁移 |
| 数据含义和生命周期 | 数据模型与功能规格 |
| 当前实现 | 代码、可执行测试和带日期证据 |
| 发布资格 | 发布门禁和已批准机器证据 |

权威来源冲突时停止受影响工作。记录冲突证据，定位或形成决策，同步全部受影响权威，再继续实现。不得选择“更方便”的文件作为事实。

`项目输入与约束注册表.json` 的 `authority_scopes[]` 用于把这条原则落实为机器可查的边界：同一 `scope + fact_type` 只能有一条 `active` 记录，来源必须是项目内可复核的原始文件，不能登记派生索引、浏览器数据或证据摘要。替代时保留旧 `AUTH-*` 为 `deprecated`，新记录以 `supersedes` 指向它；禁止删除旧记录或并列两个 active 来源。

## 输入到规格的覆盖链

输入事实不是需求，确认也不是开发授权。`confirmed` 输入和 `confirmed hard_requirement` 必须各自拥有至少一条 `COVERAGE-*`：

| 处理结论 | 必需目标 | 不得做的事 |
| --- | --- | --- |
| `current_scope` | 当前版本的稳定需求；可补充功能与 E2E | 指向非活动版本、未知 ID 或没有需求的空映射 |
| `future_candidate` | 一份唯一、正式的后续版本规划入口 | 预先创建 FR、功能或 E2E 并把候选当成已冻结范围 |
| `rejected` / `superseded` / `not_applicable` | 确认人和处理依据 | 没有理由地丢弃已确认事实；将 hard requirement 标为 rejected/not_applicable |

覆盖链是“来源到规格”的治理证据，不能替代功能 AC、测试或机器证据。覆盖变化应先更新权威规格或规划，再重新生成索引并复查相关门禁。

### 输入、约束与证据的分层

跨会话事实使用 `项目输入与约束注册表.json` 统一登记，生成的总账只用于阅读。输入和约束不能混成一个状态：

| 对象 | 允许的含义 | 进入规格的条件 |
| --- | --- | --- |
| 项目输入 | 利益相关方陈述、仓库事实、外部资料或实验结果 | 保留来源；`confirmed` 才能作为冻结候选 |
| `hard_requirement` | 必须满足且应可验收的约束 | 必须 `confirmed`；若引用输入，该输入也必须 `confirmed` |
| `soft_goal` | 优化方向或偏好 | 不能单独阻塞功能验收，除非另行确认成硬要求 |
| `reference_observation` | 对参考对象或环境的观察 | 不能自动成为需求、AC 或发布条件 |
| 证据资产 | 可复核的图片、文档、录音、二进制等材料 | 归档时记录来源、脱敏声明和摘要；不可得时写明原因 |

新会话应先阅读机器注册表和派生总账，再从已确认输入与硬性约束恢复上下文。摘要、截图或外部网页本身不是需求权威；它们只能作为有来源的输入，直到责任人确认并写入规格。

确认、否决、替代和补齐材料必须原地更新相应 `INPUT-*`、`CONSTRAINT-*` 或 `ASSET-*`。不得为同一原始事实重复创建一条“已确认”记录，也不得用新资产替代旧的缺失资产而断开证据链。

## 生命周期

### 发现

从业务问题、用户、现状证据、结果指标、范围和未知项开始。产物是事实清单，不是解决方案承诺。

### 版本冻结

确定版本目标、FR/NFR/RG、非目标、退出条件、依赖和跨功能决策。只有通过 Version Ready 门禁的版本才允许批量进入实现。

跨版本管理分三层：能力与旅程基线定义长期、稳定的用户价值和不变量；版本路线图定义版本顺序、前置和退出条件；功能演进矩阵定义具体能力在各版本中的引入、兼容、迁移、废弃或替代。后续版本规划只存放候选，必须有唯一正式入口；未登记路线图且未建立稳定需求时，不能成为当前 Goal 的范围。

版本文档完成不等于开发授权。strict Profile 必须在 `Version Ready` 前由开发者提出并决定 `version_scope` 开发确认；确认记录绑定当前版本权威摘要，权威范围变化后自动失效。确认记录只证明“可以进入受控开发准备”，不替代需求、设计、实现、测试或发布批准。未来版本的规划可以继续编辑，但不能继承当前版本确认。

### 功能设计

功能主文档冻结业务语义、接口、数据、AC 和实现落点。风险决定设计深度，不决定是否需要设计。高风险独立设计必须覆盖事务、并发、幂等、补偿和外部副作用。

### 规格草案确认

编程智能体可以起草规格，但候选内容不是事实。新建或替换规格时，先把候选 Markdown 存在 `docs` 之外，再用 `new-spec-draft` 将内容复制到 `.daoge-docs/spec-drafts/SPEC-DRAFT-*` 的隔离空间，同时冻结候选内容摘要和目标文档基线。开发者审阅后使用 `decide-spec-draft` 记录批准或拒绝；批准只代表候选可物化，仍不修改权威 Markdown。

只有 `materialize-spec-draft` 能将内容和目标基线均未变化的已批准草案写入 `docs`。此时才发生权威事实变化，现有确认、ChangeSet、Goal 与证据按各自的摘要绑定规则重新评估。`proposed`、`approved`、`rejected`、`superseded` 草案和工作台投影均不进入 Goal；草案内容被改动、目标基线变化或审批失效时必须重新提出。物化记录保留当时的内容摘要用于审计，后续正常规格修订不反向篡改这条历史记录。

### 开发授权

开发任务书包含准确目标、范围内外、已冻结决策、影响代码、验收、验证命令和回滚。发现新业务语义或范围扩大时，任务授权立即失效，返回规格与决策阶段。开发确认不是永久授权；其绑定摘要失效时必须停止 Goal、更新权威来源并重新确认。

需要编程智能体执行大型任务时，从已通过门禁的单一版本切片生成 Goal 清单，并绑定 `source_commit`、`authority_digest`、允许路径、任务依赖、停止条件和检查点。MVP、V1、V2、V3 分别形成闭环，不把后续版本规划提前纳入当前实现。准备、恢复和完成规则见 `agent-goal-execution-contract.md`。

并行开发不是共享工作区内的自由并发。每个并行 lane 必须绑定独立 Git branch/worktree、无重叠工程路径、无共享迁移/API/数据状态和独立验证命令；共享契约或集成任务保持串行。默认仍为单 Goal 串行闭环。

### 实现

除非仓库有更强顺序，按以下次序：迁移与约束、纯领域规则、应用事务、接口契约、前端交互、可观测性、测试、证据、实现状态。越靠前的规则越接近不变量，先稳定它们能减少后续返工。

### 验证与发布

AC 从单元、集成、契约、E2E、性能和安全层获得与风险相称的证据。发布只接受当前提交、当前构建、允许环境和有效审批绑定的证据。

## 可解释程序设计

### 纯规则和显式输入

价格、权限、配额、路由和状态转换应尽量使用无隐藏依赖的函数。时间、随机、配置、功能开关和外部状态作为显式输入，并记录采用的规则版本。

### 稳定分支

关键业务分支使用稳定 ID。日志、指标、测试和证据引用同一分支 ID，使读者可以从结果回到设计和 AC。重构可以移动代码，不能随意改变分支语义或复用 ID。

### 状态与副作用

状态机必须列出合法转换、守卫条件、事务边界、幂等规则和失败结果。数据库写入、通知、支付和外部调用必须说明发生顺序、重复语义、超时、重试、未知结果和补偿。

### 观测不是事后补丁

重要操作输出 request ID、主体、规则版本、分支、状态前后值、结果和脱敏错误类别。日志不记录秘密，也不能成为业务正确性的唯一来源。

## 变更同步

| 变更 | 必须同步 |
| --- | --- |
| 版本范围 | 路线图、版本总览、PRD、需求注册表、冻结决策 |
| 功能语义 | 功能主文档、AC、追踪矩阵、E2E |
| API | 接口语义、OpenAPI、错误码、契约测试 |
| 数据 | 数据模型、迁移、回滚、功能设计、恢复说明 |
| 长期选择 | ADR、冻结决策、受影响功能和架构 |
| 规格草案 | 隔离草案、开发者决定和物化审计；未物化前不改变权威范围 |
| 规格修订 | 原权威文档、ChangeSet、开发确认、受影响 Goal 和证据 |
| 开发级完成 | 目标规格、Goal completion、开发者交付确认和证据 |
| 实现 | 测试、证据、实现状态，不反向篡改需求 |
| 发布条件 | 测试策略、性能、安全、部署、回滚、恢复和证据清单 |

派生索引由工具生成。发现手工索引与权威源不一致时修改权威源并重新运行 `index`，不得直接修表格。

## 受控写入与并发

`init`、规格/注册表/审批/ChangeSet/交付回写、`index`、Goal 状态推进和证据写入等变更命令必须取得项目级写锁。锁只保护写入，不把锁文件置入项目工作树；读取 `handoff`、`check`、`gate`、`goal-plan` 和默认只读的 `goal-status` 可以并行。第二个写命令在锁释放前等待，超时后以错误退出且不修改项目。工具以同目录临时文件、`fsync` 和原子替换保存 Markdown、JSON、Goal 与草案内容，防止进程中断留下可见的半文件；这不替代 Git 提交、人工批准或跨设备协作的合并策略。

开发中的同步按事实类型处理：实现进度和测试结果只进入代码、测试、实现状态和机器证据；需求、AC、稳定分支、接口、数据或工程边界变化必须先更新权威规格/ADR，再创建 ChangeSet 记录影响范围并由开发者确认，随后使受影响 Goal 进入 `stale` 并重新准备。ChangeSet 只保存变更元数据，不复制需求正文；未受影响的后续版本规划可以继续编辑，但不能被当前实现 Goal 自动采纳。

## ChangeSet 生命周期

ChangeSet 是规格修订的治理记录，不是第二份 PRD。固定流程为：

1. 修改原权威文档，保留稳定 ID，并运行 `index` 取得新的版本范围摘要。
2. 用 `new-change-set` 登记变更类型（`add`、`change`、`deprecate`、`split` 或 `defer`）、影响 ID、权威来源、提出人、动机和非目标。
3. 由开发者用 `decide-change-set` 记录 `approved`、`rejected` 或 `cancelled`；批准必须绑定当前摘要。
4. 将文档与 ChangeSet 决定提交后，使用 `prepare-goal --change-set` 生成新的 AI 任务清单。
5. Goal 的 `ready`、执行和完成从 Goal 清单、检查点与机器证据派生；工作台分别显示 ChangeSet 确认状态和交付状态。

合法记录状态为 `proposed -> approved|rejected|cancelled`，替代关系使用新 ChangeSet 的 `supersedes`；权威摘要变化时 `proposed/approved` 派生为 `expired`，不得原地批准或刷新。

## 开发完成回写

功能、模块和版本共享一套交付状态模型。功能目标是稳定 `FR` ID；模块使用显式登记的 `MODULE-*` 且只组合既有功能；版本目标是 `Vn` 的已登记功能全集。交付登记不是规格正文，也不保存需求、AC 或设计副本。

1. `goal-complete` 先产生防篡改的 `completion.json`，其中包含最终提交、权威摘要、检查点链和最终命令证据。
2. 开发者复核后执行 `close-delivery --decision accepted`，它只能绑定当前可复验、并覆盖目标全部功能的已完成 Goal，保存 Goal 完成摘要而不是相信智能体声明。
3. 工具派生 `designing`、`ready_for_development`、`in_development`、`awaiting_delivery_confirmation`、`development_complete`、`needs_reverification` 和 `exception`。工作台只读投影这些状态。
4. 规格范围、关联目标、最终提交或完成证据变化时，旧完成记录保留审计价值，但状态转为 `needs_reverification`；重新完成后使用新的 `DELIVERY-*` 替代旧记录。

`exception` 只记录开发者明确接受的未完成或不可验证边界，不能被任何 Gate、Goal 或工作台解释为开发完成或发布许可。
