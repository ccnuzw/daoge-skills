# DAOGE Pic vNext 真实创作验证与改进台账

## 1. 目的与边界

本台账用于在真实创作会话中持续记录 `daoge-pic` 的可复现行为、功能缺失、体验问题、改进决策与回归证据。它不替代 Studio 的业务事实或运行记录：项目、任务、轮次、资产、选片和交付仍以 Studio 为唯一事实源。

记录原则：

- 先在未修改实现的基线版本中实际使用，再记录观察结果。
- 将“已复现问题”与“待验证假设”明确分开；未复现的推断不得直接进入修复范围。
- 每项改进必须包含问题、影响、修复范围、回归测试和结论。
- 不记录 API Key、完整 Provider URL、个人绝对路径、真实用户素材或未脱敏请求载荷。

## 2. 当前基线

- Skill：`daoge-pic@5.4.0`（vNext Studio）。
- 验证入口：智能体会话负责计划与确认；Studio Workbench 负责运行、资产、评审和交付管理。
- 当前测试主题：原创赛博国风武侠人物，覆盖方形头像、社媒横幅和竖版海报。
- 当前状态：4 个轮次已完成确认、预检与入队；本次会话控制的 8 个运行项均成功完成并形成受管理资产。

## 4. 已观察条目

### PIC-OBS-001：多画幅交付需要拆分为多个创作轮次

- 类型：能力边界，非缺陷。
- 观察：当前一个创作计划只表达一份提示词和一组输出规格；同一批次不能同时可靠表达 `1:1`、`16:9` 与 `4:5`。
- 当前处理：将头像正脸、45 度头像、社媒横幅和竖版海报拆为 4 个独立轮次，每个轮次 2 张。
- 证据：当前 Studio Session 的同一任务下查询到 4 个 `awaiting_confirmation` 轮次，计划版本和输出规格分别为 2 张 `1:1`、2 张 `1:1`、2 张 `16:9`、2 张 `4:5`；尚无运行记录或 Provider 调用。
- 影响：流程正确、可审计，但用户需要确认多个轮次，批量体验存在优化空间。
- 补充证据：当前主轮次的创作记录可重新读取提示词、`1:1` 输出规格、2 个计划项和计划版本；运行数为 0，确认门槛未被绕过。
- 后续验证：确认 Workbench 是否能清晰呈现同一任务下的多画幅计划、确认和结果聚合。
- 状态：观察成立，保留为候选 P2 改进项。

### PIC-OBS-002：并发上限固定为 2，无法按任务配置为 4

- 类型：功能缺失。
- 观察：当前 daemon 以固定批次预算领取运行项，用户侧没有 Workbench、CLI 或 `provider.env` 的并发配置入口；现有上限为 2。
- 用户需求：在确认后的 8 项测试中以 4 并发执行。
- 影响：不阻断生成，但无法兑现明确的吞吐量控制需求，也不利于在 Provider 限流范围内做受控性能测试。
- 证据：本次本地运行时检查确认 Studio 健康，Provider 配置完整，且声明文生图、编辑、参考图与遮罩能力；未触发 Provider 调用。
- 局限：配置状态由本地服务读取，尚不能证明现有 worker 已经重载修改后的配置；该结论保留给 PIC-HYP-001 的重启验证。
- 建议改进：增加有边界校验的工作区级并发配置；在状态和预检中展示生效值，纳入运行快照，并补充限流、暂停、重启和 1/2/4 并发回归测试。
- 状态：已确认，候选 P2 改进项。未修复前，真实运行按现有 2 并发执行。

### PIC-OBS-003：首次入队将刚完成的干跑证据判定为过期

- 类型：功能缺陷。
- 复现路径：重启 daemon 以加载当前 Provider 配置后，确认 4 个轮次并依次预检；随后立即用对应 dry-run ID 入队，第一个入队请求被拒绝为“干跑证据已过期”。
- 诊断：被拒绝轮次的计划版本、计划快照，以及可见的 Provider 身份、模型、端点和能力摘要均与当前状态一致；差异根因尚未定位。
- 恢复动作：对保持不变的计划重新预检后立即入队，4 个运行会话均成功创建。原始和刷新后的干跑证据均被保留。
- 影响：用户已确认且预检成功的首个入队请求仍被阻断，要求重复预检，属于主生成链路 P1 候选。
- 后续：在修订阶段为预检快照比较增加可解释差异、稳定序列化测试和“首次预检后立即入队”回归测试。
- 后续结果：刷新预检后创建的 4 个运行会话共 8 项全部成功完成；该恢复动作可用，但不能替代首次证据校验失败的根因修复。
- 状态：已复现，P1 候选，待在修订阶段定位快照比较差异。

### PIC-OBS-005：画幅约束未映射为 Provider 的尺寸参数

- 类型：功能缺陷。
- 复现路径：计划分别声明 `16:9` 社媒横幅和 `4:5` 竖版海报；预检通过，运行项均成功完成。
- 证据：两类抽检成品均为 `1254×1254` 方图。横幅样张仍遵循了人物位于右侧、左侧留白的构图意图，海报样张也保留了人物主视觉，但交付画幅错误。
- 根因：当前计划和预检保留 `output.aspectRatio`，HTTP Provider 适配层只读取 `output.size` 或 `output.dimensions`，缺省回落为方形尺寸；该不兼容未在预检中暴露。
- 影响：横幅和海报不能按约定用途直接交付，属于 P1 主产物正确性缺陷。
- 建议改进：定义统一且经 Provider 能力校验的输出规格；将画幅映射为各 Provider 支持的尺寸，无法映射时预检失败并给出可选规格；归档实际宽高以便验证。
- 状态：已复现，P1，待修复与回归。

### PIC-OBS-006：无参考锚点时角色脸部一致性不足

- 类型：质量与流程边界。
- 证据：4 个方向的视觉抽检均保留雨夜、红青光线、深色赛博国风服装和电影质感，但人物五官、发型和服装细节存在明显漂移。
- 影响：作为单张概念图可用；作为同一角色跨头像、横幅和海报的系列主视觉，身份一致性不足。
- 当前判断：本次没有提供角色参考图，且各轮次为独立文生图，故不能归因为 Provider/资产持久化缺陷。
- 已准备验证：已将一张正脸结果标记为仅用于测试的 `derive`，并创建以该受管理资产为引用、继承原正脸轮次的 2 张 `edit` 子轮次；计划尚未确认或调用 Provider。
- 关系校验：资产 provenance 可重新读取 `derive` 决策，且其任务 ID、父轮次 ID 与验证反馈均与写入值一致。
- 建议改进：Task Type 对角色系列任务提示先选定锚点图，再使用参考图编辑或衍生轮次；当 Provider 支持参考图时，计划应明确呈现该策略。
- 状态：已观察，候选 P2 流程改进项；参考图执行验证待用户确认。

### PIC-OBS-004：Provider 配置变更没有受控重启命令

- 类型：功能缺失。
- 观察：当前 CLI 暴露启动和状态查询，但没有重启命令；Provider 配置在 daemon 生命周期内固定。
- 测试绕行：在没有活跃运行的条件下，向旧 daemon 发送平滑 `SIGHUP`，再使用官方 `studio` 命令启动新实例；新 PID 和启动时间均已确认。
- 影响：用户无法仅用公开 Studio 操作安全地让新配置生效；配置后首次生成容易遇到“状态显示完整但 worker 仍使用旧内存配置”的困惑。
- 建议改进：提供受控 restart 命令/API，拒绝或明确处理活跃运行，展示配置指纹与重启后生效状态，并覆盖无运行、排队、运行中三种场景。
- 状态：已复现，候选 P1 改进项。

### PIC-HYP-001：Provider 配置改动后的可操作重启入口

- 类型：已完成验证。
- 结论：配置重载本身可通过平滑停止旧 daemon 后重新启动完成，但公开 CLI/Workbench 尚无受控入口；详见 PIC-OBS-004。
- 状态：已由 PIC-OBS-004 替代，不再单独作为待验证假设。

## 9. 用户确认的 Workbench 改进需求

### PIC-REQ-001：可理解、可回指的选片与衍生入口

- 来源：真实创作测试中的用户反馈。
- 基线证据：当前资产卡提供预览、选择、保留、待复核、批注、衍生和不采用等带 tooltip 的图标操作，以及评审状态；但卡片没有可读的轮次、序号或用途名称，用户仍需依赖缩略图或截断内部 ID 指认。
- 修订：用户明确拒绝将“画面描述 + 用途”作为选片方式。图片身份只能在 Studio 通过缩略图、稳定上下文标签、筛选和明确选中状态确定；语言只能说明已选集合的后续用途，不能用于猜测或解析要选的图片。
- 需求：资产卡必须显示可读的轮次、序号、用途和评审状态，并提供可见的直接选中控件；项目选片集合必须持久化，不能随刷新、范围切换或交付草稿创建而丢失。

### PIC-OBS-007：Workbench 导航与提示词证据的可发现性不足

- 类型：体验缺陷。
- 证据：当前 Workbench 用同一 `view-switcher` 将资产、生成、总览、资料库、交付和回收站并列；总览依赖任务上下文，资料库属于 Studio 全局，交付属于项目，这些范围在导航中没有分层。
- 证据：计划版本和干跑记录只在运行页“高级详情”中以原始 JSON `pre` 呈现；版本数据虽然完整，但普通创作流程无法直接阅读或对比。
- 证据：源码没有学习中心、使用指南或首次启动引导入口。
- 影响：首次使用者无法建立“我在哪个层级、下一步做什么、如何选择并复用结果”的心理模型。
- 状态：已复现，PIC-REQ-001 至 PIC-REQ-004 的实现依据。

### PIC-REQ-001：可理解、可回指的选片与衍生入口
- 操作：每张图必须提供明确命名的“预览、保留、待复核、不采用、作为衍生参考、批注”动作，并在选中后展示持久状态和影响范围。
- 会话协同：会话不得将画面描述、自然语言或资产 ID 作为选片输入；它只可在 Studio 当前选片集合已确定后，接收用途、评审或衍生意图。
- 验收：新用户只通过 Studio 的图片卡片、标签、筛选和项目选片条完成一次持久选片、批注和衍生计划；刷新、切换范围和创建交付草稿后选择仍可恢复。
- 优先级：P1。

### PIC-REQ-002：一等公民的提示词与计划工作台

- 来源：真实创作测试中的用户反馈。
- 当前观察：已确认计划、提示词和实际请求摘要可在运行高级详情中查看，但它们不是独立、可比较的创作界面。
- 需求：在任务/轮次上下文中提供“计划与提示词”工作区，展示目标、约束、参考资产、提示词版本、负向约束、输出规格、预检快照和实际 Provider 修订摘要。
- 交互：用户必须能在确认前查看和修改草稿、比较版本差异、复制或导出脱敏创作记录；确认后只能新建版本，不能篡改已执行证据。
- 边界：不得显示 API Key、完整 Provider URL 或未脱敏请求日志。
- 数据验证：当前 Studio API 已能返回同一轮次的草稿、待确认和已确认计划版本，并保留提示词、数量、输出规格、状态与确认时间；已确认版本可回溯。
- 验收：用户可在不进入技术详情的情况下追溯每张结果对应的已确认提示词与计划版本。
- 优先级：P1。

### PIC-REQ-003：按业务范围分层的 Studio 信息架构

- 来源：真实创作测试中的用户反馈。
- 当前观察：总览、资料库、资产、运行和交付位于同一套视图切换中，混合了 Studio 全局、项目、任务和轮次级信息。
- 目标层级：
  - Studio 全局：入口总览、创作资源库、学习中心、设置。
  - 项目：项目概览、任务列表、交付。
  - 任务/轮次：计划与提示词、生成运行、结果资产、评审与衍生。
- 规则：页面必须始终显示当前 Studio/项目/任务/轮次上下文；跨层跳转必须保留来源并可返回。全局资料库不得与当前轮次资产并列为同一概念。
- 验收：用户在 30 秒内能分辨全局资料、项目交付和当前轮次结果分别在哪里。
- 优先级：P1。

### PIC-REQ-004：Studio 内置首次使用学习中心

- 来源：真实创作测试中的用户反馈。
- 需求：Studio 必须提供可随时打开的中文学习中心，覆盖 Provider 配置路径与安全边界、会话到项目到轮次的流程、计划确认、预检、生成、选片、衍生、复用、交付、暂停/恢复/重试和常见异常。
- 形式：首次启动提供可跳过的引导；常驻入口提供按场景索引的操作手册；当前页面提供与上下文相关的下一步提示。流程使用 Lucide 图标、简洁状态图、示例资产与真实 UI 术语，避免一整页静态说明文字。
- 边界：学习中心不显示密钥、不充当第二个聊天入口、不绕过会话确认，也不把档案目录作为业务状态。
- 验收：首次用户可在 Studio 内理解完整工作流，并在每个关键状态找到下一步和故障处理说明。
- 优先级：P1。

### PIC-IMP-002：输出规格、并发与恢复控制面

- 画幅：新增共享 Provider 输出规格解析器，预检与 HTTP 适配器使用同一份规范化结果。显式比例会被规范化、与尺寸一致性校验并按 Provider 传输协议发送；非法或未支持比例在无外部调用的预检阶段拒绝，绝不回退成 `1024x1024`。
- 实测：当前 Provider/模型对旧 `4:5` 海报和 `16:9` 横幅计划返回明确的 `aspect_ratio_unsupported`，可选比例为 `1:1`；一轮已确认的 `1:1` 计划预检成功，干跑快照保留 `aspectRatio: 1:1`。以上均未调用 Provider。非方图必须在 Provider 明确能力配置后重新预检，不能猜测尺寸或比例。
- 预检证据：干跑的 Provider 与计划快照改为递归稳定 JSON 比较，忽略 JSON 语义中的未定义字段；等价对象键序不会再被判为证据过期，实质计划或安全 Provider 变化仍会拒绝入队。
- 并发：增加受控 `DAOGE_PIC_WORKER_CONCURRENCY`，仅接受精确值 `1`、`2`、`4`，默认保持 `2`；daemon 启动后将实际值写入安全 runtime，并将该值传给 Worker 批量领取。无效配置停止领取和预检，不静默回退。
- 控制命令：新增 `config --worker-concurrency <1|2|4>` 与 `restart`。前者仅以安全原子写入更新期望并发，后者只优雅停止同工作区 daemon、有限等待并复用启动路径，不强杀、不删锁、不绕过 `resume_pending` 的会话确认。
- 回归：全套 `npm test` 为 70/70 通过，包含输出规格、预检、稳定快照、Worker `1/2/4` 的 `N+1` 预算、CLI 命令与配置私密性。
- 实时状态：最终受控重启后 Studio 健康，实际 Worker 并发为 `4`，安全状态为已配置、无缺失字段且不含敏感配置。
