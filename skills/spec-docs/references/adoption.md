# 存量项目接入：从混乱文档到单一权威

适用于已经有代码、也有文档（或文档过期、散落、多处口径）的项目。目标是**不停止开发**地把文档收敛成“可解释、可维护、可交接”的体系。

> 新项目请走 SKILL.md 的模式 A；本文件是它的存量项目版本。

## 1. 三条接入原则

1. **先止损，再整理**：从接入当天起，新改动必须走新体系（登记编号、写功能文档、回写状态）；旧文档冻结为只读。整理可以分批，止血必须立即。
2. **先冻结，后搬家**：口径冲突（字段、枚举、错误码、状态机、资金规则）先写冻结决策，再同步文档与代码；不要一边搬家一边改口径。
3. **归档不删除**：旧文档整体进 `99-历史归档/`，用迁移映射保留“旧路径 → 新路径”；不把旧文档抄进当前目录形成第二套事实。

## 2. 六个阶段

### 阶段 0 摸底（1–2 小时）

输出一份现状清单：

| 项目 | 内容 |
| --- | --- |
| 现有文档 | 目录、格式、大致质量、最近更新时间 |
| 事实来源 | 哪些文档还被当真、哪些已经过期 |
| 口径冲突 | 同一字段/枚举/规则在不同文档的差异 |
| 可复用内容 | 值得搬进新体系的段落（产品范围、接口表、数据约束） |
| 接入范围 | 本次收敛到哪些域（建议一次 1–2 个域） |

### 阶段 1 建骨架（30 分钟）

```sh
node <skill>/scripts/init-docs.mjs --target . --name "项目名" --version V1 --tier m
# docs/ 已有旧文档时：追加 --adopt，只补缺失文件，不覆盖任何同名内容
# 需要新旧目录并行迁移时：使用 --dir docs-next，不移动旧 docs/
```

不删除、不移动任何旧文件；`--adopt` 可在已有 docs/ 中安全补缺，或用 `--dir docs-next` 建并行新目录。已有配置与脚本同样保留；需要更新脚本时再显式运行 `--refresh`。

### 阶段 2 止损规则（当天生效）

- 新功能/新改动：必须登记稳定编号、写功能主文档、回写实现状态。
- 旧文档：标记只读（或移动前先加“已冻结”提示头），不再作为开发输入。
- 团队约定：代码评审时检查是否按新体系回写。

### 阶段 3 归档与映射（0.5–1 天）

1. 先在新目录完成目标域重建；不要把整个 docs/ 根目录移动到归档，因为其中已包含新体系文件。
2. 将确认废弃的旧文件按原相对路径移入 `99-历史归档/<旧目录名>/`。
3. 建/更新 `99-历史归档/文档迁移映射.md`：旧路径 → 新路径（无对应新文件的写“待重建”）。
4. 根文档 README 作为唯一入口；所有指向旧路径的引用改为迁移映射或新文档。

### 阶段 4 权威与编号回填（按域分批）

对仍在使用的功能，逐域回填：

1. 分配 `Vx-FR-NNN` 并登记编号表与功能查找表。
2. 从旧文档摘取真实规则，逐条与代码核对；写七段主文档，并在版本实现状态表记录“基础实现/部分实现”。
3. 高风险功能补技术设计（可以先 Draft，但分支 ID 与事务/幂等必须写）。
4. 更新追踪矩阵与实现状态；**历史“已完成”不继承**，以代码与可复现证据为准。

### 阶段 5 冻结口径（遇到冲突就做）

- 把散落口径写成冻结决策（选择、影响、迁移）。
- 同步公共契约：接口契约 + openapi、数据模型、统一错误码。
- 被取代的旧结论标注取代关系，不删除历史。

### 阶段 6 接入检查与门禁

1. 先跑 `node scripts/check-docs.mjs`，把错误清零、警告记录为待办（此时不要开 `--strict`）。
2. 稳定 1–2 周后打开 `--strict` 并接入 CI（结构检查每次提交）。
3. 有发布流程时再启用 `docs-gate`：先生成配置与证据模板，报告从下一个发布批次开始积累；`--release` 只在候选发布分支运行。

## 3. 状态回填规则

| 情况 | 正确写法 | 禁止写法 |
| --- | --- | --- |
| 有代码、有可复现证据 | 本地验证/门禁通过（附记录） | 已完成（无证据） |
| 有代码、无证据 | 基础实现 | 已完成 |
| 部分接口/部分 UI | 部分实现 | 基础实现（掩盖缺口） |
| 旧文档写“已完成”但无证据 | 按代码重新评估 | 直接继承旧状态 |
| 不确定 | 开发中 + 差距清单 | 留空或“待定” |

## 4. 每阶段验收

| 阶段 | 验收标准 |
| --- | --- |
| 0 摸底 | 现状清单完成，接入范围与负责人明确 |
| 1 建骨架 | `check-docs` 运行成功（允许占位告警） |
| 2 止损 | 新改动有编号与主文档；旧文档已标记冻结 |
| 3 归档 | 旧路径全部有映射；根 README 无死链（`check-docs` 零错误） |
| 4 回填 | 目标域功能有主文档、编号与矩阵；状态与实际一致 |
| 5 冻结 | 已知冲突全部有决策编号；公共契约同步 |
| 6 门禁 | 结构检查进 CI；发布流程接入 `docs-gate` |

## 5. 反模式

- 大规模重写文档导致开发停摆。
- 把旧文档整批复制进新目录，形成两套事实。
- 为历史功能编造验收证据或直接把旧“已完成”抄进实现状态。
- 先追求目录漂亮，编号与追踪最后做——顺序反了，返工成本最高。
- 一边搬家一边改口径，导致迁移映射与决策记录互相矛盾。
- 只归档不建映射，半年后没人知道旧文档去哪了。

## 6. 接入完成判定

1. 新改动全部走新体系，旧文档已冻结归档且有映射。
2. 目标域的每个功能有稳定编号、主文档、验收标准与真实状态。
3. 已知口径冲突都有冻结决策，公共契约只有一套。
4. `check-docs` 零错误并接入 CI；发布流程有 `docs-gate` 证据链。
5. 新人能在 30 分钟内按 `docs/README.md` 找到入口并说出“当前做到哪了”。
