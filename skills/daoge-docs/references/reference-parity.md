# 参考 docs 等价标准

## “完全一样”的可验证定义

DAOGE Docs 的等价目标分为四层：

| 层级 | 等价要求 | 判定方式 |
| --- | --- | --- |
| 目录职责 | 项目、产品版本、功能、架构、测试发布、决策、参考和归档均有唯一空间 | `init --profile strict` 后运行 `check` |
| 文档深度 | 每类文档具备适用的来源、范围、规则、矩阵、失败、验收、证据和变更章节 | `check` 验证 Profile 必备章节和治理元数据 |
| 动态能力 | 能按项目事实创建版本、领域、功能、设计、E2E、架构专项、决策、证据、参考和归档 | 使用对应 `new-*` 命令并运行 `index` |
| 治理语义 | 稳定 ID、单一权威、需求追踪、风险分级、四级门禁、构建绑定、权威摘要和人工批准有效 | `audit`、`authority-digest` 与四级 `gate` |

“完全一样”不表示复制参考项目的产品名、39 个功能、49 项决策、7 个 ADR、未来版本结论、Driver 协议、历史报告或调研结论。这些都是项目事实，只能根据目标仓库和用户确认重新生成。

## 参考目录与 Skill 机制

| 参考能力 | strict 初始文档 | 动态生成或维护机制 |
| --- | --- | --- |
| 项目导航、环境、Git 规范 | `01-项目概览` | 仓库调研后填写，Discovery 门禁校验 |
| 产品蓝图、跨版本能力/旅程基线、路线图、版本约束 | `02-产品与版本` | `new-future-version` 创建唯一正式后续规划入口，`index` 更新演进图 |
| 当前版本总览、产品需求、状态 | `02-产品与版本/当前版本` | `new-version` 创建；实现状态由功能文档派生 |
| FR/NFR/RG、追踪、风险、查找 | `03-功能规格/<版本>` | `new-domain`、`new-feature`、`new-requirement`、`index` |
| 高风险技术设计 | 同名 `-技术设计.md` | `new-feature --risk high` 自动创建 |
| 总体架构、接口、数据、界面 | `04-技术架构` | 固定基线加 `new-architecture-spec` 专项扩展与示例资产 |
| E2E 规范、环境、夹具、用例、证据 | `05-测试与发布/端到端验收` | `new-e2e`、`new-evidence --type e2e` |
| 性能、容量、负载、场景、执行 | `05-测试与发布/性能与容量` | `new-evidence --type performance` |
| 部署、回滚、恢复、发布门禁 | `05-测试与发布/发布` | `new-evidence --type release` 与 Release 门禁 |
| 冻结决策和 ADR | `06-决策记录` | `new-decision`、`new-adr`、派生索引 |
| 调研、外部资料、文档浏览器 | `90-参考资料` | `new-reference`，`index` 生成浏览器和数据 |
| 旧版本与迁移映射 | `99-历史归档` | `archive` 创建历史材料并指向当前权威 |

## strict 初始化后应出现的派生制品

- 三张产品演进 SVG：版本主链路、能力热力图、门禁依赖图。
- 产品文档浏览器 HTML 和独立检索数据 JS。
- 文档驱动开发分析手册 HTML。
- 功能索引、功能查找表、风险分级、技术设计索引。
- FR/NFR/RG 编号视图和需求追踪矩阵。
- 当前版本实现状态、ADR 索引、冻结决策视图和 E2E 用例矩阵。

产品文档浏览器不能降级为文件列表，也不以展示模块数量判断等价。完整等价使用六个主视图：工作台、总览、阅读、图谱、功能演进和时间线。工作台首屏必须给出当前上下文、开发判断、一个下一步、最多三个阻塞和四段进展；总览必须达到样例级项目全貌；图谱必须覆盖产品架构、核心流程、版本路线、数据域、交付追踪和风险热区；功能演进必须按能力主线呈现逐版本变化、依赖和完成判定；时间线必须呈现具体功能的来源、实现差距、门禁和后续里程碑。

总览对标样例时保留其“先看全景、再看业务旅程和版本链”的扫描效率，但不能复制样例中的手绘业务事实或固定功能数量。产品全景使用用户与入口、业务领域、系统与依赖三层语义摘要，机器 ID 默认隐藏；业务旅程、版本步骤和摘要关系都可返回结构化权威来源；交付进度不得用文档行数、章节数或 `draft` 数量冒充代码实现。

离线正文数据、递归目录树、目录 README 优先入口、全文检索、Markdown 阅读器、章节联动、冻结决策入口、内部链接接管、阅读进度、状态恢复和移动端布局仍是必需能力。四级门禁结构信号、测试分层、函数契约、伪代码、稳定分支、AC 追踪和四类证据绑定作为工作台次级验证面板提供，并明确结构就绪不等于机器验证或发布批准。移动端的六个入口必须完整可达，目录与章节抽屉必须具有明确关闭入口；搜索和功能筛选不得因视图重绘而中断连续输入。

独立版本 Diff 页面、未变化对象列表、收藏、最近阅读列表和个人工作面板不属于等价要求。不可变快照仍须支持 authority 变化检测、Goal 恢复和审计；人类界面只在功能演进中按需显示新增、语义变化、废弃和删除摘要。浏览器只能读取派生数据，不得在页面代码中维护第二份业务事实。所有图谱、演进、时间线和进展结论必须来自带稳定 ID 与来源的标准化权威表格；缺失时明确降级，不得猜测。

用于大型任务的等价能力还包括：从已通过门禁的版本和功能生成绑定 `source_commit`、`authority_digest`、允许路径、任务依赖、AC、稳定分支、验证命令、证据要求、停止条件和检查点的 Goal 清单。Goal 清单属于派生执行输入，不替代权威文档；摘要或执行基线失效时必须停止恢复。

专项文档不能退化为通用章节壳。版本门禁必须具备输入、失效、追踪、批准和例外规则；测试体系必须具备分层、风险、失败分类和退出标准；E2E 必须从真实入口核对最终业务副作用；性能必须使用逐请求测量、批准负载、明确比较符、过载/恢复和正确性停止条件；发布必须绑定不可变制品、迁移、冒烟、观察、回滚、RPO/RTO 和一致性证据。所有功能必须具备可执行伪代码和稳定分支追踪，高风险设计还必须覆盖事务、并发、幂等、未知结果与补偿。

## 完整能力审计

完成项目事实填写和动态文档创建后运行：

```sh
python3 .daoge-docs/daoge_docs.py index --root .
python3 .daoge-docs/daoge_docs.py check --root . --json
python3 .daoge-docs/daoge_docs.py audit --root . --json
```

`audit` 通过只表示已经具备参考文档体系的能力深度。是否允许开发或发布仍分别由 `version-ready`、`feature-ready` 和 `release` 门禁决定。

## 不得为了对齐而做的事情

1. 不创建无来源的未来版本、功能、ADR 或已通过证据。
2. 不把参考项目的业务模块当作所有项目的固定模块。
3. 不复制真实密钥、URL、账户、价格、容量或发布记录。
4. 不用文件数量代替内容闭环，也不用模板占位冒充 Ready。
5. 不为了得到“完全一样”的视觉数量而制造无意义文档。
