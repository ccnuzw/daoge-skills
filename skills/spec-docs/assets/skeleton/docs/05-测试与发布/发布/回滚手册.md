# {{活跃版本}} 回滚策略

## 1. 原则

- 应用回滚和数据库回退分开决策。
- migration 必须优先向前兼容，使上一版本应用能在短窗口内继续运行。
- 已产生的业务事实（资金、用量、审计等）不得通过回滚脚本删除。
- 不使用版本回退命令、删除存储卷或手工改数据作为生产回滚。

## 2. 触发条件

- 数据不一致、重复副作用或关键不变量被破坏。
- 大面积登录/鉴权失败且无法快速配置修复。
- 新版本导致持续 5xx、ready 失败或连接耗尽。
- 外部依赖回调无法验证或无法入账。
- 敏感信息进入响应或日志。

## 3. 应用回滚

1. 停止扩流和后台任务新批次。
2. 保存 request_id、指标、日志和受影响对象范围。
3. 将前端静态资源回退到上一 build。
4. 按依赖顺序回退镜像；若问题仅在单应用则最小化回退。
5. 验证上一版本与当前 schema 兼容。
6. 执行只读 smoke，再恢复受控流量。

## 4. 数据库处理

- 加列、加表和可兼容索引通常保留，由后续 migration 清理。
- 破坏性 schema 变更必须拆为 expand/migrate/contract，contract 不与首次代码发布同批执行。
- 数据修复使用新的、可审计且幂等的修复 migration/job。
- 业务数据错误通过业务补偿流水修复，不直接覆盖历史记录。

## 5. 回滚证据

记录触发时间、版本、负责人、影响范围、执行步骤、数据库状态、恢复时间、验证结果和后续行动。失败发布和回滚记录必须保留，不能被下一次成功发布覆盖。
