# Spec-Docs-Pro Skill 深度升级计划

## 发现的关键不足

通过深入分析 `docs-old-all` 样例文档，我发现当前 Skill 在以下方面存在显著不足：

### 1. 验收标准（AC）的精细度不足

**样例中的实践**：
```markdown
#### AC 逐项测试设计

| AC | 验收重点 | 测试层级 | 目标资产 | 目标命令 | 初始资产状态（日期） |
| --- | --- | --- | --- | --- | --- |
| AC01 | 正常注册 | 后端 API/数据库集成 + 前端交互 | `server/crates/identity/tests/user_registration.rs`<br>`frontend/apps/client/src/views/__tests__/user_registration.test.tsx` | `cd server && cargo test -p tuzai-identity --test user_registration ac01`<br>`cd frontend && pnpm --filter @tuzai/client test -- user_registration` | 规划中：目标文件未创建 |
```

**当前 Skill 缺失**：
- 没有"逐项测试设计"表格模板
- 缺少测试命令的具体格式
- 没有"初始资产状态"追踪
- 缺少前后端测试文件的明确映射

### 2. 验证记录的严格性不足

**样例中的实践**：
```markdown
#### 2026-07-12 后端集成测试

`CARGO_HOME=/tmp/tuzai-cargo DATABASE_URL=postgres://tag:tag@127.0.0.1:5432/tag cargo test -p tuzai-identity --test user_registration`：6/6 通过。使用 `sqlx::test` 隔离数据库，覆盖正常注册、重复邮箱、弱密码无写入、余额联动、失败无额外数据和邮箱规范化。前端交互与 E2E01 仍待补。
```

**关键要素**：
- 完整的环境变量
- 精确的命令（包含路径）
- 具体的通过数量（6/6）
- 详细的覆盖内容说明
- 明确的遗留工作

**当前 Skill 缺失**：所有这些细节要求

### 3. 技术设计的深度不足

**样例中的伪代码质量**：
```text
FUNCTION create_hold(user_id, api_key_id, request_id, amount_cny: Decimal) -> Result<BalanceHold>:
  REQUIRE amount_cny >= 0
  BEGIN TRANSACTION
    balance = DB.lock_user_balance(user_id)                       // B19-01
    existing = DB.find_active_hold(api_key_id, request_id)
    IF existing EXISTS: RETURN existing                           // B19-02
    IF balance.balance - balance.frozen_balance < amount_cny:     // B19-03
      ROLLBACK; RETURN Err(4010001, "insufficient_balance")
```

**关键特点**：
- 明确的分支追踪 ID（B19-01, B19-02...）
- 具体的错误码（4010001）
- 清晰的事务边界
- 数据库锁的显式标注
- 条件分支的详细逻辑

**当前 Skill 缺失**：
- 分支 ID 标注机制
- 错误码的精确引用
- 事务边界的严格标注
- 并发控制的显式说明

### 4. 分支到测试追踪的缺失

**样例中的实践**：
```markdown
## 分支到测试追踪

| 分支 | 功能 AC | 跨功能验收 |
```

**当前 Skill 完全缺失这个表格**

### 5. 需求追踪矩阵的细节不足

**样例中的实践**：
- 需求 ID → 功能主文档
- 功能 → 关键接口（具体路径）
- 功能 → 关键数据（具体表名）
- 功能 → 跨功能 E2E（具体编号）
- 技术设计分支 → AC → 测试资产

**当前 Skill**：只有结构，缺少填充示例和关联逻辑

- 具体的影响描述格式
- 实施检查清单模板
- 决策状态的生命周期管理

### 7. E2E 验收规范的标准不足

**样例中的 E2E 定义**：
```markdown
## V1-E2E-06（E2E06）成功调用模型

Given 用户有余额、API Key 已绑定可用直连账号或本人号池，模型资产及账号精确证据可用。

When 使用 API Key 调用 `/v1/chat/completions`。

Then 返回 OpenAI 兼容成功响应，并新增用量记录、消费记录、余额流水；普通输入、输出以及夹具提供的缓存 Token 按 D027 的互斥桶、路由冻结的 PriceBook 和实际命中档准确结算，余额被扣减；API Key 和上游账号 `last_used_at` 更新。
```

**关键特点**：
- 前置条件极其详细
- 操作步骤具体
- 预期结果包含所有副作用
- 引用相关决策（D027）
- 明确数据状态变化

**当前 Skill**：Given/When/Then 过于简化

### 8. 接口契约的完整性不足

**样例中的接口定义**：
- 路径参数和查询参数的详细规则

- 时间格式的明确要求（RFC3339 + 时区）
- 错误码的精确映射
- 请求示例和响应示例都包含
- 并发控制和幂等性说明

**当前 Skill**：只有基础结构，缺少这些细节

### 9. 数据模型的深度不足

**样例中的数据模型包含**：

- 跨域关系与所有权表

- 外键策略和级联规则

- Migration 编号引用

**当前 Skill**：只有基础表结构，缺少这些关系和约束的详细说明

### 10. 文档之间的交叉引用不足

**样例中的引用模式**：
```markdown

```

每个技术设计文档都明确引用主文档的各个章节

**当前 Skill**：缺少这种交叉引用机制

## 总结

当前 Skill 提供了良好的结构框架，但在细节精度、追踪完整性、技术深度方面与样例文档存在显著差距。需要立即进行深度升级，才能真正辅助用户写出同等质量的文档。

升级重点：
1. 从"提供模板"升级到"提供带详细示例和规范的模板"
2. 从"章节结构"升级到"精确到字段级别的规范"
3. 从"独立文档"升级到"完整的追踪和引用体系"
4. 从"基础要求"升级到"严格的质量标准和检查清单"
