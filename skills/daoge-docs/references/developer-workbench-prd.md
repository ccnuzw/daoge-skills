# 开发执行工作台产品需求

## 1. 产品定位

开发执行工作台是给开发者看的项目认知与执行入口。它帮助开发者快速理解项目全貌、关系、演进、时间线和当前进展，并把人类确认后的文档上下文交给编程智能体。

Markdown、JSON、YAML、OpenAPI、迁移、代码和机器证据仍是权威来源。工作台只做只读派生，不编辑权威文档，不保存第二份业务结论，也不执行测试、门禁、部署或发布。

## 2. 设计原则

按以下顺序判断产品质量：

1. **简洁**：开发者先看到结论和下一步，不先看到生成器、摘要算法或数据结构。
2. **精准**：每个结论都能回到稳定 ID、权威文件和具体章节。
3. **全貌**：总览、关系图谱、功能演进、时间线和开发进展互相补充，不重复堆叠。
4. **可执行**：开发任务包和 Goal 清单能直接约束编程智能体。
5. **可验证**：结构就绪、机器验证和发布批准始终分开。
6. **渐进披露**：首屏只呈现开发判断；技术摘要、完整关系和证据明细按需展开。

工作台不是“渲染得越多越好”。任何新增模块都必须证明它能减少开发者的查找、判断或上下文拼接成本。

## 3. 核心用户问题

开发者打开浏览器后应能快速回答：

1. 这个项目解决什么问题，主要由哪些系统和领域组成？
2. 当前版本在做什么，哪些功能已经完成、阻塞或尚未验证？
3. 一个需求与功能、接口、数据、测试、证据和决策有什么关系？
4. 同一能力在不同版本如何演进，当前处于哪个阶段？
5. 我现在应该做什么，是否允许开始开发，完成后如何验证？
6. 如何把确定的范围交给编程智能体执行大型任务，并在文档变化时停止跑偏？

## 4. 产品边界

### 4.1 必须提供

- 项目与当前版本全貌。
- 产品架构、核心流程、数据域、风险和交付关系图谱。
- 能力跨版本演进与具体功能时间线。
- 当前功能的开发许可、进展、阻塞和下一步。
- 文档全文阅读、搜索、章节定位和目录 README 导航。
- 可复制的开发任务包和可生成的 Goal 执行清单。
- 当前提交、构建、证据新鲜度和 authority digest 的状态结论。

### 4.2 明确禁止

- 在页面中维护项目专属的静态业务常量。
- 用文档数量、页面可见性或结构完整冒充开发完成。
- 默认展示完整 JSON、长 digest、全部未变化对象或大段机器元数据。
- 将浏览器改造成项目管理、工时、聊天、任务分配或文档编辑系统。
- 从标题相似度、未来规划 prose 或文件时间猜测关系和版本承诺。
- 在浏览器内直接启动 Goal、测试、门禁、构建、部署或发布。

## 5. 主信息架构

主导航固定为六个入口：

```text
工作台｜总览｜阅读｜图谱｜功能演进｜时间线
```

主导航不得继续增加一级入口。门禁与证据并入工作台；版本变化并入功能演进；目录和章节使用侧栏或移动端抽屉。

旧 `#view=governance` 深链兼容跳转到 `workbench&panel=verification`。旧 `#view=diff` 深链兼容跳转到 `evolution&panel=changes`，但不再保留独立页面。

## 6. 六个核心视图

### 6.1 工作台

工作台首屏只保留四类信息：

1. **项目全景与当前上下文**：项目版本链可横向浏览；当前执行版本、功能和阶段单独明确。
2. **开发判断**：允许开发、阻塞或未评估，并给出一句依据。
3. **下一步行动**：一个主行动和最多三个最高优先级阻塞。
4. **开发进展**：规格、设计、实现、验证四段状态。

次级内容包括：开发确认、规格变更集、待确认规格草案、开发任务包、门禁与证据、完整阻塞清单、关系明细和来源。默认折叠，不与首屏争夺注意力。

开发确认必须单独展示为“未提出、待确认、已批准、已拒绝或已失效”。它只表示当前版本是否获得进入受控开发准备的人工授权，不得与规格就绪、实现完成、机器证据通过或 Release 批准合并。确认摘要变化后，工作台必须显示失效原因和重新提出动作。

规格修订必须单独展示当前版本的 ChangeSet：变更类型、稳定影响 ID、权威来源、人工决定状态、摘要是否失效，以及关联 Goal 的 `not_started`、`goal_ready`、`executing` 或 `completed` 交付状态。ChangeSet 只做治理投影，不在工作台维护第二份需求正文；未批准或已失效的修订不能显示为可执行 Goal。

工作台验证面板还必须只读展示当前版本的隔离规格草案：稳定 ID、目标文档、`create|replace`、草案状态、候选摘要与目标基线匹配、提出人、确认人和恢复动作。草案处于 `proposed`、`approved`、`rejected`、`superseded` 或派生 `expired` 时均不得被展示成规格事实或执行授权；`materialized` 只说明曾由 CLI 写入目标文档，当前事实仍应回到目标 Markdown。页面不提供编辑、批准或物化操作，也不增加一级导航。

工作台必须投影功能、模块和版本的交付状态，而不让页面或智能体手填“完成”：`设计中`、`可开发`、`开发中`、`待确认完成`、`开发级完成`、`需复验` 和 `例外` 分别来自规格、Goal 运行态、`completion.json` 与开发者 `DELIVERY-*` 回写。`开发级完成` 必须能展开到覆盖目标的 Goal、完成摘要和确认人；权威范围或证据变化后显示 `需复验`，旧完成记录仍仅作为历史审计。

工作台不再设置独立“个人工作视图”。只保留最后一次视图、功能、文档和滚动位置的本地恢复；收藏和最近阅读不作为核心能力。

Release 是发布资格而不是开发授权的前置条件。Release 结构或证据阻塞必须在“门禁与证据”中如实展示，并明确当前不可发布；当当前版本和功能已通过开发门禁时，首屏仍必须显示允许进入开发准备，不能用 Release finding 覆盖该结论。

工作台必须同时提供“全部版本”和单版本浏览范围，但浏览范围不是执行切换。页面必须持续标出 `current_version` 作为当前执行版本；用户浏览 V1 时，也不得让 V1 的功能、门禁、证据或任务包覆盖 V2 的 Gate、Goal、下一步与发布判断。各版本必须在工作台直接列出稳定功能 ID、名称和规格/实现/验证状态，并能进入真实功能文档，不能只显示功能数或让功能仅在阅读目录出现。各版本卡分别呈现规格、实现与验证状态；缺少该版本机器证据时显示 `unknown` 或 `not_run`，不得把规划、文档就绪或版本顺序显示为已交付。

### 6.2 总览

总览负责回答“项目是什么、现在到哪里了”，必须包括：

- 文档、版本、功能、需求和已确认决策的少量关键指标。
- 产品全景图。
- 当前版本核心业务闭环或关键用户旅程。
- 版本主链路。
- 当前开发进度摘要。
- 已确认关键决策和权威入口。

总览中的产品全景优先显示“用户与入口、业务领域、系统与依赖”三层语义，不把机器哈希 ID 作为主要标签；节点和关系必须可以回到权威来源，完整关系进入图谱查看。核心业务旅程和版本主链的每个步骤都必须可溯源，连接语义来自结构化关系边，不能由页面猜测闭环、分支或退出条件。

当前开发进度必须由工程落点、功能实现状态和机器证据派生，并为逐功能结论保留来源；文档处于 `draft` 只能说明规格成熟度，不能直接当作代码开发进度。总览不展示完整 finding、完整测试报告或逐功能时间线。

### 6.3 阅读

阅读视图负责忠实呈现 Markdown、JSON、YAML 和图表，必须支持：

- 项目视角、按版本与原始目录三种导航方式；它们可以不同于物理文件夹。
- 递归目录和目录 README 优先入口。
- 全文与结构化搜索。
- Markdown 表格、代码、图片和内部文档链接。
- 章节联动、阅读进度、深链接和状态恢复。
- 权威类型、状态、更新日期和源路径。

阅读必须完整保留权威 Markdown 正文，不能以摘要替代；章节索引只用于定位。搜索命中、图谱来源和工作台阻塞应优先进入精确章节并显示章节与行号。每篇文档的阅读位置仅在其 `content_digest` 未变化时恢复；文档更新后从目标章节或正文开头重新定位，避免旧位置误导开发者。功能规格及其技术设计可在页头显示紧凑开发上下文，并进入工作台或时间线，但不得在阅读页复制第二份需求结论。

语义目录只重新组织入口，不复制正文。文档版本归属必须由 front matter `version` 或 `Vn` 结构路径确定；没有结构证据的共享文档只在“项目全局”出现一次。原始目录模式必须保留，帮助开发者回到文件实际位置。

### 6.4 图谱

图谱负责回答“项目元素之间如何连接”。默认一次只展示一张图，使用紧凑的模式切换：

| 图谱 | 回答的问题 |
| --- | --- |
| 产品架构 | 用户、入口、系统、领域和外部依赖如何连接 |
| 核心流程 | 关键用户旅程和业务副作用如何闭环 |
| 版本路线 | 版本先后、关键依赖和退出条件是什么 |
| 数据域 | 数据所有权、读写边界和跨域关系是什么 |
| 交付追踪 | 需求、功能、AC、分支、测试、证据和决策如何连接 |
| 风险热区 | 高风险领域、原因、控制和验证入口在哪里 |

每个节点和关系必须包含稳定 ID 或权威路径。不能由浏览器代码硬编码项目业务图。

六类图谱共享同一节点、关系和来源契约，但不共享一套压缩拓扑布局：产品架构使用三层语义分区，核心流程使用顺序步骤流，版本路线使用带状态和退出条件的版本卡，数据域使用写入者/数据/只读者三栏，交付追踪默认聚焦一个功能，风险热区按等级显示原因、影响、控制和验证入口。主视图优先显示业务名称，稳定 ID 和完整关系放入折叠详情；不得为了把全部节点塞进首屏而缩小文字。

只有全部必需来源完整且没有待决节点时才能显示“已就绪”。已有部分节点但来源不完整时显示“信息不完整”，并明确说明当前图不能代表项目全貌。图谱节点必须能够进入权威文件的具体章节；当前图谱类型应进入 URL，便于开发者分享同一上下文。

### 6.5 功能演进

功能演进负责回答“能力如何随版本变化”，必须包括：

- 当前版本和未来版本主链路。
- 按能力主线组织的版本里程碑。
- 每个里程碑的用户变化、依赖与边界、完成判定和来源。
- 兼容、迁移、废弃和替代关系。
- 可选的最近变化摘要。

规划、实现和验证必须使用不同状态，不得把规划节点显示为已完成。

### 6.6 时间线

时间线负责回答“某个具体功能从哪里来、现在怎样、以后如何演进”，必须包括：

- 功能目标、领域、风险和权威主文档。
- 当前版本的后端、前端、数据、测试和证据状态。
- 当前主要差距和上游依赖。
- 当前门禁状态。
- 后续版本明确登记的用户变化、依赖、完成判定和来源。
- 未分配版本明确显示“未分配”，不推断取消或延期。

## 7. 版本变化决策

### 7.1 产品决定

取消独立“版本 Diff”一级视图。不可变快照仍保留在机器层，用于 authority 变化检测、Goal 恢复、审计和轻量变化摘要。

### 7.2 人类界面

功能演进中的“最近变化”只在存在两个可比较快照时出现，默认比较最近两个有效快照，只显示：

- 新增。
- 语义变化。
- 废弃。
- 删除。

不显示未变化对象，不默认显示快照 ID、完整 digest、API/data hash 或逐字段技术表。每项变化只显示对象、变化摘要、影响范围和权威入口；机器元数据放入可展开详情。

### 7.3 编程智能体

编程智能体不依赖可视化 Diff 判断能否继续。每份任务包和 Goal 清单都绑定 authority digest；摘要变化时任务直接进入 `stale`，重新生成上下文后再执行。

## 8. 与大型任务执行的关系

浏览器只帮助人类理解和确认，不直接执行大型任务。DAOGE Docs 必须从同一文档体系生成 Goal 执行清单，包含：

- 目标、范围和非目标。
- 选定版本、功能、需求、决策和依赖。
- 稳定分支、AC、测试命令和证据要求。
- 允许修改路径、禁止行为和停止条件。
- 有向任务依赖、串并行边界和集成顺序。
- source commit、authority digest 和恢复点。

Goal 执行规则以 `agent-goal-execution-contract.md` 为准。strict Profile 的 Goal 准备必须复用当前版本 `version_scope` 开发确认；确认缺失或摘要不匹配时，工作台可以显示规格阻塞，但不能提供 `ready` Goal。

## 9. 交互简洁性约束

- 主导航最多六项。
- 工作台首屏最多一个主按钮。
- 首屏阻塞最多显示三项，其余进入完整清单。
- 单个页面默认不同时展示超过一张复杂图。
- 原始路径、digest、commit 和 build ID 默认使用短摘要，完整值按需展开。
- 不使用卡片嵌套卡片，不用装饰性内容稀释开发信息。
- 移动端保持六个主入口可达，但允许横向滚动或“更多”菜单，不缩成难以阅读的小字。
- 页面中的每个状态词必须有明确语义；`passed` 只来自机器证据。

## 10. 成功标准

### 10.1 开发者体验

- 新开发者在 60 秒内能说明项目目标、当前版本和核心系统关系。
- 选择一个功能后，在 30 秒内能找到目标、依赖、当前差距、门禁和权威主文档。
- 任意阻塞项一次操作可进入具体文件和章节。
- 选择任意版本功能后，开发者可一键复制稳定功能 ID，或复制带 `--version <目标版本>` 的“准备该功能 Goal”受约束提示词；提示词只能请求 `prepare-goal` 和 `goal-resume-context`，`blocked` 时必须停止，`ready` 后在开发者确认前不得开始实现。历史版本 Goal 不改变当前执行版本、Gate、任务包或发布判断。
- “阅读”视图渲染 Markdown；“打开 Markdown 原文”在新标签页直接显示源码；“下载 Markdown”保存原始文件。三者均使用 UTF-8，不能用渲染页面冒充原文。
- 总览、图谱、演进和时间线之间没有相互矛盾的项目事实。
- 首屏不出现完整 JSON、长 digest 或全部未变化对象。
- 开发确认状态与 Release 批准、实现状态和机器证据分别显示；权威范围变化后确认可确定地进入“已失效”。

### 10.2 文档与派生质量

- 所有图节点、关系、里程碑和进展都携带来源。
- 图谱缺少结构化来源时明确降级，不根据 prose 猜测。
- 当前进展只能来自代码、测试、实现状态和机器证据。
- 100% 的 `passed` 状态能回到机器报告检查项。
- 工作台数据变化后，旧任务包和旧 Goal 清单能被识别为过期。

### 10.3 大型任务执行

- 只有通过对应门禁的功能才能生成 `ready` Goal 清单。
- Goal 中每个任务都有输入、允许路径、依赖、AC、验证和完成条件。
- authority digest 或 source commit 不一致时自动停止恢复。
- 完成结论必须由指定命令和证据支持，不能由智能体自行声称。

### 10.4 并行开发与文档同步

- 单功能执行提供一条可恢复 Goal 主线；选择多个功能时，工作台显示由依赖、工程落点和禁止边界派生的串行/并行泳道。
- 只有互不依赖、路径边界不冲突且不共享迁移、契约、状态或外部副作用的功能才进入同一并行泳道；无法证明安全时回退串行并说明原因。
- 并行泳道不改变每个任务独立提交、验证、检查点和集成顺序的要求。
- 开发期间允许更新后续版本文档，但任何影响当前 Goal 的范围、AC、ADR、数据/接口、工程落点或验证命令变化都必须先更新权威来源、登记并批准 ChangeSet，再触发停止、重索引、重门禁和新 Goal；实现状态与机器证据仍由真实代码和命令派生。

## 11. 开发优先级

| 优先级 | 状态 | 工作 | 原因 |
| --- | --- | --- | --- |
| P0 | 已实现 | 简化主导航和工作台首屏，移除独立 Diff 与个人工作面板 | 立即恢复开发者可读性 |
| P0 | 已实现 | 建立图谱、演进、时间线所需的结构化文档契约 | 没有可靠来源就无法复现样例深度 |
