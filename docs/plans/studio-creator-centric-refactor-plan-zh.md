# DAOGE Pic Studio 以人为本重构方案

> 目标：把 Studio 做成「以人为本、符合创作者操作习惯、能与 agent 充分协同」的工作台。
> 本文件是本轮全部探讨的固化结果，供后续参照实施。每条决策都标注了依据。
> 四个原待定问题已全部结案（见第 6 节）；重审与扩展设计见第 7 节；开放问题已全部结清（第 8 节）；
> 增量建议（待逐条认可）见第 9 节；**对照 Skill 协议与源码的终审见第 10 节**。

---

## 1. 根本问题

**Studio 的骨架是按「数据之间的关系」搭的**：项目 → 任务 → 轮次 → 运行 → 结果。
**创作者的路径是按「事情的时间顺序」走的**：想出图 → 出一批 → 挑几张 → 交出去。

两者错位，导致**工程结构被可见化**。实测证据：

| 现象 | 实测 |
|---|---|
| 一次出图要跨入口 | 动作线被切成三段（创作平台 / 资产管理 / 资产交付） |
| 路由状态要记 6 个维度 | `projectId` / `taskId` / `roundId` / `runId` / `assetScope` / `compareRoundIds`；`normalizeRoute` 为「哪些 id 该保留」单独写了一套规则和测试。（⚠️ 二轮重审发现 `roundId`≡`compareRoundIds[0]` 这一处冗余；施工期核查又推翻了 7.7.2 的另一处判断，见 **7.7.2**） |
| 用户被迫做系统决定 | **在「要人提供的内容」里，只有三个必填字段**：`projects.name`、`creative_tasks.name`、`creative_rounds.purpose`。前两个对创作者有意义，**`purpose` 是系统分类**（⚠️ 2026-09-17 核查修正：原写「全库只有三个 NOT NULL 且无默认值」，实测全库有 **245** 个——其余 242 个都由系统自动填，原意是「要人填的只有三个」） |
| 确认页在讲架构 | 「人工确认闸门 · 可写操作」「会话只能发起确认请求；确认后由会话核算一遍」——没有一个字回答「要出什么、几张」 |
| 画布上看不过来 | 单张画布最多 **349 个节点**；`round:plan = 159:157`（同一件事两个节点） |

**这不是谁做错了。** 数据关系必须存在（追溯、恢复、审计都靠它）。问题是它现在是**可见的骨架**，而不是**藏在后面的架子**。

## 2. 五条原则

1. **用户只做只有人能做的决定** —— 看、选、说、确认。其余全部自动。
2. **自动为主，手动为例外** —— 系统先铺好，人能覆盖。反过来（等人摆）就是 `canvas_groups = 0` 这个结果。
3. **唯一事实依据是 `studio.db`** —— 前端**不得造影子状态**。进度要**算**出来，不能**存**在前端。
4. **只展示人会关注的主线；工程化和给智能体看的东西，不必出现在界面上。**

   **判据：人在自然语言里会不会提到它。**（这条判据很硬，因为它直接测的是认知负担。）

   | 人怎么说 | 暴露的实体 | 处理 |
   |---|---|---|
   | 「我的 **XX 项目**」 | 项目 | 全程可见 |
   | 「做一个 **XX 系列**」 | 任务 | 可见 |
   | 「**上次那批**太暗了」 | 轮次 | 可见，**但要改叫「批次」** |
   | 「**这几张**不错」 | 图 / 素材 | 可见（主角） |
   | 「**用这张**做参考」 | 引用 | 可见（作为连线/标记） |
   | 「你**打算怎么出**」 | 计划 | **收起**（检查器） |
   | 「**跑**完了吗」 | 运行 | **收起**（状态融进批次） |
   | —— | 运行项 | **彻底隐藏**（它就是那张图） |
   | —— | 并发来源 / 计划版本 / Bearer 预检 | **不出现在界面上** |

   ⚠️ **这是「术语治理」的升级，两者的判据不同**：
   - **改词**（前面几轮做过）：这个词**必须存在**，只是说法要人话 —— 「运行并发上限」→「同时最多出几张」；
   - **藏概念**（本轮）：这个概念**根本不需要人知道**，它只对系统有意义 —— 「运行」「运行项」「计划版本」「Bearer 预检」。

   **唯一例外：出问题时。** 这些东西**不是删掉，是挪到疑难层** —— **平时不见，出事时找得到**。

   **三类「收」的做法**：
   - **隐藏下钻**：计划 → 检查器；运行 → 状态融进批次节点；运行项 → 消失；
   - **功能拆分**：轮次对比 → 画布上的动作（选中两个批次）；生成历史 → 检查器 + 列表视图；
     判据是**它服务的是「某个具体对象的疑问」，就该跟着那个对象走**，而不是让人先想「这个功能在哪一页」；
   - **换入口**：轮次 → 「批次」；共享素材 → 作为「导入」的来源；确认闸门 → 「就这么出」。

5. **层级模型：项目与任务是「人的概念」，批次及以下是「工程概念」。**

   **判据：用户能给它起名的，是人的概念；用户只能描述它的，是工程概念。**
   （「创作人物」是个名字，「第 3 轮」不是——**没人给轮次起名，但人人都给任务起名**。）

   | 层 | 性质 | 人怎么说 | 类比 |
   |---|---|---|---|
   | **项目** | **人的分类** | 「我那摊事」 | **文件夹** |
   | **任务** | **人的分类** | 「我在做的**这条线**」 | **子文件夹 / 一条创作线** |
   | 批次（轮次） | 半人半工程 | 「**上次那批**」——说「那批」，不说「轮次」 | 一次迭代 |
   | 计划 / 运行 / 运行项 | **纯工程** | 一个字都不说 | —— |

   **含义**：**前两层必须显眼、可管理**（建、改名、归档、**隔离切换**——切换任务即切换上下文）；
   **后两层必须收起来**（第 4 条原则）。

   ⚠️ **选词标准：用「职场通用词」，不用「领域方言」。**
   `项目 / 任务` 是任何行业都懂的词；换成「系列 / 画册 / 主题」就把它锁死在某个领域了。
   用户可能来自设计、文案、研究、电商、教育——**通用性不是修辞，是选词标准**。

## 3. 三层架构与边界（已定，不再讨论）

```
Workbench（cookie）  ⇄  同一套 HTTP API  ⇄  agent（bearer）
                        ↓ 都落到
                    studio.db —— 唯一事实依据
```

**分工是「动作级」的，不是「表级」的**——两侧走同一套 API、落同一个库。判据来自 `route-authorization.ts` 表头：

> 会花钱、会起停进程、会改存储凭据的动作，必须由可追责的一方发起（bearer）。

| | agent 侧（bearer） | 人侧（cookie） |
|---|---|---|
| 专属动作 | 写计划、**预检**、**创建运行**、控制运行 | **`rounds.confirm`**（唯一的人专属） |
| 两边都可 | 建项目、建任务、选片、交付 | 同左 |

**绝对不能动的四条红线**（与 3.1 一致）：`studio.db` 唯一事实、鉴权边界、确认闸门、工程能力只加强不删。
**推论**：让 Studio 代调 bearer 接口 = 拆掉闸门。**「Studio 发起」必须实现为「多一个入口」，而不是「多一份能力」。**

### 3.1 本次改造的性质：大版本升级，不背历史包袱（2026-09-16 定）

**这是一次大版本升级**，涉及理念、架构、界面、操作、流程。
**可以不兼容以往的任何结构与数据**——项目 / 任务 / 批次 / 运行 / 计划 / 布局**全部可重建**。

**这解放了什么**（原方案里的妥协可以拿掉）：

| 原方案的妥协 | 现在可以 |
|---|---|
| `canvas_*` 四张表「够用，一处不用改」 | **按新需求重新设计** |
| `collapsed` 字段「已经存在，用起来就行」 | **按新交互设计**，不被旧字段牵着走 |
| 「一份 layout + 视口聚焦」是为了少迁移 | **直接设计成新形态** |
| 「不新建表，复用 `events` 装请求」 | **可以新建 `studio_requests`**，队列语义更清晰 |
| schema 演进到 34 的积累 | **可以重来** |

**`events` 打满 2000、`plan_json` 里塞 `originRequest`** —— 这类「在既有结构里找位置」的设计，
本质是**为了不迁移而付的利息**。现在可以按「什么最清楚」来设计。

**⚠️ 一条独立的线：连图片资产也不迁移（2026-09-17 定）**

本节最初写的是「图片文件保留，通过导入进入新结构」——**2026-09-17 刀哥定了更彻底的方案：全新开始，连资产也不迁**。
`daoge-assets/`（1196 张）、`daoge-deliveries/`（129 项）**原地存档、不主动删除**，新系统不读取。
（**「不要」≠「要我删」**——回收磁盘是另一次单独确认的操作。）

**这个决定连带消掉了 #14 的两难**：只导图会让谱系断、全量映射要写迁移脚本——**既然都不迁，就没有「导一半」的问题**。

**⚠️ 但有一条不能因为「可以改」就改**：

| 可以重来 | 不该动 |
|---|---|
| 表结构、字段、schema 版本 | **`studio.db` 是唯一事实依据**（前端不造影子状态） |
| 布局数据的存储方式 | **鉴权边界**（bearer / cookie 的分工判据） |
| 请求队列的载体 | **确认闸门只有人能过** |
| 视图与路由的组织 | **工程能力只加强不删** |

**理由**：那四条是**这个产品的立身之本**，不是历史包袱。
前面几轮反复验证过它们的价值——比如「前端不造影子状态」正是它让「混合模式」变成零成本。
**换个 schema 是重写，换掉理念是换产品。**

## 4. 改造清单

### 4.1 出图：把问法倒过来（`purpose` 收口）

> **已实施 @ 2026-09-19（第 4 批：回执与问法倒过来）**

**现状**（`web/src/main.jsx` 的 `ROUND_PURPOSE_OPTIONS`，第 251-257 行）：不是一个下拉，是**两轮选择题**——

1. 从 5 个「轮次目的」里挑一个（探索/精修/变体/局部修改/补图，每个带一段「适合……」的说明）
2. 按选择展开「希望变化的维度 / 希望保持不变」
3. 定数量、比例
4. 最后才说需求

**关键发现**：`purpose` **不是一个分类字段，是一组默认参数的入口**。每个选项带着 `defaultCount` / `defaultAspectRatio` / `defaultRefinementGoals` / `defaultVariationAxes` / `defaultKeepConstraints` / `recommendedInputs` / `quickBriefs`。
**所以用户被要求「先认领一个套餐，再说需求」——顺序是反的。**

（顺带：`quickBriefs` 里那两句现成话术，正是「把 purpose 翻译成人话」的现成素材。）

**目标形态**：

```
这次要出什么
┌────────────────────────────────────────┐
│ 把夜景调亮，背景换成暖光                 │
└────────────────────────────────────────┘

我准备这么出：
  在上一批的基础上          ← 唯一需要用户核对的判断
  出 4 张 · 4:5
  改：光影、背景    保持：主体

        [ 就这么出 ]    [ 改一下 ▾ ]
```

**它不再是一个「选择」，而是一段「回执」。**

**什么必须问、什么可以推**：

| 项 | 现状 | 改成 | 理由 |
|---|---|---|---|
| **有没有上一批** | 散在「父轮次下拉 + `shouldSuggestParent`」两处（`main.jsx:929` / `:941`） | **必须问**（明示且可否决） | 结构性判断，猜错代价高 |
| 5 个细分里的哪个 | 用户选 | 系统推 | 猜错只影响标签 |
| 出几张 / 比例 | 有默认值 | 系统推，可改 | 猜错可改 |
| 改什么 / 保持什么 | 用户答两轮选择题 | 系统从话里提，可改 | 猜错可改 |
| 计划文本 | 用户写或点快捷句 | 用户写，系统据此填上面几项 | —— |

> 代码里**已经编码了这个分界**：`shouldSuggestParent` 那行就是 `['variation','refinement','edit','fill'].includes(purpose) && !parentRoundId`。系统早就知道「这四个需要上游」，只是没把它变成唯一那道必答题。

**推断由谁做**：**agent**（不是前端）。理由：agent 就是理解意图的一方，产出物 `plan_json` 本来就该含这些；前端做推断 = 把规则硬编码进界面。

**不动**：`purpose` 字段、5 个枚举值、那套默认参数、后端 API 契约、表结构。
（⚠️ 澄清：不动的是**字段与协议**；把枚举**拼给人看的 label** 属于显示层，按 7.9.3 走共享翻译表。）

**验收**：用户不需要知道那 5 个术语，也能出图；**点「改一下」展开的就是现在那套控件——一个都不删**。

### 4.2 双入口与请求队列

> **已实施 @ 2026-09-18（第 2 批：请求队列）＋ 2026-09-19（第 4 批：回执两动作）**

**已定：Studio 是主入口，对话保留为辅，两者共用一条队列。**

**理由（按强度排序）**：

1. **看图之后说的话，必须在图旁边说**。人说的是「这三张再亮一点」——**这句话里有指代**，只有 Studio 给得出。放到对话里说，用户得重新描述「那三张是哪三张」。
2. **但从零想一件事，对话更好**：还没有图可指、需要来回讨论、agent 要追问的。
3. **两者必须共用一个队列**，否则会出现两个真相（Studio 显示等待中、对话里也在等）。

**两者的能力侧重**：

| | Studio | agent |
|---|---|---|
| 强在 | **视觉在场**、指代明确、一句话换一个具体产出 | **能力密集**：调任意 skills、批量、来回讨论、编排多步 |
| 典型 | 「第 2 张那个光影好，按它再来 4 张」 | 「给我 20 条不同风格的提示词」 |

**技术形态**：

- **队列复用 `events` 表**（`entity_type` / `event_type` / `payload_json` 现成），**不新建表**。状态用**多条事件**表达（`created` → `accepted` → `done`），这才是事件流的正常用法。

  ⚠️ **但 `events` 只能当「传输中的队列」，不能当「请求档案」** —— 实测它**已经打满 2000 上限并在滚动淘汰**
  （`events_total 2000 / window 2000`）。而且现有 events 全是状态变更（`session.context_updated` 694、
  `run.items_updated` 268、`canvas.layout_updated` 251…），**没有任何一条记录「人说了什么」**。

- **请求的原话必须随它产生的那一轮永久保存**（`plan_json` 里加 `originRequest: { text, requestId }`）。
  下一个请求要的 `previousRequest`，**从上一轮的 plan 里读**即可 —— 不需要 events 长期承载。
  这样才闭环：原话永久可追、`previousRequest` 自然可得、`events` 只负责传输。

- **上下文连续性靠「数据」，不靠「记忆」**——这是本方案与「对话式界面」最大的区别。
  关键字段是 **`previousRequest`**：用户说「还是太暗了，**再**亮一点」，那个「再」必须有指代。
  带上上一个请求的原话，**agent 即使不记得也能看懂**。这条不依赖宿主能力，且符合「唯一事实」原则。

- **「agent 怎么理解的」现在只能从计划本身反推**（⚠️ 2026-09-17 终审修正）：
  **计划契约里没有「理解说明」字段**——`PreflightPlan` 只有 `operation` / `itemCount` / `prompt`（+ `itemPrompts`）/
  `referenceAssetIds` / `maskAssetId` / `output`（见 `src/vnext/runner/preflight.ts:6-14`，与 `SKILL.md` 会话工作法第 3 条一致）。
  原稿写「已有 `plan_json.brief`」是**错的**（凭印象写的字段名，与 09-16 终审抓到的两处同类）。
  所以「它的理解」目前**由计划本身表达**（提示词 + 数量 + 规格）；要更明确的说明，属于 **9.8 的契约扩展建议**，不是现成能力。
  推理的完整过程仍留在宿主会话、不进库（避免污染唯一事实）。

- **请求必须自带上下文**（项目、任务、选中的图）。**不要依赖 `studio_sessions.active_*`**——
  实测**两侧都在写它**（前端 `main.jsx:2280` POST `/api/sessions/<id>/context`；agent 侧有 `session-context` CLI；
  `SKILL.md` 第 35 行明写可写入角色是「Agent Bearer **或**已授权 Workbench Cookie」）。
  也就是说，**同一个字段被两种意图共用**——Studio 写「我在看哪儿」、agent 写「我在操作哪儿」，
  **必然互相覆盖**（session 上还带乐观锁，冲突会变成可见报错）。详见 **7.7.3**。
- **交接**：**队列 + 低摩擦唤醒**。在会话协议里加一条「**每次入场先看队列**」，这样用户本来就要跟 agent 说话，顺手就把单接了。摩擦从「一句专门的话」降到「本来要说的话」。
- **静默是最大的坑**：`accepted` 事件必须**立刻推回 Studio**（SSE 已有），界面显示「agent 正在理解…」。这一格不做，体验就卡在「我点了，然后呢」。
- **队列条目自带「流程要求」，skill 的介入不靠 agent 想起来**（2026-09-16 补）：`context_json` 里带一句
  **机器可读的任务规格**（「此请求需走 daoge-pic 计划流程」）。agent 从队列里读到的**不是一句裸话，
  是一个带规格的条目**——daoge-pic 本身就是 skill（计划契约、预检、参数约束、审核红线都在它那里），
  但「入场读队列」是**约定**，约定会被忘；**条目自己声明需要什么流程，就少一层「靠自觉」**。
  ⚠️ 边界不变：Studio 仍然不执行任何出图——它是排队叫号机，**执行方永远是装着 skill 的那个 agent**。
- **非出图的话也有去处**（2026-09-16 补）：用户可能说「帮我看看这批怎么样」——这类请求不走 skill 流程，
  agent 以普通对话回应，请求 `done` 时**带上回复内容**，显示在发起处（走 4.5 的「需要你」形态）。
  **队列接的是「用户说的话」，不是「出图指令」——两种话都接，分别处理。**

**不做**：让 daemon 内置 LLM 自己执行（= 造一个自动 agent，闸门失效）；让 Studio 代调 bearer 接口。

> ⚠️ **2026-09-16 重审**：本节「队列复用 `events`、原话塞 `plan_json`」两条是迁就现状，

### 4.3 画布重构（四刀）

> **已实施 @ 2026-09-17（第 1 批：折叠／去冗余／增量布局）＋ 2026-09-18／19（第 3 批：圈选发起、就地建任务）＋ 界面批 E（`d652045`：画布三件）**

**定位**：**画布就是主界面**，「表达」是画布上的一个操作，**不是另建一个动作流视图**。画布已经在了，能做的事比一个动作流页面多得多。

**目标形态**：**任务 + 批次 + 图 + 引用线**（项目不是节点，它是画布的标题与边界）

**依据（实测）**：

| 事实 | 数据 |
|---|---|
| 有上游（接续上一批）的轮次 | **77 个**（48%） |
| 无上游（全新方向） | **82 个**（52%） |
| 每任务轮次数 | 1 到 43 个都有（最多的一个任务挂 43 个） |
| 每项目任务数 | 18 个项目里 10 个只有 1 个任务 |
| 布局覆盖 | 18 个项目里 12 个有过布局，**只有 8 个有项目级布局、6 个连布局都没有** → 连项目级布局都没铺满，说明自动布局的触发本身有洞（画布「项目内」由 `canvas_layouts.project_id NOT NULL` 保证，不靠数量对应） |

**「结果用于下一批」不是设想，是几乎一半的实际行为**（77 : 82）——而现在的画布恰恰没把「图 → 图」这条引用线画出来。

#### 第一刀：折叠到轮次级
用起那个**已经存在却没人用**的 `collapsed` 字段。默认一个轮次 = **一个节点**（代表图 + 「共 N 张」），双击展开。
（⚠️ 2026-09-17 核查精确化：**node 级** `collapsed` 确实「存了但没人改」——它随布局保存/恢复（`creative-lineage-canvas.jsx` 多处
`collapsed: current[node.key]?.collapsed === true`），但**没有任何 UI 去切换它**；
而**group 级**的折叠**已经在用**——`group.metadata.collapsed` 有「展开 / 折叠」按钮（同文件 1359-1361 行）。
实施时要分清这两层：**要新建的是「节点折叠交互」，不是折叠机制**。）

**规模说明（别把「约 40」当上限）**：折叠后的节点数降到**「轮次数量」级别**。全局 159 个轮次 / 61 个 layout
平均不到 3 个，但**单个 layout 实测最多 349 个节点**，说明存在大项目（有任务挂 43 个轮次）。
所以「约 40」是**典型值不是上限**——最大的那个任务折叠后仍有约 45 个节点，
**必须配合「筛选」（按状态 / 时间 / 批次）与「视口聚焦」才看得过来**。
一句话：**折叠解决「一屏塞不下」，筛选解决「一屏全是它」。**

#### 第二刀：控制「展开后的密度」（不是又一次减法）

⚠️ **这一刀与第一刀不是先后两个减法步骤**——折叠之后图已经被折进轮次节点里，
写成「再砍一半」会让人以为要分两步做。

**它的真实含义是：展开某一个轮次时，铺什么、不铺什么。**

- `run_item` **不上画布**（它是「**出图槽位**」，不是那张图——实测 **1411 个槽位里 257 个是空的**，
  **空槽正是失败体验的数据基础**。原写「与 asset 近乎 1:1 冗余」是错的，见 **7.2**）
- `plan` **不上画布**（它是轮次的属性）

**即：展开一个批次，看到的就是它出的那些图** —— 不是「运行项 + 素材」两两成对，
也不是「轮次 + 计划 + 运行 + 运行项」四件套。

#### 第三刀：分组与连线改成系统生成
- 按轮次**自动成组**，写 `canvas_groups`
- 按 `parent_round_id` **自动画引用线**，写 `canvas_links`
- **这两张表从此不再是 0，但也不是用户画出来的**——关系系统知道，不该让人画

#### 第四刀：加「发起」
- **圈选 + 说一句** → 队列 → agent（接 4.2）
- 就地建项目/任务
- 就地标记交付

**中间过程的归属**：

| 实体 | 画布上 | 详情里 | 别处 |
|---|---|---|---|
| 任务 | 节点 | 名称、描述 | — |
| 批次 | 外框（自动） | **计划内容**，且**可复制** | — |
| 图 | 节点 | 来源、评审记录 | — |
| **计划** | ✗ | ✓ | 可导出（二级） |
| **运行** | ✗ | 状态摘要 | **疑难层**（失败详情） |
| 运行项 | ✗ | ✗ | 数据里保留，不上画布 |

**「照这个计划再来一批」的正确做法**：复制出来的应该是**草稿，不是执行命令**——把 `plan_json` 填进「说一句」的框当起点，可改再提交。理由：48% 是接续，**但接续从来不等于照抄**。

**技术要点**：
- `canvas_*` 四张表**按新语义重新设计**（⚠️ 原写「一处不用改」是迁就现状，已修订，见 **7.3 / 7.4 / 7.5**）
- 要加：布局算法改成**增量**模式（新节点插进已有布局，不重排全部）；自动分组/连线生成逻辑；过滤 UI

#### 手动挪过的节点：要保留（2026-09-16 定）

`canvas_node_layouts` 现在**没有「用户改过」这个标记**。
⚠️ 原方案写「加一个字段」是补丁式加法，**重审后改为「表里只存用户动过的节点」**（见 **7.3**）。
下面三种布局行为的划分不变。

**三种布局行为各司其职，不打架**：

| 行为 | 触发 | 效果 |
|---|---|---|
| **首次生成** | 新项目 / 尚无布局 | 自动铺一次 |
| **增量插入** | 新增节点 | **只把新节点放进已有布局，不重排已有的** |
| **自动整理** | **用户主动点** | 重排全部（明确是他要的） |

关键是第二行：**平时布局稳定，只有主动点「整理一下」才会重排**。
这样「挪过的不丢」与「新东西有地方放」同时成立。

#### 创作平台的完整构成（画布只是主区）

**创作平台 ≠ 画布。** 它是四块共同形成的，缺一块都不成工作台：

| 区块 | 内容 |
|---|---|
| **顶栏** | 当前项目（点它可切到项目列表）· 画布/列表视图切换 · 全局对话入口 |
| **主区** | 画布（看关系）或列表（看清单）—— **同一份数据的两种看法** |
| **检查器** | 属性 · 计划/提示词 · 确认按钮 · 复制/导出 · 生成历史 |
| **工具条** | 缩放 · 筛选（按类型/批次/状态）· 重排布局 · 选中对象时浮现的 3 个动作 |

**原五个平级视图的归宿**（它们本来就不在 4 个一级入口里，是藏在创作平台内部的）：

| 原视图 | 新归属 |
|---|---|
| `lineage`（谱系） | **主区的画布** |
| `tasks`（任务列表） | **画布上的任务节点 + 保留文件夹管理能力**（建 / 改名 / 归档 / 隔离切换）—— 依据第 2 节第 5 条：任务是人给的名字，不是工程实体 |
| `prompts`（计划） | **检查器**：点批次看它说了什么 |
| `runs`（生成历史） | **检查器 + 列表视图模式** |
| `studio-overview`（轮次对比） | **画布上的一个动作**：选中两个批次就是对比 |

**五个变一个，功能一个没少** —— 这是「收」，不是「删」。理由：它们**本质上是「看同一份数据的另一种姿势」，不是「另一个地方」**。

**画布外的五个功能**（操作/创建/切换/筛选/展示/选择）：

| 功能 | 设计要点 | 为什么 |
|---|---|---|
| 创建 | 空白处双击就建，不跳页 | 「建任务」不该是离开画布的理由 |
| 切换 | 顶栏点项目名 → 项目列表；画布/列表随时切 | 不用退出去重进 |
| 筛选 | 按类型 / 按状态（待确认、已交付）/ 按时间 | **这是「看不过来」的解药**，比折叠更主动 |
| 展示 | 画布看关系、列表看清单；缩放三档（全局/任务/批次） | 同一份数据的两种姿势 |
| 选择 | 单选 / 框选 / 加选 | **选中是一切动作的前提** |

**画布内的五个方面**：

| 方面 | 设计要点 |
|---|---|
| 节点 | 三类（任务/批次/图）；状态可视；批次可折叠展开 |
| 流程 | 引用线由系统画，**人不需要维护它** |
| **编排** | **选中 + 说一句**（不是画箭头）—— 见下 |
| 右键菜单 | 按「我想做什么」组织；随对象状态变；3-4 项 |
| 点击交互 | 单击选中 / 双击展开 / 空白双击新建 / 拖拽移动 |

**「编排」的形态 —— 这是本方案修正的一处判断**：

创作的「编排」**不是「把线连起来定义流程」，而是「在每个节点上说接下来做什么」**。
因为创作不是流水线：**人是边看边决定下一步的**。他看着 4 张，圈住其中 2 张说「按这两张再来」——**这就是编排**，
而它的动作**就是发起一次请求**，不需要用户先去画一组箭头。

| | 谁来画 | 表达什么 |
|---|---|---|
| **引用线** | **系统自动**（`parent_round_id`） | 事实上确实引用过 |
| **手动连线** | 用户（**能力保留，摆二级**） | 特殊情况下标自定义关系 |

手动连线不进主推位，依据：**实测 `canvas_links = 0`**。

#### 共享素材：走「导入」，不进画布

**「标记为共享」而不是「复制」是对的**：同一张图在两个项目里都能看到，`content_hash` 相同，
**不占额外空间**，也不会出现「两份逐渐不同步」。

**用法**：在「共享素材」里选 → 引入到当前项目 → 成为项目素材（`assets.kind = 'import'`，实测已有 65 个）
→ **然后才上画布**。

**不做「画布上能看见但不可编辑的外部素材角」** —— 那会模糊「画布 = 这个项目的东西」这条边界，
而它正是已定的「资产边界 = 项目」。要跨项目就走导入，明确且可控。

⚠️ **一个隐患要提前定**：**原项目删了这张图，共享的那份还在不在？**
建议 **不跟着删，但转正** —— 一旦被别的项目导入过，它就成了一份独立的项目资产（`kind: 'import'`），与原图解耦。
这样「删原图」最多影响历史记录，不会让别人的图凭空消失。

#### 画布的技术要点（补充）

- **视角：一个 layout + 视口聚焦，不要三个独立 layout。**
  实测 `scope_type` 分布是 **round 37 / task 16 / project 8**——用户早就在**聚焦到某一轮**了
  （这直接支持「第一刀折叠到轮次级」）。**但现在每个 scope 各是一个 layout，切视角布局全变、位置全丢**，
  这大概率就是 `project` 视角只有 8 个的原因：**切来切去太累，不如待在一个里**。
  新方案改为**一份布局 + 视口聚焦**（双击批次飞过去并放大，双击空白回到全局），**位置永远不变**。

> **⚠️ 实施修正（2026-09-19，界面方案审计发现，刀哥决议 ①）**：本句的**手势**部分不按原文实现——
> `双击批次` 与 `双击空白` 两个绑定位已分别被「**折叠 / 展开**」（第 1 批，实机验证）与
> 「**新建任务**」（第 3 批 G2）占用；而**视口聚焦能力已由「选中 + `F` / 适应选择 / 适应全部」提供**
> （右键菜单里也有「适应选择」）。故此处记为：**一份布局 + 视口聚焦（不新增手势）**——
> 「**位置永远不变**」的承诺不变。原文保留以便追溯。

### 4.4 菜单重设

**判据只有一条：这个动作有没有「作用对象」？**

| 位置 | 管什么 | 放什么 | 绝不放什么 |
|---|---|---|---|
| **工具栏**（固定） | **怎么看** | 缩放、过滤、重排布局、切视角 | 对某个东西做什么 |
| **右键菜单** | **对它做什么** | 就它了 / 照它再来 / 拿出去 | 全局设置 |
| **检查器**（4.5 详述） | **它是什么** | 来源、评审记录、那轮计划 | 动作 |

**有作用对象 → 右键；没有 → 工具栏。** 这一条能挡掉九成错位。

**菜单要随状态变**（状态标记库里已有：`review_decisions` 的 keep/review/reject/derive）：

| 状态 | 右键菜单 |
|---|---|
| 候选 | 就它了 / 不行 / 照它再来几张 / 拿出去 ｜ 详情 |

| 已交付 | 看它在哪次交付里 / 下载 ｜ 详情 |

### 4.5 对话的四种形态与检查器

> **已实施 @ 2026-09-17（第 1 批：检查器）**

**对话不是「一个对话框」，它有两条正交的轴**：

| | **节点级**（指向性强） | **全局**（能规划） |
|---|---|---|
| **明确要求** | 「这几张再亮一点」→ 直接出新计划 | 「出 10 张 4:5 的照片」→ 建任务 + 建批次 |
| **需要分析** | 「这几张哪张更适合当封面」→ agent 给判断 | 「我想做一系列，怎么拆」→ agent 拆解并落盘 |

- **节点级的价值在「不用解释指向」**——「这三张」的指代就是选中的节点，一个字的描述都不用花。
- **全局的价值在「能建东西」**——建任务、拆需求，而且**拆出来的结果直接变成画布上的节点**（「任务链落盘」）。

**agent 的产出有两种形态**（队列的响应不能只有一种）：

1. **就绪**：计划写好了，等人确认；
2. **需要你**：agent 有话要说，或需要补信息。

后者是真实场景逼出来的：用户可能问「需要什么分辨率和大小 / 需要多少的并发」——**这是在问，不是在给**。
这时 agent 要回答，而不是默默填参数。

**非出图的请求也落在这里**（2026-09-16 补）：用户在 Studio 说「帮我看看这批怎么样」，不走 skill 流程，
agent 以对话回应——请求 `done` 时带回复内容，显示在发起处。**队列接的是「用户说的话」，两种话都接。**

**确认闸门的位置：搬到检查器**。

节点上显示状态（如「待确认」）→ 点击 → 检查器里直接出现确认按钮。
好处：**人不用离开画布**，也不用记「那个计划在哪一页」；而且「哪一批在等我确认」扫一眼节点就知道。

**检查器（inspector）承载三件事**：

| 内容 | 说明 |
|---|---|
| **它是什么** | 属性 |
| **过程资产** | 计划、提示词、快照——**可查看、可复制、可导出复用** |
| **确认闸门** | 待确认时的按钮就在这里 |

**检查器还要能「手工改计划」**（2026-09-16 确认的结论）：

**能改，而且底层机制已经是对的**，三条证据：

1. **权限上本来就允许**：计划写入**没有登记**在 `route-authorization.ts` 里 → 默认两者皆可，
   即**人的 cookie 能改、agent 的 bearer 也能改**，这条从来没被堵过；
2. **确认是针对「某个特定版本」的**：`confirmRoundPlan` 带 `expectedVersion`，而写计划时
   `plan_version + 1` 与 `version + 1` **双递增**。所以：

   | 场景 | 结果 |
   |---|---|
   | 改 → 确认 | **有效**（确认的是新版本） |
   | **确认 → 再改** | **旧确认自动失效**（版本对不上） |

   第二行保证「确认」永远只对**你当时看到的那份计划**有效——**这个语义不用改**；
3. **每次改都存快照**：`round_plan_versions` 每改一次插一条（带 `state`: draft/confirmed）。
   **这就是「过程资产」的数据基础**——可回溯、可对比、可复制给下一批。

**所以缺的只是界面**（检查器里加一个「编辑」），不是机制。

⚠️ **必须做对的一件事**：**改完后明确提示「计划已更新，请重新确认」**。
否则会出现两种误会——改完以为确认过了（结果没出图）、或确认后改了却以为仍是确认态。
好在状态本身会重置（写计划时 `status` 回到 `awaiting_confirmation`），**界面如实反映即可**。

**一个不用额外设计的额外价值**：**「人手工改过的计划」说明 agent 没理解到位**，
而 `round_plan_versions` 已存下每一版，**对比 v1 与 v2 就知道人改了什么**——现成的信号，不用埋点。

**过程资产的保留原则（工程能力只加强不删）**：

- 计划 / 生成历史 / 提示词资产 / 快照 **一样都不删**；
- **画布** = 看脉络（默认视图）；**列表** = 找东西（生成历史、计划列表，作为**画布的另一个视图模式**，切换而非跳转）；**检查器** = 看单个东西的全部细节；
- **「在画布上展不展示」≠「删不删」**：默认只展示人看得过来的（任务 + 批次 + 图），计划/运行/运行项**默认不显示但检查器里都在**，**并允许手动展开**。默认做减法，但不禁止加法。

**一个权限上的判断**：「任务链落盘」（拆需求 → 建任务/批次节点）**只建结构、不出图**，
**不动钱，cookie 就能做，不需要 bearer**。只有到真正出图那一步才需要 agent 的 bearer 身份。
这让「Studio 里能做完大部分工作」站得住：**规划、建结构、挑图、交付都是人的活；只有「花钱执行」那一格留给 agent 和那道闸门。**

### 4.6 agent 连接管理

> **已实施 @ 2026-09-18（第 2 批：侦查与连接面板）**

**现状真相**：两侧**没有「关联」，只是恰好在用同一个 daemon**。
- Studio 的会话 id 是它自己在浏览器里 `crypto.randomUUID()` 造的（`web/src/workbench-session.mjs`），存 `sessionStorage`
- `studio_sessions.conversation_id` 是 UNIQUE 的，但它记的是**浏览器那个会话**
- agent 有它自己的 `--session`，两者**没有任何关系**
- **所以 agent 不知道用户在 Studio 看哪个项目**（`active_*` 两侧都在写、各写各的意图，见 7.7.3）

⚠️ **三轮核查修正（2026-09-17）**：上面「Studio 只读 `active_project_id` 却从不写它」**是错的**；
中途我曾据数据（118 条里 90 条有值）推断「是 agent 在写」，**也不对**。
**真相是两侧都在写**：前端 `main.jsx:2280` 有 POST `/api/sessions/<id>/context`；`SKILL.md` 第 35 行允许两侧；agent 有 `session-context` CLI。
结论不变（**不能依赖它**），正确理由见 **7.7.3**。

**现有地基（都已具备）**：

| 能力 | 载体 |
|---|---|
| 事件流 + SSE | `events` 表 + `GET /api/events` + `text/event-stream` |
| 会话表 | `studio_sessions`（含 `conversation_id`、`active_*_id`） |
| 身份 | `daoge-studio/runtime/daemon.json` 的 `capability` |
| 协议 | `skills/daoge-pic/SKILL.md`（**daoge-pic 本身就是一个 skill**） |

**要做的三块（只到「连接层」，不碰「能力层」）**：

1. **侦查（自动）**：扫 `~/.agents/skills`、`~/.workbuddy`、`~/.codex`、`~/.claude`、`PATH`，报告装了哪些 agent CLI。
   ⚠️ **登记一侧已有地基**：`register-skill` 已在往 `<workspace>/.agents/skills/daoge-pic`（project）与
   `~/.codex/skills/daoge-pic`（user）装 skill——**它是「配对登记」的现成雏形**，本节的「登记一次」应复用它，而不是另造。
2. **显示（最要紧）**：**当前有没有 agent 在场、最后活动时间**。这是 4.2 那套「队列 + 低唤醒」成立的前提——没有它，输入框点下去就是石沉大海
3. **配置（少而必要）**：只留「怎么唤起 agent」

**配对不需要用户记任何码**：**同一个 workspace 就是天然凭据**（一个 workspace 一个 daemon，daemon 知道自己的 `workspaceRoot`，Studio 由 daemon 提供，天生在这个 workspace 里）。agent 启动或首次操作时**登记一次**即可。

**登记要带「身份申报」**（2026-09-16 补）：登记的不只是「我在场」，还有**「我能跑什么」**——agent 启动时
申报 skill 清单与版本（如 daoge-pic v5.x），状态卡显示「daoge-pic · 已装载」。
⚠️ **这不越界**：skills 的管理（增删改）仍归宿主，Studio 只**展示 agent 的自我申报**——
用户在输入框说一句之前，先知道接单的会不会按 daoge-pic 的规范出图；
**没申报 daoge-pic 时，输入框旁明确提示**（而不是让请求石沉大海）。这是「在场 ≠ 胜任」的解法。

**边界划死**：

| 层 | 归谁 | Studio |
|---|---|---|
| 装了哪些 skills、怎么配 | 宿主 | **不碰** |
| agent 装在哪、在不在线、怎么唤起 | 系统/运行时 | 侦查 / 显示 / 配置 |

**一旦越到 skills 那一行，就变成了「Studio 在管理 agent 的 skills」——那你装几十个提示词引擎的灵活性就没了。**

**由此推出一条硬要求**：**Studio 的输入框必须足够自由**。绝不能做成「从下拉里选模板」——那样用户就没法指定用哪个 skill 了。

### 4.7 首次路径与空状态

> **已实施 @ 2026-09-17（第 1 批：首屏三形态）**

**三种形态**（不是「空状态 + 正常状态」两种）：

| 形态 | 什么时候 | 显示什么 |
|---|---|---|
| **没项目** | 全新用户 | **突出「新建项目」** —— 他连容器都还没有 |
| **有项目、没选** | 老用户每天打开的第一眼 | **项目列表** + 新建入口 |
| **选了项目** | 在做 | **画布** |

**首屏只有两条路：选一个已有项目，或建一个新项目。没有第三条。**
「直接说一句话就出图」**不属于首屏**——它是进了项目之后的事。理由：**项目是「东西放哪」**，
不选一摊事，那句话产出的图往哪儿放？**项目不是可选项，是容器。**

⚠️ **现在的实现有个错**：空状态用的是「**还没有匹配项目**」——那是**搜索无结果**的说法。
三个场景（全新用户 / 搜索无果 / 筛选无果）**共用了一句话**，所以对全新用户格外别扭：
他会以为是自己操作错了。**这三者该看到的东西完全不同**——前者要「建第一个」，后者要「换个词再搜」。

**对话的作用域：这是「对话 vs 界面」的根本区别**

| | 语境从哪来 | 所以 |
|---|---|---|
| **agent 对话** | **靠顺序**（「刚才说的那个」） | 可以说「建个新项目叫 X」，**接着说的自然属于它** |
| **Studio** | **靠选中**（「现在看的这个」） | **必须先选中一个项目**，否则不知道你在说哪个 |

**推论**：Studio 里的对话，**作用域是「项目内」，不跨项目**。
它能建任务、拆需求、发起创作、按批次迭代；**不能**新建项目并切过去、不能在项目之间搬东西。
跨项目那一步只能靠**显式选择项目**完成。（前面用的「全局对话」这个词，准确含义是**项目内的全局**。）

**创建项目时的「名称」**：

- **Studio 里建项目是显式动作**，名称是表单里的字段；
- 可以**预填一个建议值**（省打字），**但必须显示出来让他改**；
- 关键差别不在「能不能推」，而在**「推的结果要不要经过他的眼睛」**——
  对话里他亲口说了名字，所以不用再确认；表单里推出来的**必须摆在面前**，
  否则就成了「系统悄悄给他建了一摊事」。

### 4.8 挑图体验

> **已实施 @ 2026-09-17（第 1 批：挑图快捷键／2–4 张对比／4× 缩放）**

**挑图不属于「资产管理」，它属于「创作」。**

`assets`（资产管理）回答的是「我这里都有什么」——**那是盘点**；
挑图回答的是「**这几张行不行**」——**那是决策**。
所以**挑图该发生在画布上、在批次旁边**，而不是在资产管理页里翻。
（这也解释了为什么现在的评审动作本来就出现在画布里——**它在对的地方，只是缺了让它快起来的那一半**。）

**现状盘点**：

| 能力 | 现状 |
|---|---|
| 两张并排对比 | ✓ `inspector-images` 有 `is-compare` 分支（`assets.length === 2`） |
| 评审四动作 | ✓ 画布里有「成果 / 未定 / 不采用」（对应 `keep` / `review` / `reject` / `derive`） |
| 基础键盘可达 | ✓ 画布 `tabIndex={0}`、节点 `role="button"` |
| **快捷键** | ✗ |
| **3–4 张对比** | ✗ 只支持 2 张 |
| **全屏放大 + 缩放** | **部分有**：放大弹层 ✓（`onPreviewAsset`→`image-inspector`）、**缩放 0.75×–2× ✓**（放大/缩小按钮 + `--inspector-zoom` 变量，`main.jsx:1271`）；**缺的是「全屏」与「更大倍率」**（看脸/手/边缘需要 4×+） |

**挑图的心理顺序：扫 → 放大 → 比 → 标 → 下一步**

**瓶颈在「标」这一格**：10 张里挑 2 张，意味着至少 8 次「不要」的判断——
每一次都要「点开 → 找到按钮 → 点」是不可接受的。

**四条设计**：

**一、快捷键是刚需，不是锦上添花**

| 键 | 动作 |
|---|---|
| `←` `→` | 上一张 / 下一张（当前批次内） |
| `空格` | 就它了 |
| `X` | 不行 |
| `Enter` | 放大看（全屏） |
| `Esc` | 收起 |

出一批 10 张：**有快捷键是 10 次按键，没有是 10 轮「点开—找—点」**。这个差距在每天用的人身上会被放大很多倍。

**二、对比支持 3–4 张。** 两张只够「选 A 还是选 B」；实际挑图常是「这几张里挑一张」。

**三、放大要能全屏、能缩放。** 挑图的核心判断是**细节**（脸、手、边缘），缩略图上根本看不出来。

**四、挑完就地能接下一步。** 挑完那一瞬间，人最想做的是「**按这几张再来**」——
**这个按钮该就在手边**，不该让人回到画布再找节点。
这正好落在 4.3 那条上：**编排 = 选中 + 说一句**。

### 4.9 出图过程中的交互

> **已实施 @ 2026-09-17（第 1 批：占位符与撤销窗口）＋ 2026-09-18（第 2 批：队列进度）**

**现状：底层全通，缺的是「长在哪儿」**

| 能力 | 现状 |
|---|---|
| 实时推送 | ✓ `use-studio-events.mjs` 用 SSE，**带游标**（`/api/events?after=`） |
| 出图进度 | ✓ 靠 `run.items_updated` 事件 |
| 暂停 / 取消 / 恢复 / 重试 | ✓ 四个接口都在 |
| 前端接线 | ✓ `onControlRun` / `canCancelActiveRun` 已存在 |

#### ⚠️ 但有一个真实缺陷：运行控制按钮点了没用

**实测**：`runs.pause` / `runs.retry` / `runs.resume` / `runs.cancel` **四条全部 `actor: 'bearer'`**，
而界面按钮走的是浏览器 **cookie** → **必然 403**。
更糟的是**失败被静默吞掉**了——用户感觉是「**没起到作用**」而不是「报错」。
（静默失败比报错差得多：报错你知道该找谁，静默让你以为是自己不会用。）

**这是设计意图发生了倒置**：登记成 bearer 的理由是「会起停进程的动作必须由可追责的一方发起」，
意图是**防 agent 自作主张**。但**暂停和取消是止损动作**（停止继续花钱）——
**结果这道门防住的是人**：agent 不能乱停，但人也不能停。
**闸门该防的是「系统自己决定要不要花钱」，不是「人想省钱」。**

#### 解法：两类分治（2026-09-16 定）

| 动作 | 性质 | 处理 |
|---|---|---|
| **暂停 / 取消** | **止损**——不花钱且减少支出 | **开放给 cookie** —— 要改 `route-authorization` 的 `actor` |
| **重试 / 恢复** | **会重新花钱** | **保持 bearer**，但界面按钮**走队列**（点了就排上，由 agent 执行） |
| **开始生图** | 就是「确认」 | ✓ 已经是 cookie-only，已可控 |

**用户感觉都是「点了就生效」**——但重试那一类背后走的是 agent。**既不拆闸门，也不让用户等。**
（止损慢一步是实打实的成本，所以暂停/取消必须直接生效。）

#### 出图过程中的界面：让图「长出来」

**不要只给进度数字**，让**已出的图一张张填进批次框**。

**先出占位符和连线**：

- 说了要出 10 张 → 批次框里**立刻出现 10 个占位**；
- 占位上跑「生成中」的动画；
- **每出一张就替换掉一个占位**；
- 连线也可以先画，因为计划已经确定了下游。

**为什么这比进度条好**：它**同时表达了「要出几张」和「出了几张」**。
否则界面会空着好几分钟，用户只能盯着一个数字。**占位符让结构先立起来，等待这件事就有了形状。**

**四条配套设计**：

1. **已出的图立即可用**——先出的几张可以先挑（就它了 / 不行），**不用等整批完成**；
2. **控制就地**——暂停 / 取消 / 重试出现在**批次节点上**（右键或浮出工具条），**不跳 `runs` 视图**；
3. **挑完就地接下一步**——「按这几张再来」在手边（同 4.8 第四条）；
4. **部分失败的显示**——10 张里 2 张失败，界面说「**8 张出来了，2 张没成**」并给「**重试那 2 张**」，
   这比「运行失败」四个字有用得多（失败的是 2 张，不是整批）。

#### 一条要提前知道的约束

**同一个批次不能并行跑两条运行**——`idx_generation_runs_round_open` 这个唯一索引就是这么设计的
（一个轮次只能有一条活跃运行）。**但不同批次可以并行。**

**所以用户完全可以「上一批还在出，先开下一批」**——只要新建一个批次。
这是个好的约束：**它让「边说边出」成为可能，出图不用把人钉在原地。**

### 4.10 失败体验

> **已实施 @ 2026-09-17（第 1 批：失败归因）＋ 2026-09-18（第 2 批：重试走队列）**

**真实数据**（不是假设）：

```
运行：  completed 98 / failed 23 / partial 12 / cancelled 10 / paused 1 / resume_pending 1
运行项：succeeded 1154 / cancelled 92 / blocked 65 / outcome_unknown 45 / failed 36 / pending 19
```

**用户其实只问三个问题**：

| 用户的问法 | 对应状态 | 好不好办 |
|---|---|---|
| 出来了吗 | `succeeded` | ✓ 好办 |
| 没出来吗 | `failed` / `blocked` | ✓ 好办 |
| **到底出没出来** | **`outcome_unknown`** | ✗ **难办** |

#### 自动重试与手动重试，分属两层（都要有）

| | **自动重试** | **手动重试** |
|---|---|---|
| **层级** | **单张图** | **整个批次** |
| **触发** | 系统（瞬时抖动、限流） | 用户（看完成结果后决定） |
| **次数** | 由「失败后最多重试几次」这个设置决定 | 用户点几次是几次 |
| **界面** | **静默**——用户不需要知道「这是第 2 次尝试」 | **显式**——点「重试这 2 张」 |
| **结果** | 多数情况**用户无感** | 用户自己判断要不要 |

**分工**：**自动重试处理「能给一次机会的错」**（网络、限流）；
**手动重试处理「需要人介入的错」**（额度、提示词问题）。
**自动重试 N 次仍失败 → 变成 `failed` → 交给用户决定。**

#### `outcome_unknown`：先由系统对账，对不出来才请人核实

**它意味着**：请求发出去了但没收到结果——**图可能已经出了（只是没记录），也可能真没出**。
直接摆给用户会让他两头堵：**重试怕重复扣费，等又不知道等到什么时候**。

**⚠️ 2026-09-17 终审修正：这不是「系统全部消化」，而是两段式。**
`SKILL.md` 明确规定「**`outcome_unknown` 必须先由用户核实并 `resolve-unknown` 结案；不能直接重试**」，
且 `resolve-unknown`（鉴权表 `runs.outcomes-resolve`）是 **bearer**。
原稿写「必须由系统消化、不能暴露」**与 Skill 协议冲突**。正确写法：

1. **第一段（系统，自动）**：`runs.reconcile` 由 daemon 侧发起，尝试对账、把能确认的结掉；
   **对账期间界面显示「这张还在确认中……」**——这是**阶段提示**，不是终态，也不暴露术语；
2. **第二段（人，显式）**：对不出来的，**由用户核实**（去服务商后台看一眼到底出没出），
   再由 agent 执行 `resolve-unknown` 结案。
   这一步界面说的是**人话的动作邀请**（如「去服务商后台看看这张有没有出，回来告诉我就行」），
   **永远不是「结果未知」四个字**。

⚠️ **技术细节**：`runs.reconcile` 与 `runs.outcomes-resolve` 在鉴权表里**都是 bearer**，
两步都不能靠界面直接调：对账由 daemon 自己触发，结案**走队列 → agent 执行**（与 4.9 重试同一路径），
否则又会撞上「按钮点了没用」的坑。

#### 四类状态，四种说法

| 系统状态 | ✗ 不该写 | ✓ 该写 |
|---|---|---|
| `failed` | 运行失败 | **这 2 张没出来**　［重试这 2 张］ |
| `blocked` | 运行项被阻断 | **额度不够，先解决这个再试** |
| `cancelled` | 已取消 | **你取消了这一批**（不是失败） |
| `partial` | 部分完成 | **8 张出来了，2 张没成** |
| `outcome_unknown` | 结果未知 | **这张还在确认中……** |

**`blocked` 与 `cancelled` 都不是失败**——一个是钱包的问题，一个是他自己的决定。
**归到「失败」里会让用户以为系统不稳。**

#### 三条呈现原则

1. **说人话，不说状态码**；
2. **给下一步，不只给结论**（「没出来」后面永远跟一个动作）；
3. **分清「我的问题」和「系统的问题」**：

| 谁的问题 | 例子 | 该说什么 |
|---|---|---|
| **用户的问题** | 额度不够、提示词被拒 | **告诉怎么改**（充额度 / 换个说法） |
| **系统的问题** | Provider 挂了、网络抖动 | **告诉「等下再试」**，并**别让他反复试** |

**这一条决定用户该不该动手。** 分不清，他就会对着一个自己无法解决的问题反复点重试。

#### 位置：融进批次状态，不弹窗

批次显示「**完成 · 2 张没成**」，而不是跳一个错误框。
**因为失败是结果的一部分，不是异常。** 弹窗会打断人，而状态只是他扫一眼就知道的信息。

## 5. 实现难度与分期

### 5.1 难度评估

| 改造 | 难度 | 碰什么 | 主要风险 |

## 6. 原待定问题的结案（2026-09-16，全部结案）

四条**已全部结案**，不再挂「待定」。结论与依据如下。

### 6.1 Studio 里能不能内嵌对话入口？→ **按「当前不支持」设计**

**依据**：官方文档站是用户向的、没有开发者接口；本机无 hooks 配置；无任何公开的「向会话投递消息」入口。

**但结论不阻塞开发**：「队列 + 低摩擦唤醒」**本来就必做**——就算宿主支持投递，队列仍然要有
（否则 agent 怎么知道用户在 Studio 做了什么？）。差异只有一处：用户说完那句之后，是「无感等一下」
还是「回对话说一声」。

**升级路径已留好**：宿主将来开放这个能力，**只需替换交接环节**，队列 / 事件 / 状态机全不动。

### 6.2 画布上「项目」怎么呈现？→ **标题与边界**

1. **项目不是节点**，是画布的标题与边界（依据：60 项目 : 60 layout 一一对应）；**顶栏要能就地切换**，不用退出去重进。
2. **共享素材走「导入」，不进画布**——画布是项目内的（`canvas_layouts.project_id` NOT NULL），
   共享素材是 studio 级、不属于任何项目，天然在画布之外。
   ⚠️ 隐患已定：**原图被删时不跟着删，而是转正**为独立项目资产（`kind: 'import'`），与原图解耦。
3. **视角从「三个独立 layout」改成「一份 layout + 视口聚焦」**（⚠️ 重审后进一步：**删掉 `scope_type` / `scope_id` 两列**，见 **7.4**）——实测 `scope_type` 分布
   **round 37 / task 16 / project 8**，且每个 scope 各一份 layout → 切视角**布局全变、位置全丢**，
   这大概率就是项目视角只有 8 个的原因。改后**位置永远不变**。存量迁移见 6.5。

### 6.3 手动挪过的节点，自动布局要不要保留？→ **要保留**

见 4.3 的「手动挪过的节点」小节：增量插入 + 主动触发的自动整理；「记住挪过」的实现已由重审改为**表里只存用户动过的节点**（见 7.3），不再加字段。

### 6.4 `purpose` 推断出错的兜底？→ **不加额外强制确认**

**因为确认闸门本身就是兜底**：推断出错的那一刻（比如把「换个新方向」推成「接续上一批」），
计划里必然带着这个判断，界面显示「**在上一批的基础上** · 出 4 张 · …」，
而**出图这一步本来就卡在人这里**——用户正站在闸门前，看清那一行就会改。

**所以真正的问题不是「要不要确认」，是「那一行够不够显眼」**：

| 推断置信度 | 界面表现 |
|---|---|
| 高（上下文明确） | 正常显示，一行字 |
| **低（含糊、无明确指向）** | **高亮那一行 + 提示「点这里切换」** |

**不弹窗、不拦截、不问「你确定吗」**。这条模式**适用于所有「系统替你定」的东西**
（张数、比例、变体维度）——底层逻辑是一句话：
**替用户做决定是对的，但决定的结果必须可见、可改、不静默。**

### 6.5 存量数据：全部不迁移（2026-09-16 提出 → 2026-09-17 最终定）

**原疑问**：61 个 layout（round 37 / task 16 / project 8）、3828 条节点位置，
改成「一份 layout + 视口聚焦」之后，另外 60 份里的摆位怎么办。

**最终结论（2026-09-17 刀哥定）：全新方案，不做任何迁移——连图片资产也不迁。**

- 结构数据（项目 / 任务 / 批次 / 运行 / 计划 / 布局）**全部重建**——依据见 3.1；
- **图片资产也不迁移**（`daoge-assets/` 1196 张、`daoge-deliveries/` 129 项）——
  这**改写了本节的早期结论**（原定「图片保留、通过导入回新结构」）。
  **#14 的两难随之消失**：只导图会让谱系断、全量映射要写迁移脚本——**既然都不迁，就没有「导一半」的问题**；
- ⚠️ **「不要」≠「要我删」**：旧库与素材**原地存档、不主动删除**，新系统**不读取**旧数据。
  将来若确实要回收磁盘，那是一次**单独的、走删除清单确认**的操作。

**旁证支持这个决定**：`canvas_groups` 与 `canvas_links` 实测都是 0（用户从没在画布上手动建过东西）——
旧数据里真正不可再生的东西本来就少。

**于是「存量迁移」这一项彻底消失**：**不动表、不迁移、不删文件，新系统从零开始，旧数据原地留档。**

## 7. 重审与扩展设计（2026-09-16）

**本章地图**：7.1–7.6 = 第一轮重审（换掉迁就现状的设计）· 7.7 = 二轮（关系与路由）· 7.8 = 三轮（视图与搜索）· 7.9 = 四轮（术语守卫盲区）· 7.10 = 工程能力处置 · 7.11 = 四模块以人为本改造。

前面几节里有不少设计带着一句潜台词——**「能复用就别新建」**。本章逐条复核这些地方，
凡是因为怕改而保守的，换成「按新需求该有的样子」。**四条红线不动**（见 3.1）。

**判据只有一条**：这个设计是在**表达需求**，还是在**迁就现状**？

### 7.1 队列不该复用 `events` → 新建 `studio_requests`

> **已实施 @ 2026-09-18（第 2 批：迁移 35 `studio_requests`）**

**原设计（4.2）**：「队列复用 `events` 表，不新建表，状态用多条事件表达」。

**这是典型的迁就现状**——理由是「字段现成」，但语义根本不对：

| 事实 | 实测 |
|---|---|
| `events` **已精确打满上限** | **2000 / 2000**，且**只用 4 天就填满**（2026-09-12 → 09-16），正在滚动淘汰 |
| 现有 event_type 全是**状态变更** | `session.context_updated` 694、`run.items_updated` 268、`canvas.layout_updated` 256 |
| **记录「人说了什么」的** | **0 条** |

**用事件流表达状态，要回放事件才知道当前状态**；而它又在滚动淘汰——
**一个还没被接单的请求可能直接被冲掉**。这不是「省一张表」，是埋一个**静默丢单**的洞。

**新设计**：`studio_requests` 一行 = 一个请求，**状态用列表达，不用事件序列**：

```
studio_requests
  id · studio_id · project_id · task_id
  text              ← 用户原话，永久保存
  context_json      ← 自带上下文（选中的图等），不依赖 session
  status            ← pending | accepted | done | rejected
  created_at · accepted_at · done_at
  result_round_id   ← 产生的轮次（可空）
```

**连带修正（4.2）**：原话**不再塞进** `plan_json.originRequest`。
`plan_json` 只留 `request_id` 外键——**原话住在请求表里，轮次引用它**。
这样「一个请求出两批」也不会把同一句话存两遍。

### 7.2 `run_items` 不是 assets 的冗余 → 它是「出图槽位」

> **已实施 @ 2026-09-18（第 2 批：迁移 36 `run_items.asset_id`）**

⚠️ **原方案那句「run_item 与 asset 近乎 1:1（冗余表达）」是错的，已就地修正。**

**实测**：`run_items` **1411** 条，其中**只有 1154 条产出了图**，**257 条是空槽**
（cancelled 92 / blocked 65 / outcome_unknown 45 / failed 36 / pending 19）。

**空槽不是垃圾，它是 4.10「失败体验」唯一的数据基础**——
界面上「完成 · 2 张没成」那个「2」，就来自这些空槽。
**要是按「冗余」把它们合并掉，失败就再也表达不出来了。**

顺带一个实证：**`outcome_unknown`（结果未知）实测有 45 个**——
4.10 里「不能把「结果未知」四个字摆给用户」不是设想，是已经发生了 45 次的事（处置见 4.10 的两段式修正）。

**但这里确实有一个真缺陷，而且方向相反**：
`run_items` **表里根本没有 `asset_id` 列**，产出的图 id **藏在 `result_json` 的 JSON 字符串里**。
想查「这张图是哪一次出图产生的」**得先解析 JSON**——这违反「唯一事实依据」的可查性。

**新设计**：`asset_id` 提成**可空列 + 外键**。
语义变成：**槽位（`sequence` / `status` / `attempts` / 租约）与产出（`asset`）分开，靠外键连起来。**
空槽 = `asset_id IS NULL`，一句话就能查出来。

### 7.3 「手动挪过」不该加布尔字段 → 表里只存例外

> **已实施 @ 2026-09-18（第 2 批：迁移 38，只存用户动过的节点）**

**原设计（4.3）**：给 `canvas_node_layouts` 加一个「用户改过」的标记字段。

**问题**：那是「全量记录 + 一个特例标记」——3828 条里绝大多数是自动算出来的，
却每条都要多背一个字段，而且**判断逻辑散落在每一个读它的地方**。

**新设计**：**这张表只存用户动过的节点。没记录 = 自动布局算的。**

| | 原设计 | 新设计 |
|---|---|---|
| 记录数 | 3828（全量） | 用户动过的那些（实测可能就是 0） |
| 语义 | 「这条是不是用户改的」 | **「表里有的，都是用户改的」** |
| 自动整理 | 逐条判断再决定动不动 | **`DELETE FROM` 全清即可**，语义天然正确 |
| 空表含义 | 没有布局 | 全部自动布局（**空表是合法状态**） |

**这条改动的真正价值**：把「判断」从**每次读取**搬到**写入的那一刻**，
而且让「自动整理」从「遍历判断」变成「清空」。

### 7.4 `canvas_layouts` 不该有 `scope_type` / `scope_id`

> **已实施 @ 2026-09-18（第 2 批：画布一项目一份）**

**原设计的包袱**：60 份 layout 的根源就是这两列（round 37 / task 16 / project 8）。

**新设计**：一个项目**只有一份** layout，这两列**直接删掉**。

`viewport_json` **保留**（重开还在原处是有价值的），但只留一份，
并且明确它不是创作事实——**不进备份与导出的语义核心**。

### 7.5 `entity_type` 的枚举该收敛到实际上画布的那几个

> **已实施 @ 2026-09-18（第 2 批：枚举收敛四类）**

实测 `canvas_node_layouts.entity_type` 的 CHECK 约束里塞了
`project / task / round / plan / run / run_item / asset / shared_asset / delivery / group / task_type / style_ki…`

而 4.3 已经定了：**只有 task / round / asset 上画布**（外加自动生成的 group）。

**新设计**：枚举收敛到 **`task` / `round` / `asset` / `group`** 四个。
**让 schema 自己挡住违规**——「计划不上画布」就不再只是文档里的一句话，而是**数据库不让你写**。

这类约束比文档可靠，因为**文档会被绕过，CHECK 不会**。

### 7.6 本章改了什么（一览）

| 原设计 | 改为 | 为什么 |
|---|---|---|
| 队列复用 `events` | 新建 `studio_requests` | 事件表 4 天打满在滚动淘汰，会**静默丢单** |
| 原话塞 `plan_json` | 原话住请求表，`plan` 只留 `request_id` | 一个请求可出多批，不重复存 |
| `run_item` 是 asset 冗余 | **结论错误已修正**：它是出图槽位 | 257 个空槽是失败体验的基础，**合并等于删掉失败数据** |
| asset id 藏 `result_json` | 提成 `asset_id` 列 + 外键 | 「这张图哪来的」要能查，不能靠解析 JSON |
| 加「用户改过」字段 | **只存用户动过的节点** | 判断从读取搬到写入；自动整理 = 清空 |
| layout 按 scope 分 60 份 | 一项目一份，**删 scope 两列** | 60 份的根源就是它 |
| `entity_type` 十几项 | 收敛到 4 项 | 让 CHECK 约束替文档挡住违规 |

**没动的**：四条红线（3.1）。这七条改的全是**结构**，**没有一条碰理念**。

### 7.7 二轮重审：上一轮盯「表结构」，漏了「关系」和「路由」两块（2026-09-16）

上一轮重审的判据只扫了「表结构要不要改」，漏了两个更深的地方：**关系怎么表达**、**路由状态怎么组织**。
这两块才是 3.1 授权「大胆设计」后最该动、却还在迁就现状的地方。

#### 7.7.1 资产归属是一条要跳五跳的链，不是一条外键

> **已实施 @ 2026-09-18（第 2 批）＋ 2026-09-19（第 3 批 T1：读侧列优先）**

**实测**：`assets` 表里**没有** `project_id` / `task_id` / `round_id` 任何一列。
一张图「属于哪个项目」**不是直接关系**，是要在 `asset_relations` 里拼出来的：

```
asset  ──output_of──▶  run_item  ──▶  run  ──▶  round  ──▶  task  ──▶  project
```

| 关系 | 数量 | 说明 |
|---|---|---|
| `output_of → run_item` | **1154** | 产出图唯一的归属线索 |
| `attached_to → project` | 62 | 只有导入的图（`kind='import'`）有 |
| `attached_to → creative_round` | **6** | 几乎没人写 |
| `included_in → delivery` | 50 | 交付关系 |

**所以 1154 张产出图里，有 1095 张在库里没有任何「项目/轮次」级的直接归属记录**——
它们的项目归属要**跳五跳**才能查出来。

**这是「为了不迁移而付的利息」的典型**：资产表当年没加 `project_id` 列，
于是靠一张泛化的关系表去表达**本该是外键**的东西。后果：
- 「这张图属于哪个项目」**不是一个查询，是一段 JOIN 链**；
- 「资产边界＝项目」这条**已定的架构决策，在库里不是一条约束，是一个约定**——约束会被 schema 挡住，约定靠人记得。

**新设计**：给 `assets` 加 `project_id`（可空，导入/共享素材在建盘时未必有项目归属）。
**产出图在落库那一刻就写死它的项目**，不再靠关系表事后拼。
`asset_relations` 保留，但只承载**真正的「关系」**（引用、交付、brand/style kit），**不再兼任「归属」**。

**红线校验**：这不是「前端造影子状态」——恰恰相反，是把「归属」从**约定**升格为**约束**，更符合「唯一事实依据」。

#### 7.7.2 路由的 6 个维度里，有一个是冗余的（2026-09-17 施工期修正）

> **已实施 @ 2026-09-17（第 1 批 A1：降级为小改）**

文档第 1 节把「路由要记 6 个维度」当作「工程结构被可见化」的**证据**（`projectId` / `taskId` / `roundId` / `runId` / `assetScope` / `compareRoundIds`）。

**重读 `workbench-route.mjs` 后**，这 6 个里确实**有一个是冗余**：

- `roundId` 与 `compareRoundIds[0]` **是同一个值**（`parseWorkbenchRoute` 里 `roundId = compareRoundIds[0]`）——**真冗余，可只留一个**。

##### ⚠️ 原版本的错误论断（2026-09-17 施工期推翻）

本节最初写的是：`assetScope` 兼任「上下文层级」与「筛选范围」，而 `normalizeRoute` 那 41 行里
「一半在**防御一个本不该存在的歧义**」，且「拆成两个字段后，**那一半守卫直接消失**」。**这个判断被施工核查推翻了。**

**实测**（读 `tests/vnext/workbench-route.test.js`，134 行 / 10 个测试）：那些守卫**不是在防御字段歧义**，
而是在**锁住修过的真实 bug**——测试注释写得很明白：

| 守卫 | 测试注释里的原因 |
|---|---|
| 「路由不留没有支撑的上下文层级」 | 孤儿 round 曾让上下文 loader 报「请先选择一个任务，再继续查看轮次或运行。」 |
| scope 沿层级降级 | 「轮次 scope 的资产请求没有轮次时 `assetRefreshPath` 返回 null，**于是列表静默保留了旧内容**」——静默比报错更糟 |
| `assets/lineage` 深链不留 studio 作用域 | 跨层级混看没有意义 |
| `runId` 只在渲染 run 的视图存活 | 切 tab 带过去的 `run` 曾让页面答「请先打开生成运行视图」 |

**它们拆字段也不会消失**——`scope=round` 而没 `roundId` 本来就是不自洽的，**降级逻辑必须保留**。

**修正后的设计（比原方案保守，但安全）**：

- **做**：把「上下文层级」提取为**显式派生函数** `contextLevelOf(route)`
  （`roundId ? 'round' : taskId ? 'task' : projectId ? 'project' : 'studio'`），供后续（画布按层级铺、筛选范围）复用；
  在注释里澄清 `assetScope` 的角色是「筛选范围」；消除 `roundId` ≡ `compareRoundIds[0]` 的冗余；
- **不做**：删降级守卫、重写 `normalizeRoute`——那会破坏修过 bug 的防线。

**方法论（值得记住）**：**「某段代码在防御一个不该存在的歧义」是一个需要证据的断言**，
证据就是守卫测试的注释——**先读守卫，再决定删不删**。
本案中我凭 `normalizeRoute` 的代码长度推断「一半是防御」，读注释才发现每一行都对应一次真实故障。

#### 7.7.3 `studio_sessions.active_*` 的真相：两侧都在写，一个字段被两种意图共用

> **已实施 @ 2026-09-18（第 2 批：迁移 37 `agent_*`）＋ 2026-09-19（第 4 批：`sessions.context` 收 bearer）**

文档 4.6 原写「Studio 只读 `active_*` 却从不写它」；二轮重审时我据数据（118 条里 90 条有值）推断「是 agent 在写」。
**⚠️ 2026-09-17 三轮核查用代码推翻了这个修正——真相是「两侧都在写」。**

| 证据 | 说明 |
|---|---|
| `web/src/main.jsx:2280` | 前端**确实 POST** `/api/sessions/<id>/context`（带 projectId / taskId / roundId + expectedVersion）——**Studio 在写** |
| `SKILL.md` 第 35 行 | Studio Session 的可写入角色明写「**Agent Bearer 或已授权 Workbench Cookie**」——**协议允许两侧写** |
| 鉴权表 | `sessions.context` **未登记** → 默认两者皆可 |
| agent 侧 | 有 `session-context` CLI（`SKILL.md` 第 133 行）——**agent 也在写** |

**所以「不要依赖 `active_*`」这条结论成立，但前后两个理由都不对**——既不是「没人写」，也不是「只有 agent 写」。
**真正的原因是：同一个字段被两侧的两种意图共用**——Studio 写的是「我正在**看**哪儿」，
agent 写的是「我正在**操作**哪儿」，**两个不同的事实挤在一个字段里，必然互相覆盖**（4.2 原话「混在一起会互相覆盖」正是这个，现在有了代码实证）。

**新设计（比原方案更明确）**：
- 界面侧的「我正在看哪儿」**改由路由承载**（7.7.2 已定：上下文层级由三个 id 算出来，不需要存）；
- `active_*` **留给 agent 独占**（改名 `agent_*`，或在代码与注释里明确「这是 agent 的工作指针」）——
  **不是「删掉」，是「还给它的真正主人」**：agent 确实需要这个指针，只是不该和界面共用一格。

**这一条与 4.2「请求自带上下文」是同一条结论的两个落点**：上下文从「谁最后碰过 session」改成「各自明说」。

#### 7.7.4 二轮重审一览

| 原设计（迁就） | 改为 | 实测依据 |
|---|---|---|
| 资产归属靠 `asset_relations` 拼五跳 | `assets.project_id` 直接外键，产出图落库即写死 | 1154 张产出图里 1095 张无项目级归属记录 |
| 路由 6 维度都必要 | 只消除 `roundId`≡`compareRoundIds[0]` 冗余；「上下文层级」改显式派生函数 | ⚠️ 原断「一半守卫在防御歧义」被施工核查**推翻**（那些守卫锁的是真实 bug），见 7.7.2 |
| 「Studio 只读不写 `active_*`」 | **两侧都在写**（前端 + agent CLI）→ 界面侧交给路由，`active_*` 归还 agent | `main.jsx:2280` + `SKILL.md` 第 35 行 |

**三条全是「关系/状态的组织」，没有一条碰四条红线**——反而都是让「唯一事实」更硬。

### 7.8 三轮重审：视图组织和搜索索引，两处「照抄工程字段」的地方（2026-09-16）

前两轮扫了「表结构」「关系」「路由状态」，这轮扫**视图怎么组织**和**搜索怎么索引**。
两者是同一个病灶：**内容照抄了库里的工程字段，而不是「人会看/会搜的东西」**。

#### 7.8.1 搜索索引只认 3 种实体，图（主角）被类型层排除

> **已实施 @ 2026-09-18（第 2 批）**

**实测 `studio_search` 表**：`project` 18 / `task` 35 / `round` 159，**`asset` 一条都没有**。
而且这不是「没来得及建」，是**类型层就写死了**——`queries.ts:174` 的返回类型是
`entityType: 'project' | 'task' | 'round'`，**asset 从类型定义上就被排除**。

**索引内容的建法**（`migrations.ts:47-63`）是机械拼接：

| 实体 | 索引进什么 | 是人话吗 |
|---|---|---|
| project | `name || ' ' || description` | ✓ 人话 |
| task | `name || ' ' || intent_json` | ✗ `intent_json` 是 JSON |
| round | 直接 `plan_json` | ✗ 整段 JSON（含 prompt/operation/itemCount） |
| **asset** | **没建** | —— |

**两个矛盾**：
1. 文档第 2 节第 4 条说「图是主角」——但**用户搜图搜不到**，因为索引里没有 asset。
   「搜一张图」这条在数据层就是断的。
2. 搜索结果的 round `label` 是 `task.name || ' / ' || round.purpose`（`queries.ts:182`）——
   **把那个正要收口的 `purpose` 工程术语直接当显示标签**，术语治理（第 2 节）在这里被绕过。

**根因**：搜索索引的 content 是「库里有什么字段就塞什么」，不是「人会搜什么」。
`plan_json` 能搜到，是因为它正好是文本；但用户搜的是「夜景」「暖光」这种**描述**，
不是 `{"operation":"generate"}` 这种结构。

**新设计**：
- **asset 进索引**，content 用「图的可描述信息」（来源轮次的 prompt 摘要 + 评审反馈 + 交付名），
  不是文件路径或 hash；
- **round 的索引 content** 从「整段 plan_json」改成「一段人话摘要」——摘要来源是
  **计划的 `prompt` + `itemCount` + `output`**（⚠️ 计划契约**没有 `brief` 字段**，见 4.2 的终审修正）；
  若 9.8 的「理解说明」字段将来落地，则优先用它；
- **搜索结果的 label** 不再用 `purpose`，改用人话（「第 3 批 · 夜景探索」）。

**红线校验**：这仍是「唯一事实」的延伸——索引**不是**新的事实源，它是事实的**人话投影**。
「图能搜到」不是造影子状态，是补齐「图是主角」这句原则在搜索层的缺失。

#### 7.8.2 视图的「归属」是写死在高亮集合里的，不是一个结构

> **已实施 @ 2026-09-17（第 1 批 A2：视图注册表）**

文档 4.3 说「五个平级视图收成一个」，但代码（`workbench-navigation.jsx:21-24`）里，
那五个视图**不是靠「收成」实现的，是靠 `ACTIVE_VIEWS` 集合「蹭别人的高亮」**：

```js
const LINEAGE_ACTIVE_VIEWS = new Set(['lineage', 'studio-overview', 'prompts', 'runs']);
const ASSET_ACTIVE_VIEWS    = new Set(['assets', 'trash', 'shared-assets']);
```

`studio-overview` / `prompts` / `runs` 归「创作平台」、`trash` / `shared-assets` 归「资产管理」——
**这个「谁属于谁」的关系，散在几个 `Set` 字面量里，没有一个结构化的「视图 → 宿主」注册表**。

**迁就体现在**：
1. 新加一个视图，实际要动**三到四处**：`WORKBENCH_VIEWS`（`workbench-route.mjs:3`）、
   `main.jsx` 的 `viewRenderers`（每个 view 一个渲染器 key）、某个 `ACTIVE_VIEWS`（高亮归属），
   如果是 Studio 级还要加 `STUDIO_VIEWS`。漏一处就出现「视图能进但不高亮」或「高亮但没有入口」。
   ⚠️ **但漏一处并非无人发现**（2026-09-17 核查修正）：`tests/vnext/phase4-navigation-registry.test.js` **已经在守这件事**——
   它断言 `WORKBENCH_VIEWS` 与 `WORKBENCH_VIEW_RENDERERS` 一一对应、每个 view 在 main.jsx 里都有渲染器 key、
   辅助区视图必须有真入口（**明确防「孤儿视图」**）、甚至锁住「生成历史不许回一级入口」。
   所以真正的痛点是「**要手改的地方散**」，不是「漏了没人知道」；
2. 这个「视图归属」其实**和 4.3 说的「五个变一个」是同一件事**，但方案里没意识到它已经用
   「高亮集合」这种**非结构化**方式半实现了——**该把它显式化，而不是继续用 Set 凑**。

**新设计**：一个**视图注册表**（`view → { 宿主视图, label, 是否一级入口, 所需上下文 }`）。
`NAVIGATION_ITEMS`、`ACTIVE_VIEWS`、`WORKBENCH_VIEWS` 三个来源**收成一个**，从「三处手改」变「一处声明」。
这也正好接上 7.7.2——**视图的「上下文层级」和「筛选范围」拆开之后，注册表就是它唯一的落点**。

**为什么之前没发现**：前两轮的重审判据是「结构迁就现状」，而视图组织是**前端代码组织**的问题，
不在「schema/关系/路由」的射程内。这一轮把判据扩到「**照抄工程字段的地方**」，才扫到它。

#### 7.8.3 三轮重审一览（本轮）

| 原设计（迁就） | 改为 | 实测依据 |
|---|---|---|
| 搜索只索引 project/task/round | **asset 进索引**，content 用人话描述 | `studio_search` 表 0 条 asset，类型层就排除 |
| 索引塞 `plan_json` / `intent_json` 原文 | 索引入「人话摘要」（由计划字段拼；**契约无 `brief`**） | round 索引内容是整段 JSON |
| 搜索结果 label 用 `purpose` | label 用人话 | `queries.ts:182` 直接拼 `round.purpose` |
| 视图归属靠 `ACTIVE_VIEWS` Set 凑 | 收成一个**视图注册表** | 新视图要三处手改，漏一处就不高亮 |

**两条都碰不到红线**：索引是事实的「人话投影」，不是新事实源；视图注册表是前端组织，不碰鉴权/闸门/唯一事实。

### 7.9 四轮重审：术语守卫扫不到的地方（2026-09-16）

这轮扫「术语治理与文案的交叉点」。判据变了——不再是「迁就现状」，而是**「守卫扫不到的地方」**。
守卫（`terminology-guard.test.js`）只扫 `web/src` 里的**中文字符串字面量**，于是有两类文案漏网：
**① 后端造的文案；② 前端从数据字段透传的文案**。这两类都不是「字符串字面量」，守卫天生看不到。

#### 7.9.1 搜索结果是术语漏网的重灾区：英文枚举直接裸奔

> **已实施 @ 2026-09-17（第 1 批 A3：共享翻译表）**

**实测 `purpose` 存的是英文枚举**（`creative_rounds.purpose`：exploration 62 / variation 60 / refinement 32 / edit 3 / fill 2）。

而搜索结果的三处展示**全没走人话翻译**：

| 位置 | 代码 | 用户看到 |
|---|---|---|
| 后端拼 label | `queries.ts:182` `task.name \|\| ' / ' \|\| round.purpose` | `夜雨街头头像 / refinement` |
| 前端副标题 | `studio-search.jsx:22` `<small>{result.purpose}</small>` | `refinement`（英文裸奔） |
| 前端实体类型 | 同上 `'项目' : '任务' : '轮次'` | 「轮次」这个工程词也没改 |

**根因分两层**：
1. 后端 `queries.ts` 在 `src/vnext`，**不在守卫的扫描目录里**——它拼的 label 是「后端造文案」，前端只是 `<b>{result.label}</b>` 照显；
2. 前端 `<small>{result.purpose}</small>` 显示的是**数据字段**，不是字符串字面量——`visibleCopyStrings` 只抓字面量，**抓不到 `{result.purpose}` 这种运行时才求值的表达式**。

**讽刺的是**：前端 `main.jsx:251-256` 其实**已经有一张「枚举→人话」翻译表**（`ROUND_PURPOSE_OPTIONS`：exploration→「探索新方向」、refinement→「精修当前结果」…）。
**同一份 purpose，前端选片时翻译了，搜索时却裸奔**——因为翻译表没有被后端和搜索组件复用。

#### 7.9.2 「轮次→批次」的改名，决策定了、治理没跟上

> **已实施 @ 2026-09-17（第 1 批 A4：界面「轮次」→「批次」，155 处）**

文档第 2 节第 5 条已定：**「轮次」要改叫「批次」**（人只说「上次那批」，不说「轮次」）。

**但术语单（`terminology.mjs`）里根本没有「轮次」这个词**——既没标「译好」也没标「收回」。
于是「轮次」在 **18 个前端文件里出现 113 次**（不含「草稿轮次」「父轮次」），**没有一条守卫拦它**。

**这是「文档定了 ≠ 代码执行了」的又一个实例**，和之前踩过的「定义了常量 ≠ 用上了常量」是同一个病：
**决策写进了方案文档，但没落进治理三件套（术语单 + 守卫 + 人读文档），所以代码照旧。**

#### 7.9.3 判据的收束：术语守卫有两个天生盲区

这轮暴露的不是「漏改了几个词」，是**守卫机制本身有结构性的盲区**：

| 盲区 | 为什么漏 | 例子 |
|---|---|---|
| **后端文案** | 守卫只扫 `web/src`，`src/vnext` 拼的 label/message 不扫 | `queries.ts` 的 `round.purpose` |
| **数据透传** | `visibleCopyStrings` 只抓字面量，抓不到 `{result.purpose}` 运行时值 | `studio-search.jsx` 的 `<small>{result.purpose}</small>` |

**新设计**（不碰红线，只是把治理补全）：
1. **「枚举→人话」翻译表提到一个共享模块**（现在散在 `main.jsx` 的 `ROUND_PURPOSE_OPTIONS`），
   后端 `searchStudio` 和前端搜索组件都从它取 label——**一份翻译表，三处共用**；
2. **「轮次→批次」正式进术语单**（标「译好」或「收回」，给 creator 面说法「批次」），
   让守卫真正开始拦它，而不是继续靠文档口头约定；
3. 可选：给守卫加一个「**后端文案出口**」的检查点——但这一步要谨慎，
   因为后端返回的字段名（`purpose` / `status`）是**协议**，不能改；能改的只是「哪些字段**拼进给人看的 label**」。

**红线校验**：术语治理本来就是「界面词与协议词解耦」（`terminology.mjs` 头注释明写）。
这轮补的正是解耦的**另一半**——协议字段（`purpose` 英文枚举）可以继续留在库里，但**拼给用户看的时候必须翻译**。

#### 7.9.4 四轮重审一览（本轮）

| 原设计（漏网） | 改为 | 实测依据 |
|---|---|---|
| 搜索 label 用英文 `round.purpose` | label 走「枚举→人话」翻译表 | `purpose` 存英文枚举，label 裸奔 `refinement` |
| 「轮次」没进术语单 | 「轮次→批次」正式登记，守卫开始拦 | 术语单无此词，18 文件 113 处裸奔 |
| 翻译表散在 `main.jsx` | 提到共享模块，前后端共用 | `ROUND_PURPOSE_OPTIONS` 只在选片时翻译 |

**三条都碰不到红线**——反而是在**补全**术语治理那套「界面词与协议词解耦」的既定原则。

### 7.10 工程能力的处置：保留 + 增强 + 新增（2026-09-16）

**这轮不是「扫迁就」，是给工程能力做一次盘点，并定下新架构下的处置。**
刀哥澄清了「工程能力只加强不删」的含义：**不是冻结现状，而是允许增、改、增强——只要不删掉已有能力。**
所以这一节回答三个问题：现在有哪些能力、新理念落地后哪些会「入口消失但能力仍在」、为了支持新理念要增/增强什么。

#### 7.10.1 能力盘点：三层（端点 / 模型 / 入口）

**后端约 40 个端点**（`route-authorization.ts` + `server.ts` 实盘），覆盖：资产、交付、批次、备份/恢复、
预算、确认模板、项目模板、任务类型、风格/品牌 kit、质量指标、搜索、会话、事件、运行控制、用量。

**前端模型层已经相当齐备**（`web/src/*-model.mjs` + `use-*.mjs`，共 22 个）：
交付、导入、导出、离线策略、搜索、疑难处理、选择、参考用途、质量指标、视口 / minimap / 缩略图、
无障碍、provider 设置、workspace 列表、导航模型。

**入口层（`main.jsx` 里的视图 + 按钮 + 弹窗）** 是「五个平级视图 + 四个一级入口」。

**三层是齐的，真正的问题在「新交互下入口会不会断」**——见下两小节。

#### 7.10.2 会「断供」的能力：入口消失 ≠ 能力删除，必须给新入口

> **已实施 @ 2026-09-17（第 1 批）＋ 界面批 C／D（入口盘点与归位）**

「五个平级视图收成一个」之后，这些能力**后端还在、模型还在，但入口（那个视图/按钮）会消失**：

| 能力 | 现在的入口 | 收成后的风险 | 处置 |
|---|---|---|---|
| **质量指标** | `ProjectOverview`（`project-overview` 视图） | 这个视图不在 4.3 的「五视图归宿」表里，**收成后它的面板没地方去** | 迁到**检查器**（看「这个项目」时可见），或列表视图的一栏 |
| **生成历史**（runs） | `runs` 视图 | 4.3 已定「检查器 + 列表」 | 已定，无需再议 |
| **计划列表**（prompts） | `prompts` 视图 | 同上 | 已定 |
| **轮次对比** | `studio-overview` 视图 | 4.3 已定「选中两个批次」 | 已定 |
| **导出**（lineage-export） | `lineage` 视图的工具条 | 画布主区还在，工具条重设后要保住 | 保留在工具条/检查器「复制/导出」 |
| **离线策略**（offline-strategy） | 学习中心 / 独立提示 | 与画布无关，**不该被画布重构波及** | 保留独立入口，别跟着画布一起「收」 |

**关键判据**：**「收起来」只针对「看同一份数据的另一种姿势」**（4.3 已定）。**凡是一个能力的价值不在「看数据」而在「做一个动作」**（导出、备份、恢复、质量复盘），**它就不该被画布重构带走入口**——该有自己的稳定位置（工具条 / 检查器 / 系统面板）。

#### 7.10.3 该「增强」的能力：新理念让它们从「能用」变「该有」

新理念（以人为本、画布为主、队列、确认搬检查器）落地后，这些能力**本来就有，但要按新交互增强**：

| 能力 | 现状 | 增强方向 |
|---|---|---|
| **搜索** | 只搜 project/task/round，asset 缺失（7.8.1） | **asset 进索引** + 人话摘要 + 搜索即跳转选中 |
| **选择**（selection-model） | 单选/框选/加选 | 圈选发起、跨批次多选（4.3 第四刀的前置） |
| **导出** | 单批/单图 | 「按这几张再来」后导出**草稿**而非执行命令（4.3 已定） |
| **重试** | `runs.retry`（bearer） | 界面按钮走队列，用户无感（4.9 已定） |
| **暂停/取消** | `runs.pause/cancel`（bearer，点了 403） | **改成 cookie**（4.9 已定，⚠️ 鉴权表里**仍是 bearer**，未改） |
| **agent 在场** | 无（4.6 现状） | 侦查 + 显示 + 配置（4.6 已定） |

⚠️ **其中「暂停/取消改 cookie」是「方案定了、代码没改」的又一例**——和 7.9.2 的「轮次→批次」、
以及记忆里「定义了常量 ≠ 用上了常量」同款。`route-authorization.ts` 里 `runs.pause` / `runs.cancel`
现在还是 `actor: 'bearer'`，实机 cookie 打过去仍会 403。

#### 7.10.4 该「新增」的能力：新理念要求、但当前没有的

这是「工程能力只加强不删」里「加强」的真正含义——**为了支持新架构而补的新能力**：

| 新能力 | 为什么必须有 | 之前四轮的落点 |
|---|---|---|
| **`studio_requests` 队列** | 「说一句被接单」的地基 | 7.1 已定新建表 |
| **agent 入场读队列** | 队列要有人消费 | 4.2 / 7.1 |
| **视图注册表** | 三处手改变一处声明 | 7.8.2 |
| **「枚举→人话」共享翻译表** | 前后端共用一份翻译 | 7.9.1 |
| **资产 `project_id` 外键** | 归属从约定升格为约束 | 7.7.1 |
| **出图占位符 + 预期条目数** | 「让图长出来」（4.9） | 4.9 已定，需 `item_count` 前置 |
| **队列条目自带流程要求 + agent 身份申报** | skill 规范不靠自觉、在场 ≠ 胜任（4.2 / 4.6） | 2026-09-16 补，随队列与 agent 管理（二批） |

**这六条都是「新增」，不是「删」——它们补的是旧架构里「用关系表/事件流/散落翻译凑合」的洞。**

#### 7.10.5 处置原则（收束）

1. **「收起来」的判据只有一个**：它是不是「看同一份数据的另一种姿势」。
   - 是 → 收（画布/列表/检查器三态切换）；
   - 不是（它是一个**动作**：导出、备份、恢复、复盘）→ **不跟着收**，给稳定入口。
2. **「不删」的真正风险不是「有人主动删」，是「入口断了没人发现」**——
   一个能力后端在、模型在、但入口在重构时被漏掉，就静默变成了孤儿。
   **所以每个收起的视图，都要在 4.3 那张「归宿表」里有一行**；没收进的（质量指标就是漏网的那个），要显式补进去。
3. **「方案定了、代码没改」要单独列清单**——目前已知两处：`runs.pause/cancel` 仍 bearer、`轮次→批次` 没进术语单。
   这类「定了但没落地」比「没定」更危险，因为会让人误以为已经做了。

### 7.11 四个模块的「以人为本」改造（2026-09-16）

前几轮只深挖了「创作平台」。但另外两个一级入口（**资产管理**、**资产交付**）和两个管理界面
（**agent 连接管理**、**provider 设置**）同样要用「以人为本」的标准过一遍。
这轮是**正面设计**——给每个模块定目标形态，不是扫迁就。

#### 7.11.1 资产管理：从「盘点」回到「挑图的地方」

> **已实施 @ 2026-09-18～19（第 3 批 H1）＋ 界面批 D（`e80f993`：资产后台定位）**

**现状**（已核实）：后端能力扎实——`/api/assets`、`/api/assets/import`、`/api/shared-assets`、
选片（`/api/projects/:id/selection`）、评审（`review_decisions` 表，keep 407 / review 19 / derive 13 / reject 12）。
前端有 `selection-model.mjs`、`asset-import-model.mjs`、`asset-state-legend.jsx`。

**但文档 4.8 已经点破了它的定位错位**：`assets` 回答「我这里都有什么」是**盘点**，而创作者要的是
「这几张行不行」是**决策**。所以**挑图该发生在画布上、在批次旁边**（4.8 已定）。

**这带来的连锁问题**：如果挑图挪到了画布，那「资产管理」这个一级入口还剩什么？它不能变成空壳。
答案是——**资产管理退成「导入 / 整理 / 回收」的后台**，不再是「挑图的主场」：

| 资产的子能力 | 现在的归属 | 以人为本的归属 |
|---|---|---|
| **挑图（评审 keep/reject）** | 资产管理页 | **画布**（批次旁边，4.8 已定） |
| **导入外部图** | 资产管理页 | **画布/检查器的「导入」动作**（4.3 共享素材走导入） |
| **跨项目共享** | shared-assets 视图 | **保留**，但降为「来源」，不是「工作台」 |
| **整理 / 去重 / 回收站** | 资产管理页 | **保留**，作为「资产后台」——盘点确实是它的本分 |
| **质量指标** | project-overview | **检查器**（7.10.2 已定） |

**一句话**：资产管理不再是创作者「每天待的地方」，而是「需要整理时才去的地方」。**挑图从它身上剥走，回到画布**——这正是「以人为本」的核心：**人做事的地方，和东西摆放的地方，是两个地方。**

#### 7.11.2 资产交付：能力最扎实，但「用得太少」——问题是心智，不是功能

> **已实施 @ 2026-09-18（第 3 批 G3：拿出去挂选中）＋ 界面批 C／D**

**现状（已核实）**：后端交付能力**是全部模块里最硬的**——三态（draft/ready/exported）+ 幂等 receipt +
`delivery_export_journal` + `quarantine` 隔离 + 文件身份校验（contentHash/byteSize）+ 导出三件套
（`manifest.json` + `contact-sheet.html` + `creative-record.json`）。前端 `creator-delivery.jsx` 也是完整的
三阶段流程（挑选→准备→下载）+ 历史 + 批次合并 + 打包下载。

**但实测数据暴露了问题**：`deliveries` 只有 **6** 条、`delivery_assets` 50、`delivery_batches` 1、`versions` 4。
**能力最硬，用得最少。**

**这不是功能缺失，是心智错位**：交付被设计成「独立的第三段」（创作平台 → 资产管理 → 资产交付），
但创作者的真实心智是——**「我挑好了这几张，怎么拿走」**。交付不该是「另开一个地方走流程」，
该是「挑完就地接的那一下」（4.8 第四条已经说过「挑完就地接下一步」）。

**改造方向**：

| 现状 | 改为 | 为什么 |
|---|---|---|
| 「发起交付」藏在交付页里 | **发起动作挂在「选中」上**（挑完就地「拿出去」）；**一级入口保留**，作为交付记录与领取的家 | 「发起」是动作、「找回收据」是地方——动作挂选中，入口不删 |
| 三阶段（草稿/准备/导出）独立流程 | **保留流程，但起点挂在「选中」上** | 能力不删，入口从「页面」变「选中后的动作」 |
| 「合并多份交付」藏在折叠 details | **保留**，但明确是「一次发布」的二级能力 | 发布是多组图的场景，不该占主路径 |
| 导出三件套 | **保留 + 增强**（contact-sheet 已经是人话产物） | 硬能力不删 |

**判据**：和 7.10.5 一致——**交付是一个「动作」，不是「看数据的姿势」**。所以它不跟画布重构走，
而是**把「交付」这个动作接到「选中」这个所有动作的共同前提上**（4.3 已定「选中是一切动作的前提」）。

⚠️ **与已定决策对齐**：「4 个一级入口」是已定架构决策，**不重开**。本节只动「发起交付」的触发方式，
**「资产交付」这个一级入口保留**——已导出的图必须有个能找回来的地方。

#### 7.11.3 agent 连接管理：有「登记」无「探测」，按「连接层」补建

> **已实施 @ 2026-09-18（第 2 批 C1／C4：侦查与唤起配置）**

**现状（已核实；2026-09-17 三轮核查修正）**：前端**零文件**（没有 agent / detect / connect 相关组件）；
后端**不是零地基，而是「有登记、无探测」**——

- ✅ **已有登记动作**：`register-skill`（`src/vnext/cli/register-skill.ts`）会把 daoge-pic 装到 agent 侧：
  `--scope project` → `<workspace>/.agents/skills/daoge-pic`；`--scope user` → `~/.codex/skills/daoge-pic`（symlink 安装 + 安全校验）。
  **即：daemon 已经知道「agent 的 skill 目录长什么样」。**
- ❌ **没有探测动作**：没有扫 `~/.workbuddy` / `~/.codex` / `~/.claude` / `PATH` 去报告「装了哪些 agent CLI」的代码；
  `capability` 字段指 provider 的能力，不是 agent CLI 的能力。

⚠️ **这个修正让实现路径变短**：「登记」不必从零造——**4.6 的「配对登记」可以长在 `register-skill` 的路径知识上**，
真正要新建的只剩「探测」与「在场显示」。这又一次印证 8.9 的观察：**设计收敛的复利**。

**文档 4.6 已定「只到连接层，不碰能力层」**，三块要做的（侦查 / 显示 / 配置）都还没动。这一节把它的**界面形态**定下来：

| 块 | 做什么 | 界面形态 |
|---|---|---|
| **侦查** | 扫 agent CLI（workbuddy / codex / claude / PATH） | 自动，**不打扰**——只在「连接」面板里列结果 |
| **显示** | 当前有没有 agent 在场、最后活动时间 | **状态卡**（像 provider 状态卡那样，放在系统面板） |
| **配置** | 怎么唤起 agent（命令、超时） | **一个折叠区**，少而必要 |

**关键设计判断**：
1. **agent 管理不该是「一级入口」**——它和 provider 一样是「系统配置」，该在**系统面板**里（rail 右侧），
   不是和「项目管理 / 创作平台 / 资产管理 / 资产交付」平级的工作区入口；
2. **「在场」比「配置」重要**——用户最想知道的是「我说一句，有没有人在听」。
   所以**状态卡是第一优先级**（4.6 已定「显示是最要紧的」），配置是第二优先级；
3. **配对零门槛**——同一个 workspace 就是凭据（4.6 已定），**界面上不该出现「配对码」这种东西**。

#### 7.11.4 provider 设置：已成熟，只需三处「更进一步」

> **已实施 @ 2026-09-18（第 3 批 P 组：配置即测、能力徽章）**

**现状（已核实）**：`provider-settings.jsx`（453 行）已经成熟——信任模式（4 档）、连接测试
（先探测模型列表端点、按状态码分开表述）、能力徽章、密钥脱敏、config 面术语+人话副标题的治理。
**它是四个模块里唯一「已经以人为本」的。**

**可优化的三处**（不是返工，是「更进一步」）：

| 现状 | 优化 | 理由 |
|---|---|---|
| 连接测试是「点了才测」 | **保存/切换 profile 时自动测一次** | 「配完就安心」比「配完再手动验证」更以人为本 |
| 能力徽章只显示「支持不支持」 | **加「当前模型能不能用」的实时态** | 支持 ≠ 当前模型开了这个能力 |
| 限流/内存退避埋在设置页 | **退避状态浮到 rail 状态卡**（⚠️ 2026-09-17 核查修正：`runtimeReasonLabel` **已在界面上**——显示在 provider 设置页「同时出几张」旁，`provider-settings.jsx:356`；缺的不是文案也不是显示位，是**它埋在二级设置页里，常显的状态卡上看不到**） | 用户该在**不打开设置**的情况下看到「服务在限流，先放慢出图」 |

**注意**：这三处都**不碰 config 面的术语治理边界**（那套「允许术语+人话副标题+隔离」已经是对的），
只是把「测试/状态/退避」这些**运行时事实**从「藏在日志」提到「界面可见」。

#### 7.11.5 四模块收束：同一条「以人为本」判据

四块改完，归到同一条判据（和第 2 节五条原则、7.10.5 处置原则一致）：

| 模块 | 它是「地方」还是「动作」 | 处置 |
|---|---|---|
| 创作平台 | 地方（画布为主） | 主界面 |
| 资产管理 | **后台**（盘点/整理/回收） | 挑图剥走，留「整理」 |
| 资产交付 | 动作（发起）+ 地方（记录领取） | 发起挂「选中」，一级入口保留 |
| agent 管理 | **系统配置** | 进系统面板，状态卡优先 |
| provider 设置 | **系统配置** | 已成熟，补运行时态 |

**一句话收束**：**「以人为本」不是把界面做漂亮，是让每个模块回到它该在的位置——**
**做事的地方（画布）、放东西的地方（资产后台）、拿走东西的动作（交付）、系统自报家门（agent/provider 状态）。**
