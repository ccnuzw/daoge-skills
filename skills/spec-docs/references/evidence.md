# 证据：分级、记录、机器可读报告、两层检查

## 1. 证据分级

从低到高，**低等级不能冒充高等级**：

| 等级 | 含义 | 能证明什么 |
| --- | --- | --- |
| 静态核验 | 文档对照 + 代码阅读 + `EXPLAIN`/静态审计 | 需求输入自洽、结构风险；不能证明功能可用 |
| 本地自动化 | 本地单元/集成/E2E 通过 | 逻辑与契约在本地环境成立 |
| 门禁环境 | 受控 staging/门禁环境、真实依赖或接近真实的依赖 | 跨进程、真实数据库/回调/限流行为 |
| 生产验证 | 生产或生产等价环境的真实运行、故障注入、恢复演练 | 可交付、可运维 |

标注规则：静态核验必须显式声明“不构成测试通过证据”；本地结果不能改名为门禁结果；mock 掉数据库/队列/鉴权/外部回调的测试不能声称 E2E。

## 2. 验证记录格式

每条验证记录至少包含：

```text
验证日期：YYYY-MM-DD
环境：local / staging / production-gate
代码版本：commit 或构建标识
命令/用例：...
结果：通过 / 失败
证据：日志、报告或工单路径
遗留风险：...
```

功能主文档的“实现与验证”章节、版本实现状态、发布验证证据都使用这一格式。没有代码版本和命令的记录视为无效证据。

## 2.1 批次 manifest（必需）

每份交付报告都必须配一份 `<run_id>-manifest.json`，字段：`run_id / environment / code_version / commit / command / working_directory / exit_code / stats / started_at / test_report / asset_sha256 / cleanup / sanitization / scope / limitations / prior_attempts`。

- 完整 `commit` 绑定被测源码提交；`asset_sha256` 对该提交中的源码/脚本摘要逐项重算。被测提交之后存在其他源码变化时发布门禁失败。
- `limitations` 写清“不能证明什么”（例如仅 UI 证据、无生产结论），防止本地证据被升格。
- 制品与 manifest 放入执行空间的 `报告/` 目录，只追加不覆盖，命名与字段规范见该目录 README。

## 3. 一次功能验证要覆盖的层级

与功能风险相称：单元测试（分支与边界）、数据库集成（唯一、外键、事务、锁、幂等）、API 集成（鉴权、字段契约、错误码、副作用）、前端测试（表单、加载、错误、成功、权限）、关联 E2E（跨功能闭环）。资金与控制面写操作必做数据库集成；每个公开写接口必做 API 集成；每个主要页面流程必做前端测试。

## 4. 机器可读报告（可选，L 档推荐）

当项目需要“能否交付”的自动判定时，把证据写成机器可读报告 + 一份清单索引：

- **配置**：记录活动版本、权威路径、源码范围、允许的证据环境。
- **清单**：只保存当前审批与四类报告的仓库内路径。
- **报告类型**：
  - 开发环境：干净检出状态、依赖模式、实际命令与退出码、服务地址、HTTP 状态、就绪结果；结果由检查器重算。
  - E2E：环境、依赖模式、规范命令、逐用例状态；跳过或失败用例不能产生通过结果。
  - 性能：已批准负载配置的 ID、摘要、批准人和时间；每场景指标单位、比较符、阈值、实测值；检查器重算比较，不信任手填通过状态。
  - 发布：精确制品标识、当前 E2E/性能报告路径、迁移、备份、恢复、安全、冒烟、观察、回滚、角色审批；必须绑定当前提交。
- **审批绑定**：审批记录提案 ID、确认人、确认时间、权威文档 SHA-256。权威文档变化后摘要不匹配，原审批自动失效；不允许脚本自行批准或预先填写确认。

## 5. 证据边界

- 报告路径必须在仓库内或由仓库文件稳定引用受控存储，不用个人临时路径。
- 报告不包含密钥、令牌、签名 URL、完整请求体或未脱敏数据。
- 失败批次不可被后续成功批次覆盖；清单只选择当前证据，不删除历史。
- 不同环境证据不可互换。
- 不得为使门禁通过而伪造审批、时间、提交、制品、执行结果或剩余门禁。

## 5.1 轮次证据规则

- 批次状态必须带环境与日期（如 `local-mock Passed（2026-08-14）`），避免跨轮次误读。
- 历史通过不替代本轮证据；专项轮次只在专项设计文档登记本轮结论，不扩写成全项目或生产验收结论。
- 失败批次与回滚记录保留，不被后续成功批次覆盖。

## 6. 两层检查的设计

| 层 | 名称 | 检查内容 | 通过意味着 |
| --- | --- | --- | --- |
| 结构层 | `check-docs` | 目录与必需文件、链接解析、稳定 ID 唯一性、索引与文件一致、AC 映射列存在、状态词汇合法 | 文档体系自洽，可以继续工作 |
| 交付层 | `docs-gate` | AC → 测试资产存在性、命令可执行性、证据状态、审批摘要与当前提交绑定、环境匹配 | 当前构建具备交付证据 |

关键约束：**结构检查通过不代表交付就绪**；严格门禁缺少真实环境、当前源码或责任人确认时必须失败。缺证据是预期失败，不得通过填写虚构报告消除阻塞。

两个工具都已随 skill 提供，项目内各有一份副本：

1. `scripts/check-docs.mjs` + `docs-policy.json`：目录、链接、稳定编号、索引与治理一致性。
2. `scripts/docs-gate.mjs` + `docs-gate.json` + `docs-evidence.json`：AC→资产→命令→证据、四类报告重算（开发/E2E/性能/发布）、manifest 摘要、审批与权威文档摘要绑定、提交绑定、秘密扫描。
3. 两者都输出“文件:行 [CODE] 说明”，退出码非零表示失败；`docs-gate --json` 便于 CI 解析。
4. 结构检查进入日常 CI；`docs-gate` 只在候选发布分支或发布流水线运行，缺真实证据时失败是预期行为。

完整设计（配置字段、报告契约、manifest 字段、检查矩阵）见 [docs-gate.md](docs-gate.md)。
