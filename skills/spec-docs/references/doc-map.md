# 文档地图：每件事应该写在哪里

判断顺序：**先问它属于哪个问题层（范围/行为/一致性/事实），再问谁是这个事实的权威维护者**。跨文档引用用链接，不复制内容。

## 目录总览

```text
docs/
  01-项目概览/       工程结构、本地环境、上手与提交规范
  02-产品与版本/     产品蓝图、版本边界、当前版本范围与实现状态
  03-功能规格/       功能开发流程、文档规范、按版本的功能主文档
  04-技术架构/       跨功能一致的架构、接口、数据、错误码、界面约束
  05-测试与发布/     测试策略、验收空间、发布与回滚、证据规范
  06-决策记录/       冻结决策（结论）、ADR（为什么）、文档变更记录
  90-参考资料/       调研与参考，不是当前依据
  99-历史归档/       已废弃材料 + 路径迁移映射
```

编号前缀的作用是稳定排序与稳定引用，不要随意重排目录名。

## 每个目录的职责与边界

| 目录 | 回答什么问题 | 必须包含 | 不要写 |
| --- | --- | --- | --- |
| 01-项目概览 | 怎么跑起来、怎么协作 | 环境要求与启动、目录结构、提交信息规范 | 产品规则、接口字段 |
| 02-产品与版本 | 做不做、哪个版本做、做到哪了 | 蓝图、路线图、全版本硬约束、开发门禁、当前版本总览/产品需求/实现状态 | 单功能接口字段、异常矩阵 |
| 03-功能规格 | 单个可验收目标怎么做 | 开发流程、文档规范、版本索引、编号表、追踪矩阵、查找表、风险分级、技术设计索引、领域 README、逐功能主文档（+高风险技术设计） | 跨功能公共规则、重复的接口/数据总表 |
| 04-技术架构 | 跨功能必须一致的东西 | 总体架构、服务/领域边界、接口契约 + openapi、数据模型、统一错误码、界面与路由规范 | 单功能业务规则、验收用例 |
| 05-测试与发布 | 怎么证明做到、怎么上线与回退 | 测试策略、安全基线、证据报告规范、端到端验收规范 + 执行空间（环境说明/测试夹具/执行手册/用例矩阵/验证证据）、发布执行空间（检查清单/部署/回滚/恢复/验证证据） | 需求原文、接口定义 |
| 06-决策记录 | 为什么这样定、推翻了什么 | 冻结决策（含状态与取代关系）、ADR（背景/备选/理由/后果）、文档变更记录 | 实现进度、待办清单 |
| 90-参考资料 | 调研、外部资料、旧系统参考 | 调研结论、参考项目笔记、离线浏览工具 | 当前权威结论（只能引用） |
| 99-历史归档 | 以前是什么样 | 废弃文档、迁移映射、Brainstorm 记录 | 当前开发输入 |

## 命名规则

- 人工阅读的文档：`编号-中文主题.md`，例如 `19-余额冻结与调用扣费.md`、`06-添加上游服务商-技术设计.md`。
- 版本前缀文档：`V1-版本总览.md`、`V1-接口契约.md`、`V1-数据模型.md`。
- 保留行业英文名的文件：`README.md`、`openapi.yaml`、`migration` 文件、代码标识、API 路径、数据库字段。
- 版本目录：`当前版本/`（活跃、完整规格）、`后续版本/`（单文件规划，未过门禁不拆细）、`V1/`（功能规格内按版本分组）。
- 领域目录：`01-身份与权限/`、`02-供给与路由/` 这类两位编号 + 域名词。域的数量和名称按项目实际定义，不要照抄示例。
- 功能编号在版本内全局唯一、跨版本不复用；功能文件在领域目录内用两位编号。
- 功能主文档开头保留 YAML frontmatter（`title/version/feature_id/domain/updated`），便于检索与自动检查。实现状态只在版本实现状态文档维护，功能文档不复制状态值。

## 公共基线清单（每个活跃版本）

这些是跨功能一致性的落点，任何功能文档只引用、不复制：

| 基线 | 文件 | 说明 |
| --- | --- | --- |
| 接口语义 | `04-技术架构/当前版本/V1-接口契约.md` | 公共规则：鉴权、分页、幂等、错误包体结构 |
| 机器可读接口 | `04-技术架构/当前版本/V1-openapi.yaml` | HTTP 字段、类型、约束、请求/响应示例的唯一权威 |
| 数据语义 | `04-技术架构/当前版本/V1-数据模型.md` | 约束、状态、事务、删除与保留策略 |
| 数据物理事实 | 代码库 migration 目录 | 表结构以 migration 为准，文档负责解释 |
| 错误码 | `04-技术架构/统一错误码.md` | 数值码 + error_key + 触发条件，一一对应 |
| 界面与路由 | `04-技术架构/当前版本/V1-界面规范.md`、`V1-页面路由矩阵.md` | 页面状态、交互约定 |
| 全版本硬约束 | `02-产品与版本/全版本产品与交互约束.md` | 所有版本必须遵守的产品级约束 |
| 测试与证据 | `05-测试与发布/测试策略.md`、`证据报告规范.md` | 层级、最低矩阵、证据格式 |
| 跨功能验收 | `05-测试与发布/端到端验收/README.md` + `Vx-端到端验收规范.md` | 规范冻结“验收什么”，执行空间负责环境/夹具/顺序/证据 |
| 性能与容量 | `05-测试与发布/性能与容量/README.md` + `场景矩阵.md` | 负载模型、场景、报告与门禁证据；静态预检不等于压测通过 |
| 发布门禁 | `05-测试与发布/发布/README.md` + `检查清单.md` | 部署、回滚、恢复、签字与证据 |

## 导航文档写法

每个目录的 `README.md` 只做三件事：

1. 一段话说明本目录职责。
2. 链接列表（按阅读顺序或主题分组）。
3. 如目录内存在多个权威来源，附“权威来源表”。

根 `docs/README.md` 额外包含：按任务查找表、推荐查找顺序、目录说明、权威来源总表、命名规则、搜索与检查命令。它是人和 AI 的第一入口，必须保持链接有效（由 `check-docs` 校验）。

## 常见“写错地方”的判断

| 内容 | 正确位置 | 原因 |
| --- | --- | --- |
| HTTP 接口字段、类型、约束与示例 | OpenAPI；功能主文档只写业务语义、错误条件及 operationId 引用 | 避免同一字段在 Markdown 与 OpenAPI 双重维护 |
| 可执行示例与夹具（driver/schema/fixture） | `04-技术架构/当前版本/示例/` | 示例只证明契约可解析，不建立第二套规则 |
| 生成的图表（演进图、依赖图） | `02-产品与版本/图表/` | 由脚本生成，属于聚合视图而非权威 |
| 客户端法律文本（用户协议/隐私政策） | `02-产品与版本/客户端法律文本.md` | 版本无关、需要版本化与生效日期 |
| 目标环境部署形态与配置清单 | `05-测试与发布/发布/部署配置.md` | 与部署手册分离：一个写“配什么”，一个写“怎么发” |
| 脱敏证据制品与 manifest | `05-测试与发布/端到端验收/报告/` | 批次证据只追加不覆盖，命名与字段有固定规范 |
| 专项/轮次测试设计（带日期） | `05-测试与发布/端到端验收/` 下单独文件 | 不进主用例矩阵，主矩阵只挂索引 |
| 金额单位、精度 | 数据模型 + 统一错误码/计费公共规则 | 跨功能一致性约束 |
| “为什么不用 MySQL” | ADR | 有备选方案和长期后果 |
| “这个字段默认值改成 30 天” | 冻结决策 + 功能文档 + 契约 | 影响多方的口径变化 |
| “目前做到哪了” | 版本实现状态 | 单一状态来源 |
| 旧版接口示例 | 99-历史归档 + 迁移映射 | 不能与当前契约并列 |
| 竞品调研、技术选型对比 | 90-参考资料 或 ADR | 前者是素材，后者是结论 |
