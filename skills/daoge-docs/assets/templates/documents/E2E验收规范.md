E2E 验收只覆盖跨组件用户旅程和最终业务结果，不替代单元分支、数据库约束、契约测试、性能或安全专项。

## 关键旅程

每条旅程必须单独建立用例文档，并至少包含：

1. Given：用户、权限、数据、依赖和功能开关状态。
2. When：从公开 UI、API、回调或受控任务入口触发。
3. Then：响应、数据库状态、审计、外部调用次数和可观察副作用。
4. Replay/Failure：适用的重复、并发、超时、未知结果、失败和补偿。
5. Cleanup：失败与成功后的数据保留或清理。

## 依赖真实性

- PostgreSQL、身份/权限、领域事务和本系统状态持久化必须使用真实实现。
- 如果缓存、队列、对象存储或外部渠道属于目标行为，必须使用真实组件或明确的发布级等价环境。
- 可控替身必须记录请求、支持确定响应和失败注入；不得 mock 内部 repository/service 后声称 E2E。
- 每批报告必须记录依赖模式和与生产的差异；低等级结果不得改名为高等级证据。

## 通过与失败规则

- 必须从真实入口触发，不直接调用内部函数绕过协议、授权或事务。
- 必须校验最终业务状态和副作用，不能只断言页面可见或 HTTP 200。
- `passed` 要求所有必需步骤和副作用断言通过并有稳定证据。
- `skipped`、`not_run`、`environment_failed`、`evidence_incomplete` 都不能计入通过。
- 业务失败与环境失败必须分开；手工改库、补写终态或删除失败数据不能把批次改为通过。
- 涉及资金、权限、删除或不可逆外部副作用的不变量失败时立即停止相关用例。

## 退出条件

- [ ] 当前版本所有稳定需求至少映射一个 E2E 用例。
- [ ] 必需用例 ID 与机器报告 `required_case_ids` 完全一致。
- [ ] 每条必需用例从真实入口执行，核心组件真实性满足环境下限。
- [ ] 成功、拒绝、重复、依赖失败和补偿终态具有适用覆盖。
- [ ] 报告绑定当前 commit/build、带时区时间、命令、退出码和脱敏证据。
- [ ] 无未解释跳过、共享环境污染或跨批次夹具依赖。
