# 设计评审：提问方法与高风险识别

所有写规格的模式都先用本文件的方法做设计评审，再生成文档。价值在于写文档之前发现设计漏洞，而不是把需求换个格式。

## 目录

1. 提问原则
2. 高风险信号与必问问题
3. 风险分级
4. 对话示例

## 1. 提问原则

- **先读后问。** 用户已经给出的信息（功能名、范围、风险判断）不再重复问。有代码或旧文档时先读，再基于证据提问：“代码里用事务同时创建用户和余额账户，这是有意的设计吗？”
- **一轮集中问 3～5 个关键问题。** 不要一次一个问题地来回拉扯，也不要列 20 个问题的清单。优先问会改变数据模型、事务边界或接口契约的问题。
- **问具体的失败场景。** 不要问“考虑过异常吗”，要问“用户记录创建成功、余额账户创建失败时，会留下半成品用户吗？”
- **给出可选方案和取舍。** 用户没想过的问题，给 2～3 个方案和各自代价，让用户选择，而不是让用户从零设计。
- **用户说“你决定”时：** 选一个方案并写明理由，在冻结决策里记录“由助手选定、用户授权”，不要伪称用户逐条确认。
- **信息足够时直接写。** 用户给了完整输入且风险为标准时，可以不提问，直接生成，并在交付说明里列出你做的假设。

## 2. 高风险信号与必问问题

| 信号 | 典型问题 | 需要落到文档的位置 |
| --- | --- | --- |
| 一个操作写多个表或资源 | 中间步骤失败时前面的写入要撤销吗？是同一事务还是补偿？ | 业务规则、数据与事务、回滚 AC |
| 并发访问同一资源 | 两个请求同时扣同一余额会超扣吗？用什么锁或约束？ | 技术设计并发控制、并发 AC |
| 重复请求（重试、回调、用户重复点击） | 幂等键是什么？重复请求返回什么？ | 接口契约、幂等 AC |
| 调用外部服务 | 超时多久？失败重试吗？外部成功本地失败怎么补偿？ | 外部调用与补偿、对账 AC |
| 状态机 | 哪些状态转换非法？并发转换怎么处理？ | 状态与生命周期、非法转换 AC |
| 金额、权限、密钥、个人数据 | 精度和币种？谁能看谁能改？日志会不会泄露？ | 安全与日志、越权 AC，独立技术设计 |
| 删除 | 物理删除还是软删除？历史记录如何关联？ | 冻结决策、数据约束 |

发现这些信号时，主动指出并给出建议，不要等用户问。

## 3. 风险分级

| 级别 | 判断标准 | 文档要求 |
| --- | --- | --- |
| 标准 | 单表 CRUD、无资金、无外部调用、无复杂并发 | 功能主文档；简要技术设计写在主文档“技术设计”章节 |
| 高风险 | 命中上表中资金、权限、密钥、外部回调、并发写任一项 | 功能主文档 + 独立技术设计（带分支 ID 和分支到测试追踪表） |

用户自己判断的风险等级与信号不一致时，说明理由并建议调整，最终以用户决定为准，并写进功能卡“风险等级”。

## 4. 对话示例

**用户：** 我要做余额扣费，调用模型前扣钱。

**好的回应（一轮集中提问）：**

> 扣费涉及资金和并发，我按高风险功能处理，会生成独立技术设计。动笔前需要确认 4 件事：
>
> 1. 调用前不知道实际用量。是先按上限冻结、结束后按实际扣费并释放差额，还是调用后直接扣？前者防超扣，后者实现简单但可能透支。
> 2. 同一用户并发调用时，用行锁（`SELECT … FOR UPDATE`）串行化，还是用条件更新 `balance >= amount` 加重试？
> 3. 幂等键用请求 ID 吗？同一请求重放时返回首次结果还是报错？
> 4. 上游调用失败时，冻结金额立即释放，还是由后台任务按超时释放？
>
> 我倾向：预冻结 + 行锁 + 请求 ID 幂等 + 失败立即释放。你确认后我把第 1、3 条记为冻结决策。

**不好的回应：** 依次问“功能名是什么？”“目标是什么？”“包含哪些能力？”，每次只问一个；或者不问任何问题直接套模板生成。
