# SDD 开发输入完整度：功能、契约与端到端验收

本指南用于把产品场景收敛成可实现、可验证的规格。样板的价值是每条链路都能回答“输入、规则、终态、失败、副作用、证据”；不要求复制样板的篇幅或把同一字段维护在多个文件。

## 当前版本与未来能力

当前版本的功能主文档只让**本版交付切片**进入 Ready 和本版 AC。跨版本延续同一功能 ID 时，在功能边界或演进矩阵概述未来方向；未来版本的行为、AC、技术设计和 E2E 放到对应版本的规划/规格空间。已经分配的稳定 ID 不重命名、不复用；历史上误用当前版本前缀标记未来用例时，保留原记录作迁移映射，在未来版本解锁时分配新用例 ID，并更新引用。

每个 AC 需要给出可观察结果及失败时不应发生的副作用。将正常、权限、非法输入、重复、并发、外部失败、恢复、取消/回滚对照功能风险逐项判断；不适用时写理由。初始测试资产和命令可以标为计划，不能当成已执行证据。

## 接口公共契约

公共接口文档应逐操作列出：稳定 `operationId` 或 SDK/事件动作 ID、入口和传输、鉴权主体、所属功能、实现阶段、成功终态、主要失败和字段权威位置。组合表达如 `create/update/delete` 不能代替三个独立操作的契约映射。HTTP 字段和响应形状以 OpenAPI 为权威；非 HTTP IPC/SDK/事件有对应机器可读 schema 或明确的契约文件。若只知道逻辑动作、还不知道字段/认证/错误，标为 Draft，不宣称可以据此编码。对有状态变更或外部副作用的操作补齐超时预算、重试/退避与幂等边界、并发控制、观测信号、告警和恢复；不适用要说明理由。

对每条跨进程写操作，核对幂等键、并发版本、权限重新校验、超时/重试、失败副作用与观测方式。规划中的操作与本版可调用操作分区，接口清单与 OpenAPI/SDK schema 的操作集合一致；从契约清单追到功能 AC 和 E2E。

## 数据公共契约

先按版本和领域列实体清单，区分本版持久化实体、派生快照、短暂缓存与未来模型。对于本版关键实体，至少说明所有者、标识、关系、状态与转换、唯一/引用/检查约束、并发和幂等保护、删除/保留/敏感数据策略。跨域写入要标出事务边界和失败补偿。尚未选择数据库或 migration 时说明待冻结问题、责任人和前置依赖，保持 Draft；不能用几十个字段名代替结构决策。

物理列、索引和 DDL 以 migration 为准；数据文档解释为什么需要约束及验证方式，并链接 migration。每次迁移写兼容窗口、回滚/失败处理、可复现验证证据和责任人。规划期可以先写逻辑实体和预期不变量，但不能声称物理约束已落地。

## 端到端验收规范

规范中的每个本版 E2E ID 独立成节，写明关联功能和 AC、入口、必须真实的本系统依赖、允许的外部替身、Given/When/Then、至少一条关键失败或无副作用断言。用例矩阵负责目标测试资产、断言事实类型、环境、日期、代码版本、命令、证据路径、限制和当前状态；单行摘要不能替代规范正文。矩阵里的本版用例与规范中的 ID 应双向对应，发布门禁只引用本版用例。未来版本用例写在未来版本规划/验收方向；不要因为已有夹具名称而提前计入当前门禁。

Then 要检查响应之外的最终事实，例如数据库状态、事件/任务终态、审计、外部请求次数和敏感信息未泄露。关键依赖被 mock 时只能证明较低层级；证据报告写出环境、依赖模式、提交、命令、结果和限制。

## 评审顺序

1. 从版本 PRD 的每条关键场景追到本版功能、接口/数据契约和 E2E；无来源的操作、实体和用例必须解释。
2. 从每个功能的正常与高风险失败分支反向检查 AC、技术设计分支和测试目标，确保没有“实现时再决定”的规则。
3. 核对当前/未来版本、Draft/Ready、计划/已执行证据的边界。发现冲突先冻结决策，再同步权威来源。
4. 运行结构检查并评审业务语义。自动检查能发现缺节、断链、错误归属，不能证明设计选择正确。
